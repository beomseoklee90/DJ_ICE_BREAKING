<section class="chapter">
  <div class="chapter-number">Chapter 01</div>

  <h2>가장 먼저 해야 하는 것 — 프로젝트의 기본 틀 만들기</h2>

  <p>
    아직 아무 프로젝트도 없다면
    가장 먼저 Codex가 작업할 수 있는
    <strong>프로젝트의 기본 틀</strong>을 만들어야 합니다.
  </p>

  <p>
    이 단계에서는 실제 기능을 만들지 않습니다.
    프로그램을 개발할 수 있는 기본 환경만 준비합니다.
  </p>

  <div class="key-point">
    <strong>이번 단계의 목표는 하나입니다.</strong><br><br>

    앞으로 기능 개발을 시작할 수 있는
    <strong>빈 프로젝트를 정상적으로 만드는 것</strong>입니다.
  </div>


  <h3>1. 기술 스택을 몰라도 괜찮습니다</h3>

  <div class="concept">
    <div class="concept-title">
      🏗 어떤 기술을 사용할지는 Codex에게 판단하게 할 수 있습니다.
    </div>

    <p>
      개발 입문자가 처음부터 React, Vue, Vite,
      상태 관리 library 같은 기술을 비교해서 선택할 필요는 없습니다.
    </p>

    <p>
      어떤 프로그램을 만들 것인지 알려주고,
      현재 규모에 적절하면서 많이 사용되는 기술을
      Codex가 선택하게 할 수 있습니다.
    </p>
  </div>

  <div class="warning">
    <span class="box-title">⚠️ 아직 기능을 만들지는 않습니다</span>

    이번 프롬프트에서는
    로그인, 일정 관리, 게시판 같은 실제 기능을 구현하지 않습니다.

    먼저 프로젝트가 정상적으로 시작되는 상태까지만 만듭니다.
  </div>


  <h3>2. 빈칸만 채워서 새 프로젝트를 만듭니다</h3>

  <p>
    아래에서 <strong>빈칸만 자신의 아이디어에 맞게 작성</strong>하면 됩니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">Template 01 — 새 프로젝트 만들기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">새로운 웹 애플리케이션 프로젝트를 만들어줘.

[만들고 싶은 프로그램]
→ ______________________

[프로그램의 규모]
→ ______________________
예: 개인이 사용하는 작은 웹앱
예: 여러 사용자가 사용하는 웹 서비스

[앞으로 만들 예정인 주요 기능]
- ______________________
- ______________________
- ______________________

나는 구체적인 기술 스택을 잘 모른다.

현재 프로그램의 규모와 목적에 맞는
일반적이고 유지보수하기 쉬운 기술 스택을 네가 선택해줘.

다음 조건을 지켜줘.

- 현재 규모에 비해 지나치게 복잡한 기술은 사용하지 마.
- 특별한 이유가 없다면 널리 사용되는 기술을 우선해줘.
- 아직 필요하지 않은 backend, database, authentication은 추가하지 마.
- 불필요한 dependency는 추가하지 마.
- 미래 기능을 예상해서 과도한 architecture를 만들지 마.

이번 작업에서는 프로젝트의 기본 틀만 만들어줘.

아직 실제 기능은 구현하지 마.
`.md` 프로젝트 문서도 아직 만들지 마.
배포도 하지 마.

프로젝트 생성이 끝나면
선택한 주요 기술이 무엇인지와
각각 어떤 역할을 하는지만 간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      아무것도 없는 상태에서
      실제 기능 개발을 시작할 수 있는 빈 프로젝트를 만드는 템플릿입니다.
    </div>
  </div>


  <h3>3. 이 프롬프트가 하는 일은 딱 하나입니다</h3>

  <div class="concept">
    <div class="concept-title">
      📁 개발 가능한 기본 프로젝트 생성

    </div>

  <h2>프로젝트의 규칙과 설명을 `.md` 파일에 남깁니다</h2>

  <p>
    프로젝트의 기본 틀이 만들어졌다면
    다음으로 Codex가 앞으로 계속 참고할
    <strong>프로젝트 설명과 작업 규칙</strong>을 남깁니다.
  </p>

  <p>
    이때 사용하는 것이 Markdown,
    즉 <code>.md</code> 파일입니다.
  </p>

  <div class="key-point">
    <strong>쉽게 생각하면:</strong><br><br>

    소스코드 = 실제 프로그램<br>
    <code>.md</code> = 프로그램에 대한 설명과 개발 규칙
  </div>


  <h3>1. 왜 채팅에만 적어두면 안 될까요?</h3>

  <div class="concept">
    <div class="concept-title">
      💬 채팅과 프로젝트 문서는 역할이 다릅니다.
    </div>

    <p>
      ChatGPT나 Codex와 대화하면서
      여러 가지 개발 결정을 할 수 있습니다.
    </p>

    <div class="concept-example">
      “현재 framework는 계속 유지한다.”<br><br>

      “새로운 library는 꼭 필요한 경우에만 추가한다.”<br><br>

      “기능 수정 때문에 기존 데이터를 깨뜨리지 않는다.”<br><br>

      “현재 디자인 스타일을 유지한다.”
    </div>

    <p>
      이런 중요한 내용이 채팅에만 있다면
      다음 작업을 할 때 다시 설명해야 할 수 있습니다.
    </p>

    <p>
      중요한 내용을 프로젝트 안의 <code>.md</code> 파일에 남겨두면
      Codex가 다음 작업에서도 다시 읽고 참고할 수 있습니다.
    </p>
  </div>


  <h3>2. 처음에는 문서를 많이 만들 필요가 없습니다</h3>

  <p>
    작은 프로젝트에서 처음부터
    문서 파일을 10개씩 만들 필요는 없습니다.
  </p>

  <p>
    입문 단계에서는 우선 아래 두 종류만 이해하면 충분합니다.
  </p>

  <div class="role-grid">

    <div class="role-card">
      <h3>🤖 AGENTS.md</h3>

      <p>
        Codex가 프로젝트에서 작업할 때
        <strong>계속 지켜야 하는 기본 규칙</strong>을 적습니다.
      </p>

      <p>
        예:
      </p>

      <ul>
        <li>현재 기술 스택을 함부로 바꾸지 않는다.</li>
        <li>기존 코드를 먼저 확인한다.</li>
        <li>불필요한 dependency를 추가하지 않는다.</li>
        <li>임시방편으로 문제를 해결하지 않는다.</li>
        <li>배포는 사용자가 요청할 때만 한다.</li>
      </ul>
    </div>


    <div class="role-card">
      <h3>📚 docs/*.md</h3>

      <p>
        프로젝트 자체에 대한
        <strong>자세한 설명</strong>을 적습니다.
      </p>

      <p>
        예:
      </p>

      <ul>
        <li>무엇을 만드는 프로젝트인가?</li>
        <li>현재 어떤 기능을 만들 계획인가?</li>
        <li>어떤 기술을 사용하고 있는가?</li>
        <li>어떤 기능은 아직 만들지 않는가?</li>
      </ul>
    </div>

  </div>


  <div class="key-point">
    <strong>구분해서 기억하세요.</strong><br><br>

    <code>AGENTS.md</code> = Codex에게 주는 작업 규칙<br>
    <code>docs/*.md</code> = 프로젝트에 대한 설명
  </div>


  <h3>3. 가장 먼저 AGENTS.md만 만듭니다</h3>

  <p>
    첫 번째 명령에서는

  <div class="prompt-card">

    <pre class="prompt-body">현재 프로젝트에
`AGENTS.md` 파일을 만들어줘.

이번 작업의 목적은
앞으로 Codex가 이 프로젝트에서 작업할 때
항상 따라야 하는 기본 규칙을 기록하는 것이다.

현재 프로젝트 구조와 사용 중인 기술을 먼저 확인한 뒤,
이 프로젝트에 맞는 `AGENTS.md`를 작성해줘.

다음 원칙을 포함해줘.

[기본 작업 원칙]

- 작업 전에 관련 기존 코드를 먼저 확인한다.
- 현재 framework와 주요 기술 구성을 특별한 이유 없이 변경하지 않는다.
- 새로운 주요 dependency는 꼭 필요한 경우에만 추가한다.
- 같은 기능을 하는 로직을 불필요하게 중복해서 만들지 않는다.
- 임시방편, TODO, hardcoding으로 핵심 문제를 해결하지 않는다.
- 현재 프로젝트 규모에 비해 지나치게 복잡한 architecture를 만들지 않는다.
- 관련 없는 코드를 불필요하게 수정하지 않는다.

[안전 원칙]

- 기존 데이터를 깨뜨릴 수 있는 변경은 조심해서 진행한다.
- destructive한 데이터 변경은 사용자의 명시적인 요청 없이 진행하지 않는다.
- 배포는 사용자가 명시적으로 요청할 때만 진행한다.
- 중요한 기술 구조 변경이 필요하면 임의로 진행하지 말고 먼저 알려준다.

[문서 원칙]

- `AGENTS.md`를 지나치게 길게 만들지 않는다.
- 상세한 프로젝트 설명은 나중에 `docs/` 문서로 분리할 수 있게 한다.
- 아직 결정되지 않은 미래 architecture를 임의로 공식 규칙으로 만들지 않는다.

이번 작업에서는
`AGENTS.md`만 만들어줘.

소스코드는 수정하지 마.
새로운 기능도 구현하지 마.
다른 `.md` 문서도 아직 만들지 마.

완료되면
`AGENTS.md`를 만들었다고만 간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      Codex가 앞으로 프로젝트에서 작업할 때
      계속 지켜야 하는 기본 규칙만 만드는 템플릿입니다.

<section class="chapter">

  <h2>이미 있는 기능의 동작을 수정합니다</h2>

  <p>
    앱을 직접 사용하다 보면
    기능 자체는 필요하지만
    <strong>현재 동작 방식이 마음에 들지 않는 경우</strong>가 있습니다.
  </p>

  <p>
    이때 기능을 새로 만들 필요는 없습니다.
    Codex에게 현재 구현을 확인하게 한 뒤
    원하는 동작으로 수정하도록 요청하면 됩니다.
  </p>

  <div class="key-point">
    <strong>이번 단계의 목표는 하나입니다.</strong><br><br>

    이미 존재하는 기능 하나를
    <strong>원하는 방식으로 수정하는 것</strong>입니다.
  </div>


  <h3>1. 현재 동작과 원하는 동작을 나누어 설명합니다</h3>

  <div class="concept">
    <div class="concept-title">
      🔄 “무엇이 지금과 달라져야 하는가?”를 알려줍니다.
    </div>

    <p>
      어떤 파일이나 함수를 수정해야 하는지
      직접 찾을 필요는 없습니다.
    </p>

    <p>
      대신 다음 두 가지를 명확하게 설명합니다.
    </p>

    <div class="concept-example">
      <strong>현재 동작</strong><br>
      완료 버튼을 누르면 일정이 현재 위치에 그대로 남아 있다.<br><br>

      <strong>원하는 동작</strong><br>
      완료 버튼을 누르면 완료된 일정이 목록 아래쪽으로 이동했으면 좋겠다.
    </div>
  </div>


  <h3>2. 빈칸을 채워 기능 하나를 수정합니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">Template 08 — 기존 기능 수정하기</span>
      <span class="prompt-target">Codex</span>

    <pre class="prompt-body">현재 프로젝트에 이미 있는
아래 기능 하나를 수정해줘.

작업 전에
`AGENTS.md`, 관련 `docs/`,
그리고 이 기능과 관련된 기존 코드를 먼저 확인해줘.

[수정할 기능]
→ ______________________

[현재 동작]
→ ______________________
→ ______________________

→ ______________________

2. ______________________________________________

- ______________________
- ______________________

→ ______________________

특별한 조건이 없다면:
→ 기존 데이터가 깨지지 않게 유지

- 관련 없는 다른 기능은 변경하지 마.

- 현재 구현에서 재사용할 수 있는 로직은 그대로 활용해줘.
- 임시방편이나 hardcoding으로 원하는 동작처럼 보이게 만들지 마.

이번 작업에서는
위 기능의 동작만 수정해줘.

다른 기능은 추가하지 마.

<section class="chapter">
  <div class="chapter-number">Chapter 06</div>

  <h2>더 이상 필요하지 않은 기능을 삭제합니다</h2>

  <p>
    개발하다 보면 처음에는 필요하다고 생각했던 기능이
    나중에는 필요 없어질 수 있습니다.
  </p>

  <p>
    이때 화면에서 버튼만 숨기는 것이 아니라,
    <strong>그 기능과 관련된 코드를 실제로 정리</strong>할 수 있습니다.
  </p>

  <div class="key-point">
    <strong>이번 단계의 목표는 하나입니다.</strong><br><br>

    현재 프로젝트에서
    <strong>특정 기능 하나를 안전하게 삭제하는 것</strong>입니다.
  </div>


  <h3>1. 기능 삭제는 버튼 하나를 지우는 것과 다를 수 있습니다</h3>

  <div class="concept">
    <div class="concept-title">
      🗑 하나의 기능이 여러 코드와 연결되어 있을 수 있습니다.
    </div>

    <p>
      예를 들어 일정 중요도 기능을 삭제한다고 생각해 봅시다.
    </p>

    <div class="concept-example">
      중요도 선택 UI<br>
      ↓<br>
      중요도 데이터 저장<br>
      ↓<br>
      중요도 표시<br>
      ↓<br>
      중요도 관련 상태 관리<br>
      ↓<br>
      중요도 관련 테스트
    </div>

    <p>
      화면에서 선택 버튼만 없애면
      사용하지 않는 코드나 데이터 처리 로직이
      프로젝트 안에 계속 남을 수 있습니다.
    </p>
  </div>

  <div class="key-point">
    그래서 Codex에게는
    <strong>기능과 관련된 영역을 먼저 찾아본 뒤 삭제</strong>하도록 요청하는 것이 좋습니다.
  </div>


  <h3>2. 삭제하기 전에 영향 범위만 확인할 수도 있습니다</h3>

  <p>
    단순한 기능은 바로 삭제해도 되지만,
    다른 기능과 많이 연결되어 있을 것 같다면
    먼저 어디에 영향을 주는지만 확인할 수 있습니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">Template 13 — 삭제할 기능의 영향 범위 확인하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트에서
아래 기능을 삭제하려고 한다.

[삭제하려는 기능]
→ ______________________

아직 코드는 수정하지 마.

`AGENTS.md`, 관련 `docs/`,
그리고 현재 소스코드를 확인해서
이 기능이 어떤 부분과 연결되어 있는지만 조사해줘.

다음 내용만 알려줘.

- 이 기능과 직접 관련된 주요 영역
- 함께 삭제해야 할 코드가 있는지
- 다른 기능이 이 기능에 의존하고 있는지
- 저장된 데이터에 영향을 줄 가능성이 있는지

아직 실제 삭제 작업은 하지 마.</pre>

    <div class="prompt-purpose">
      기능을 바로 삭제하기 전에
      다른 기능이나 데이터에 미치는 영향만 확인하는 템플릿입니다.
    </div>
  </div>


  <h3>3. 빈칸을 채워 기능 하나를 삭제합니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">Template 14 — 기존 기능 삭제하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트에서
아래 기능 하나를 삭제해줘.

작업 전에
`AGENTS.md`, 관련 `docs/`,
그리고 이 기능과 연결된 기존 코드를 먼저 확인해줘.

[삭제할 기능]
→ ______________________

[삭제 후에도 반드시 유지해야 하는 기능]

- ______________________
- ______________________
- ______________________


[기존 저장 데이터 관련 조건]

→ ______________________

특별한 조건이 없다면:
→ 기존 사용자의 다른 데이터는 그대로 유지


다음 원칙을 지켜줘.

- 화면에서 기능만 숨기고 관련 코드를 그대로 남겨두지 마.
- 해당 기능에서만 사용하던 코드가 있다면 함께 정리해줘.
- 다른 기능에서도 사용하는 공통 코드는 삭제하지 마.
- 관련 없는 코드는 수정하지 마.
- 다른 기능의 동작은 변경하지 마.
- 기존 사용자 데이터 중 다른 기능에 필요한 데이터는 삭제하지 마.
- 현재 framework와 주요 dependency는 유지해줘.

이번 작업에서는
위 기능 하나를 삭제하는 것만 진행해줘.

새로운 기능을 추가하거나
다른 기능을 redesign하지 마.

완료되면
어떤 기능을 삭제했는지만 간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      기존 기능 하나와 그 기능에서만 사용하던 코드를
      안전하게 제거할 때 사용하는 기본 템플릿입니다.
    </div>
  </div>


  <h3>4. 예를 들어 중요도 기능을 삭제한다면</h3>

  <div class="concept">
    <div class="concept-title">
      ✏️ 이런 식으로 작성할 수 있습니다.
    </div>

      • 일정 수정<br>
      • 일정 삭제<br>
      • 완료 처리<br><br>

      중요도와 관련 없는 일정 데이터는 그대로 유지한다.

  <p>

  <p>

  <p>

      여러 기능의 연결을 확인하는 Integration Test,
      실제 사용자 흐름을 확인하는 E2E Test 등을 사용할 수 있습니다.
    </p>

    <p>
      어떤 테스트 방법이 적절한지는
      현재 프로젝트를 보고 Codex가 판단하도록 맡길 수 있습니다.
    </p>
  </div>


  <div class="prompt-card">

- 사용하지 않는 코드가 확실하다면 제거해줘.
- 지나치게 복잡한 코드는 가능한 범위에서 단순화해줘.
- 임시방편이나 hardcoding이 있다면 확인해줘.
- 관련 없는 대규모 변경은 하지 마.

현재 프로젝트 구조를 먼저 분석한 뒤

    </div>
  </div>


  <h3>6. 중요한 프로젝트 결정이 바뀌면 문서만 수정합니다</h3>

  <p>
    개발하면서 앞으로 계속 유지할 새로운 규칙이 생길 수 있습니다.
  </p>

  <div class="concept-example">
    “앞으로 모든 화면은 모바일을 기본 지원한다.”<br><br>

    “새로운 주요 library는 추가하지 않는다.”<br><br>

    “사용자 데이터는 앞으로 서버에 저장한다.”
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">Template 23 — 프로젝트 문서 갱신하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트에서
아래 새로운 결정을 내렸다.

[새로운 결정]
→ ______________________
→ ______________________

`AGENTS.md`와 `docs/`를 확인해서
이 내용을 기록하기에 가장 적절한 기존 문서 하나를 찾아줘.

그리고 그 문서에
이번 결정만 반영해줘.

같은 내용을 여러 문서에 반복해서 적지 마.

이번 작업에서는
프로젝트 문서만 수정해줘.

소스코드와 기능은 변경하지 마.</pre>

    <div class="prompt-purpose">
      앞으로도 유지할 중요한 결정을
      프로젝트 문서에만 반영할 때 사용하는 템플릿입니다.
    </div>
  </div>


  <h3>7. 정상적인 상태는 Git에 저장해둡니다</h3>

  <div class="concept">
    <div class="concept-title">
      💾 Git은 정상적으로 동작하던 상태를 다시 찾을 수 있게 해줍니다.
    </div>

    <p>
      기능을 만들고 실제로 확인했는데
      정상적으로 동작한다면
      그 상태를 Git에 기록해두는 것이 좋습니다.
    </p>

    <p>
      이후 다른 작업에서 문제가 생겨도
      이전 정상 상태와 비교하거나 되돌릴 수 있습니다.
    </p>
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">Template 24 — 현재 변경사항 Git에 저장하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트의 변경사항을
Git에 commit해줘.

[이번 작업 내용]
→ ______________________

현재 변경사항을 먼저 확인하고,
이번 작업 내용을 잘 나타내는
간단한 commit message를 만들어서 commit해줘.

이번 작업에서는
코드를 추가로 수정하지 마.</pre>

    <div class="prompt-purpose">
      기능이나 수정 작업이 정상적으로 끝난 뒤
      현재 상태를 하나의 Git 기록으로 남길 때 사용합니다.
    </div>
  </div>


  <h3>8. 배포는 마지막에 별도로 요청합니다</h3>

  <div class="warning">
    <span class="box-title">⚠️ 배포는 코드 작성과 별개의 작업으로 생각합니다</span>

    개발 중간에 Codex가 임의로 실제 서비스를 배포하게 하지 않고,
    사용자가 동작을 확인한 뒤 별도의 명령으로 진행하는 것이 좋습니다.
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">Template 25 — 현재 프로젝트 배포하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트를
기존에 설정되어 있는 배포 환경에 배포해줘.

새로운 hosting 서비스나
새로운 배포 방식을 도입하지 마.

현재 프로젝트에 이미 존재하는
배포 설정을 먼저 확인해서 그대로 사용해줘.

이번 작업에서는
기능이나 소스코드를 수정하지 말고
현재 상태를 배포하는 작업만 진행해줘.</pre>

    <div class="prompt-purpose">
      기능 개발과 분리해서
      이미 준비된 현재 버전만 실제 서비스 환경에 배포할 때 사용합니다.
    </div>
  </div>


  <div class="summary">
    <div class="summary-title">Chapter 07에서 배운 작업</div>

    <p>
      기능 개발 외에도 Codex에게 다음 작업을 각각 따로 맡길 수 있습니다.
    </p>

    <p>
      <strong>
        테스트하기<br>
        원인 조사하기<br>
        버그 수정하기<br>
        에러 분석하기<br>
        리팩터링하기<br>
        문서 갱신하기<br>
        Git에 저장하기<br>
        배포하기
      </strong>
    </p>
  </div>
</section>

  <h2>Codex에게 한 번에 하나의 일을 명확하게 맡깁니다</h2>

  </div>
