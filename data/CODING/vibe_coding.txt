    무엇을 만들고 싶은지 정리하고, 모르는 것은 ChatGPT와 상담하고,
    실제 프로젝트 작업은 Codex에게 맡기는 기본 개발 흐름을 익히는 것이 목표입니다.
  </p>

<section class="chapter">
  <div class="chapter-number">Chapter 01</div>
  <h2>먼저 알아야 할 최소한의 개발 개념</h2>

  <p>
    바이브 코딩을 시작하기 위해 개발자가 알고 있는 모든 내용을 배울 필요는 없습니다.
    다만 ChatGPT나 Codex가 사용하는 몇 가지 기본 용어를 알고 있으면
    AI와 훨씬 편하게 대화할 수 있습니다.
  </p>

  <div class="key-point">
    <strong>중요:</strong>
    아래 개념들을 완벽하게 외울 필요는 없습니다.
    “대충 무엇을 의미하는지”만 알고 있다가,
    실제 개발 중 이해되지 않는 내용이 나오면 ChatGPT에 다시 물어보면 됩니다.
  </div>

  <h3>1. 프로젝트 Project</h3>

  <div class="concept">
    <div class="concept-title">📁 프로젝트는 프로그램을 구성하는 전체 작업 공간입니다.</div>
    <div class="concept-subtitle">
      하나의 앱은 보통 하나의 파일이 아니라 여러 파일과 폴더로 이루어져 있습니다.
    </div>

    <p>
      예를 들어 일정 관리 앱을 만든다면 화면을 만드는 파일,
      데이터를 저장하는 파일, 여러 기능을 담당하는 파일,
      이미지와 설정 파일 등이 하나의 프로젝트 안에 들어갑니다.
    </p>

    <div class="concept-example">
      Codex에게 <strong>“현재 프로젝트를 먼저 확인해 주세요.”</strong>라고 하면
      Codex는 특정 코드 한 줄만 보는 것이 아니라 프로젝트 안의 파일들을 살펴보면서
      필요한 코드를 찾을 수 있습니다.
    </div>
  </div>

  <h3>2. Repository</h3>

  <div class="concept">
    <div class="concept-title">🗂 Repository는 프로젝트와 변경 기록을 관리하는 공간입니다.</div>

    <p>
      실습에서는 우선 <strong>“Codex가 작업할 프로젝트 폴더”</strong> 정도로 이해해도 충분합니다.
      Git을 사용하면 어떤 파일이 수정되었는지 확인하거나,
      이전 상태로 되돌리는 것도 가능해집니다.
    </p>

    <div class="concept-example">
      Codex가 “repository를 분석하겠습니다”라고 말한다면,
      어렵게 생각하지 않아도 됩니다.
      <strong>현재 프로젝트 전체를 먼저 살펴보겠다는 뜻</strong>입니다.
    </div>
  </div>

  <h3>3. Frontend</h3>

  <div class="concept">
    <div class="concept-title">🖥 Frontend는 사용자가 직접 보고 조작하는 부분입니다.</div>

    <p>
      버튼, 메뉴, 카드, 입력창, 화면 배치, 글자 크기처럼
      사용자의 화면에 나타나는 대부분의 요소가 프론트엔드에 해당합니다.
    </p>

    <div class="concept-example">
      예를 들어 이런 요청은 대부분 프론트엔드 작업입니다.<br><br>

      “상단 탭을 조금 왼쪽으로 이동시켜 주세요.”<br>
      “완료 버튼을 더 눈에 잘 띄게 해 주세요.”<br>
      “모바일에서는 카드가 한 줄에 하나씩 나오게 해 주세요.”
    </div>
  </div>

  <h3>4. Backend</h3>

  <div class="concept">
    <div class="concept-title">⚙️ Backend는 화면 뒤에서 필요한 일을 처리하는 부분입니다.</div>

    <p>
      사용자가 직접 보지는 않지만,
      로그인 확인, 데이터 저장, 여러 사용자 사이의 데이터 처리,
      권한 확인처럼 화면만으로 해결하기 어려운 일을 담당합니다.
    </p>

    <div class="concept-example">
      사용자가 로그인 버튼을 눌렀다고 생각해 봅시다.<br><br>

      프론트엔드는 이메일과 비밀번호를 입력받습니다.<br>
      백엔드는 실제로 그 사용자가 맞는지 확인합니다.<br>
      확인이 끝나면 결과를 다시 프론트엔드에 전달합니다.
    </div>
  </div>

  <h3>5. API</h3>

  <div class="concept">
    <div class="concept-title">🔌 API는 다른 기능을 가져오거나, 백엔드의 기능을 요청할 때 사용하는 연결 방법입니다.</div>

    <p>
      API를 처음 배울 때
      “프로그램끼리 데이터를 주고받는 통로”라고 설명하는 경우가 많지만,
      처음에는 그 말 자체가 어렵게 느껴질 수 있습니다.
    </p>

    <p>
      실제 개발에서는 다음처럼 생각하면 훨씬 쉽습니다.
    </p>

    <div class="concept-example">
      <strong>내 프론트엔드만으로 할 수 없는 일을 다른 곳에 부탁하는 방법</strong><br><br>

      • ChatGPT의 AI 기능을 내 앱에서 사용하고 싶다 → OpenAI API 사용<br>
      • 현재 날씨를 가져오고 싶다 → 날씨 서비스 API 사용<br>
      • 사용자의 로그인 정보를 확인하고 싶다 → 백엔드의 로그인 API 사용<br>
      • 서버에 저장된 일정을 가져오고 싶다 → 내가 만든 백엔드 API 사용
    </div>

    <p>
      즉 API에는 크게 두 가지 상황이 자주 등장합니다.
    </p>

    <ul>
      <li>
        <strong>외부 서비스의 기능을 가져오는 경우</strong><br>
        AI, 지도, 번역, 결제, 날씨 등 이미 다른 회사가 제공하는 기능을 사용합니다.
      </li>
      <li>
        <strong>내 백엔드에서 만든 기능을 프론트엔드가 사용하는 경우</strong><br>
        로그인, 데이터 저장, 사용자 정보 조회 같은 기능을 백엔드에 요청합니다.
      </li>
    </ul>
  </div>

  <div class="tip">
    <span class="box-title">💡 모르면 바로 ChatGPT에 물어보세요</span>
    Codex가 “이 기능을 구현하려면 API가 필요합니다”라고 이야기했는데
    API가 왜 필요한지 이해되지 않는다면 개발을 멈출 필요가 없습니다.
    그 내용을 그대로 ChatGPT에 붙여 넣고 설명을 요청하면 됩니다.
  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">개발 용어가 이해되지 않을 때</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">나는 바이브 코딩을 배우고 있는 개발 입문자야.

현재 Codex와 함께 웹 애플리케이션을 개발하고 있는데,
Codex가 아래와 같은 내용을 이야기했어.

[여기에 Codex의 설명을 붙여 넣기]

다음 기준으로 설명해줘.

1. 위 내용에서 내가 반드시 이해해야 하는 핵심 개념을 먼저 알려줘.
2. 어려운 개발 용어는 처음 개발하는 사람도 이해할 수 있게 설명해줘.
3. 각각의 개념이 지금 내가 만드는 기능에서 왜 필요한지도 설명해줘.
4. 여러 선택지가 있다면 각각의 장단점을 비교해줘.
5. 지금 당장 결정하지 않아도 되는 내용은 구분해줘.
6. 마지막에는 내가 Codex에게 어떤 결정을 전달하면 되는지 정리해줘.

코드 자체를 자세히 설명하기보다,
내가 개발 방향을 판단할 수 있도록 설명해줘.</pre>

    <div class="prompt-purpose">
      개발 용어를 전부 공부하려고 하지 않고,
      현재 작업에 필요한 만큼만 이해하기 위한 프롬프트입니다.
    </div>
  </div>

  <h3>6. Library / Dependency</h3>

  <div class="concept">
    <div class="concept-title">🧩 이미 다른 개발자가 만들어 놓은 기능을 가져다 사용할 수 있습니다.</div>

    <p>
      프로그램의 모든 기능을 처음부터 직접 만들 필요는 없습니다.
      이미 만들어진 기능을 프로젝트에 추가해서 사용할 수 있습니다.
    </p>

    <p>
      이런 외부 기능을 흔히 <strong>라이브러리</strong>라고 부르고,
      프로젝트가 그 라이브러리를 필요로 할 때
      <strong>dependency</strong>라고 표현하기도 합니다.
    </p>

    <div class="concept-example">
      달력 기능을 만들기 위해 날짜 계산을 전부 직접 구현하는 대신
      검증된 날짜 처리 라이브러리를 사용할 수 있습니다.<br><br>

      예쁜 아이콘 수백 개를 직접 그리는 대신
      아이콘 라이브러리를 설치할 수도 있습니다.
    </div>
  </div>

  <div class="warning">
    <span class="box-title">⚠️ 라이브러리를 무조건 추가하는 것은 좋은 개발이 아닙니다.</span>
    작은 기능 하나를 만들기 위해 큰 라이브러리를 계속 추가하면
    프로젝트가 복잡해질 수 있습니다.
    따라서 Codex가 새로운 핵심 라이브러리나 개발 방식을 도입하려 한다면
    이유를 확인한 뒤 결정하는 것이 좋습니다.
  </div>

  <h3>7. Framework</h3>

  <div class="concept">
    <div class="concept-title">🏗 Framework는 프로그램을 만드는 기본적인 틀입니다.</div>

    <p>
      웹앱을 만들 때 모든 것을 아무 규칙 없이 처음부터 작성하지 않고,
      일정한 구조와 개발 방법을 제공하는 도구를 사용하는 경우가 많습니다.
    </p>

    <p>
      예를 들어 React를 사용하는 프로젝트라면
      화면을 여러 개의 컴포넌트로 나누어 만드는 방식을 사용할 수 있습니다.
    </p>

    <div class="concept-example">
      중요한 것은 프레임워크 종류를 외우는 것이 아닙니다.<br><br>

      이미 React로 만들어진 프로젝트라면,
      특별한 이유 없이 Codex가 다른 프레임워크로 프로젝트 전체를 바꾸지 않도록
      기존 구조를 유지시키는 것이 더 중요합니다.
    </div>
  </div>

  <h3>8. 데이터 저장</h3>

  <div class="concept">
    <div class="concept-title">💾 앱에서 만든 정보를 어디에 보관할지 결정해야 합니다.</div>

    <p>
      일정 관리 앱에서 사용자가 일정을 만들었다면
      새로고침하거나 앱을 다시 실행해도 일정이 남아 있어야 할 수 있습니다.
    </p>

    <p>
      간단한 프로젝트에서는 브라우저 내부 저장소를 사용할 수도 있고,
      여러 기기와 사용자가 데이터를 공유해야 한다면
      서버와 데이터베이스가 필요할 수도 있습니다.
    </p>

    <div class="concept-example">
      <strong>작은 개인용 앱</strong><br>
      → 브라우저에 저장하는 방법으로 시작할 수도 있습니다.<br><br>

      <strong>로그인해서 여러 기기에서 사용하는 서비스</strong><br>
      → 서버와 데이터베이스가 필요한 경우가 많습니다.
    </div>
  </div>

  <h3>9. Test</h3>

  <div class="concept">
    <div class="concept-title">🧪 AI가 코드를 만들었다고 해서 개발이 끝난 것은 아닙니다.</div>

    <p>
      코드가 존재하는 것과 실제 기능이 정상적으로 동작하는 것은 다른 문제입니다.
      따라서 Codex에게 구현뿐 아니라 테스트까지 맡기는 습관이 중요합니다.
    </p>

    <p>
      입문 단계에서는 테스트의 세부 문법보다
      다음 차이만 이해하면 충분합니다.
    </p>

    <ul>
      <li>
        <strong>Unit Test</strong> —
        작은 기능 하나가 올바르게 동작하는지 확인합니다.
      </li>
      <li>
        <strong>Integration Test</strong> —
        여러 기능이 연결되었을 때 정상적으로 동작하는지 확인합니다.
      </li>
      <li>
        <strong>E2E Test</strong> —
        실제 사용자가 앱을 사용하는 것처럼 전체 흐름을 확인합니다.
      </li>
      <li>
        <strong>Regression Test</strong> —
        새로운 기능을 추가한 뒤 기존 기능이 망가지지 않았는지 확인합니다.
      </li>
    </ul>
  </div>

  <div class="key-point">
    <strong>바이브 코딩에서 중요한 습관:</strong>
    “코드 작성 완료”를 작업 완료라고 생각하지 말고,
    가능한 범위에서 <strong>구현 → 테스트 → 실패하면 수정 → 다시 테스트</strong>까지
    하나의 작업으로 생각합니다.
  </div>

  <h3>10. Build</h3>

  <div class="concept">
    <div class="concept-title">📦 Build는 작성한 프로젝트가 실제로 실행 가능한 상태인지 확인하고 준비하는 과정입니다.</div>

    <p>
      웹 프로젝트에서는 여러 소스 파일을 실제 서비스에서 사용할 수 있는 형태로
      정리하고 변환하는 과정이 필요할 수 있습니다.
    </p>

    <p>
      Build가 실패한다면 화면이 얼핏 정상처럼 보여도
      프로젝트 내부에 오류가 남아 있을 가능성이 있습니다.
    </p>

    <div class="concept-example">
      입문자가 build 명령어를 외울 필요는 없습니다.<br><br>

      Codex에게
      <strong>“필요한 검사와 테스트를 실행하고 문제가 있다면 알려주세요.”</strong>
      라고 요청하는 것부터 시작하면 됩니다.
    </div>
  </div>

  <h3>11. Git</h3>

  <div class="concept">
    <div class="concept-title">↩️ Git은 개발 과정의 변경 기록을 남기고 되돌릴 수 있게 해줍니다.</div>

    <p>
      AI가 한 번에 여러 파일을 수정할 수 있기 때문에
      바이브 코딩에서는 오히려 변경 기록을 관리하는 것이 중요해질 수 있습니다.
    </p>

    <p>
      첫 수업에서 Git 명령어를 모두 배울 필요는 없습니다.
      우선 <strong>“작업 전후의 상태를 기록해서 문제가 생기면 이전으로 돌아갈 수 있다”</strong>
      정도만 이해하면 충분합니다.
    </p>
  </div>

  <div class="summary">
    <div class="summary-title">이 장에서 기억할 것</div>
    <p>
      프로젝트, 프론트엔드, 백엔드, API, 라이브러리, 데이터 저장,
      테스트 같은 기본 용어를 모두 전문적으로 알 필요는 없습니다.
    </p>
    <p>
      중요한 것은 <strong>AI가 말하는 내용을 대략 이해하고,
      이해되지 않는 순간 ChatGPT에게 다시 질문할 수 있는 것</strong>입니다.
    </p>
  </div>

  <h2>ChatGPT와 Codex는 서로 다른 일을 맡깁니다</h2>

  <p>
    바이브 코딩에서 모든 일을 하나의 AI에게 맡길 필요는 없습니다.
    오히려 역할을 나누면 훨씬 편하게 개발할 수 있습니다.
  </p>

  <div class="role-grid">
    <div class="role-card">
      <h3>💬 ChatGPT Web</h3>
      <p>
        개발 과정에서 <strong>생각하고 이해하고 결정하는 일</strong>에 사용합니다.
      </p>
      <ul>
        <li>아이디어 정리</li>
        <li>필요한 기능 결정</li>
        <li>모르는 개발 개념 질문</li>
        <li>기술 선택지 비교</li>
        <li>프로젝트 진행 순서 상담</li>
        <li>Codex에게 전달할 프롬프트 작성</li>
      </ul>
    </div>

    <div class="role-card">
      <h3>🤖 Codex</h3>
      <p>
        결정된 내용을 바탕으로 <strong>실제 프로젝트에서 작업하는 일</strong>에 사용합니다.
      </p>
      <ul>
        <li>프로젝트 구조 조사</li>
        <li>관련 파일 찾기</li>
        <li>코드 작성 및 수정</li>
        <li>리팩터링</li>
        <li>테스트 작성 및 실행</li>
        <li>오류 조사 및 수정</li>
        <li>프로젝트 문서 갱신</li>
      </ul>
    </div>
  </div>

  <div class="key-point">
    <strong>가장 중요한 개발 습관:</strong><br>
    Codex에게 무엇을 시켜야 할지 모르겠다면
    억지로 개발 지식을 추측하지 말고 먼저 ChatGPT와 상담합니다.

  <h3>ChatGPT → Codex 기본 흐름</h3>

  <ol class="flow">
    <li>

    </li>

    <li>
      <span class="flow-title">모르는 기술을 질문합니다.</span>

    </li>

    <li>
      <span class="flow-title">Codex용 작업 프롬프트를 만듭니다.</span>
      결정된 요구사항을 실제 개발 에이전트가 이해하기 좋은 형태로 정리합니다.
    </li>

    <li>
      <span class="flow-title">Codex에게 실제 개발을 맡깁니다.</span>

    </li>

    <li>
      <span class="flow-title">결과를 확인하고 수정 요청을 합니다.</span>

    </li>

    <li>
      <span class="flow-title">테스트하고 중요한 결정은 프로젝트에 남깁니다.</span>

    </li>
  </ol>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">처음 아이디어를 개발 계획으로 바꾸기</span>
      <span class="prompt-target">ChatGPT</span>

[만들고 싶은 서비스]
나는 개인 일정과 할 일을 관리할 수 있는 애플리케이션을 만들고 싶어.

[현재 생각하고 있는 핵심 기능]
- 일정을 추가할 수 있다.
- 일정을 수정하고 삭제할 수 있다.
- 할 일을 완료 처리할 수 있다.
- 오늘 해야 할 일만 따로 볼 수 있다.
- 새로고침하거나 다시 접속해도 데이터가 유지되어야 한다.

[현재 상황]
- 아직 구체적인 기술 구조는 결정하지 않았다.
- 개발에 필요한 기술 용어는 잘 모를 수 있다.
- 실제 코딩은 Codex에게 맡길 예정이다.

다음 순서로 도와줘.

1. 내가 만들려는 서비스를 한 문단으로 명확하게 정의해줘.
2. 지금 적은 기능을 기준으로 최소 기능 제품(MVP)에 반드시 필요한 기능과 나중에 추가해도 되는 기능을 나눠줘.
3. 개발을 시작하기 전에 내가 결정해야 하는 사항을 질문 형태로 정리해줘.
4. 각 질문에서 기술적인 선택지가 있다면 입문자도 이해할 수 있도록 차이를 설명해줘.
5. 아직 결정할 필요가 없는 기술적인 세부사항은 제외해줘.
6. 기능을 어떤 순서로 구현하면 안전하고 이해하기 쉬운지 개발 순서를 제안해줘.
7. 마지막에는 지금까지 결정된 내용을 Codex에게 전달할 수 있는 개발 작업 명세의 초안을 만들어줘.

내가 코드를 직접 작성하는 방법보다,
무엇을 결정하고 어떤 순서로 Codex에게 일을 맡겨야 하는지를 중심으로 설명해줘.</pre>

    <div class="prompt-purpose">
      아이디어만 있는 상태에서 바로 코드를 만들기보다,

    </div>
  </div>

<section class="chapter">
  <div class="chapter-number">Chapter 03</div>
  <h2>아무것도 없는 상태에서 프로젝트를 시작하는 방법</h2>

  <p>
    지금부터는 이미 만들어진 프로젝트를 수정하는 것이 아니라,
    <strong>아이디어만 있는 상태에서 처음부터 애플리케이션을 만드는 과정</strong>을 시작합니다.
  </p>

  <p>
    개발을 처음 시작할 때 가장 흔한 실수는
    아이디어가 떠오르자마자 Codex에게 바로
    “이 앱을 만들어 주세요”라고 요청하는 것입니다.
  </p>

  <p>
    Codex는 그렇게 해도 상당한 부분을 알아서 만들 수 있습니다.
    하지만 우리가 결정하지 않은 부분이 많을수록
    Codex가 기술과 구조를 대신 선택해야 하는 영역도 많아집니다.
  </p>

  <div class="key-point">
    <strong>처음에는 코드를 만들지 않습니다.</strong><br>
    먼저 ChatGPT와 대화하면서
    <strong>무엇을 만들 것인지, 어떤 기능이 필요한지,
    어떤 중요한 선택을 해야 하는지</strong>를 정리합니다.
  </div>

  <h3>1. 처음 필요한 것은 기술 지식이 아니라 아이디어입니다</h3>

  <div class="concept">
    <div class="concept-title">💡 처음에는 이 정도만 알고 있어도 시작할 수 있습니다.</div>

    <div class="concept-example">
      “개인 일정 관리 앱을 만들고 싶다.”<br><br>

      “해야 할 일을 카드 형태로 정리하고 싶다.”<br><br>

      “친구들과 여행 계획을 함께 정리하는 웹앱을 만들고 싶다.”<br><br>

      “내가 공부한 내용을 저장하고 검색할 수 있는 앱을 만들고 싶다.”
    </div>

    <p>
      어떤 framework를 사용할지,
      데이터베이스를 무엇으로 할지,
      어떤 폴더 구조를 사용할지는 아직 몰라도 됩니다.
    </p>

    <p>
      그런 선택은 필요한 순간에 ChatGPT와 상담하면서 결정할 수 있습니다.
    </p>
  </div>

  <h3>2. 아이디어를 바로 코드로 만들지 않는 이유</h3>

  <div class="concept">
    <div class="concept-title">🧭 먼저 방향을 정하면 Codex가 훨씬 정확하게 일할 수 있습니다.</div>

    <p>
      예를 들어 다음 두 요청을 비교해 봅시다.
    </p>
  </div>

  <div class="compare-grid">
    <div class="compare-card bad">
      <span class="compare-label">❌ 너무 많은 판단을 AI에게 넘긴 요청</span>
      일정 관리 앱 만들어줘.
    </div>

    <div class="compare-card good">
      <span class="compare-label">✅ 먼저 요구사항을 정리한 요청</span>
      개인이 사용하는 일정 관리 웹앱을 만들고 싶다.
      첫 버전에서는 일정 추가, 수정, 삭제, 완료 처리가 필요하다.
      데이터는 우선 브라우저에 저장하고,
      로그인과 서버 기능은 나중에 추가하고 싶다.
    </div>
  </div>

  <p>
    두 번째 요청에서는 Codex가 무엇을 만들어야 하는지가 훨씬 명확합니다.
  </p>

  <p>
    중요한 것은 프롬프트를 길게 쓰는 것이 아니라
    <strong>사용자가 결정해야 할 중요한 내용과
    Codex가 판단해도 되는 내용을 구분하는 것</strong>입니다.
  </p>

  <h3>3. 처음 ChatGPT와 상담할 내용</h3>

  <p>
    앱을 처음 만든다면 최소한 다음 정도를 정리하면 좋습니다.
  </p>

  <div class="minimum-list">
    <div class="minimum-item">
      <strong>① 목적</strong>
      이 앱은 무엇을 하기 위한 앱인가?
    </div>

    <div class="minimum-item">
      <strong>② 사용자</strong>
      나 혼자 사용하는가, 여러 사람이 사용하는가?
    </div>

    <div class="minimum-item">
      <strong>③ 핵심 기능</strong>
      첫 버전에서 반드시 필요한 기능은 무엇인가?
    </div>

    <div class="minimum-item">
      <strong>④ 화면</strong>
      사용자는 어떤 화면에서 어떤 행동을 하는가?
    </div>

    <div class="minimum-item">
      <strong>⑤ 데이터</strong>
      새로고침해도 정보를 유지해야 하는가?
      여러 기기에서 같은 데이터를 사용해야 하는가?
    </div>

    <div class="minimum-item">
      <strong>⑥ 외부 기능</strong>
      AI, 지도, 번역, 로그인, 결제 같은 외부 기능이 필요한가?
    </div>

    <div class="minimum-item">
      <strong>⑦ 첫 버전의 범위</strong>
      지금 반드시 만들 기능과 나중에 만들 기능은 무엇인가?
    </div>
  </div>

  <div class="note">
    <span class="box-title">📌 이 질문에 대한 답을 미리 모두 알고 있을 필요는 없습니다</span>
    오히려 ChatGPT에게 하나씩 질문받으면서 결정하는 방법이 좋습니다.
    중요한 선택지가 나타나면 그때 설명을 듣고 결정하면 됩니다.
  </div>

  <h3>4. 아무것도 없는 상태에서 사용하는 첫 번째 프롬프트</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">아이디어를 개발 가능한 프로젝트로 구체화하기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">나는 개발 입문자이고,
Codex를 이용해서 처음부터 웹 애플리케이션을 만들려고 해.

현재는 아직 프로젝트 파일도 없고,
구체적인 기술 구성도 결정하지 않은 상태야.

[만들고 싶은 애플리케이션]
나는 개인 일정과 할 일을 관리할 수 있는 웹 애플리케이션을 만들고 싶어.

[현재 생각하고 있는 기능]
- 일정을 추가할 수 있다.
- 일정을 수정하고 삭제할 수 있다.
- 할 일을 완료 처리할 수 있다.
- 오늘 해야 할 일을 따로 볼 수 있다.
- 새로고침해도 저장한 데이터가 유지되었으면 좋겠다.

[현재 내가 모르는 것]
- 어떤 framework를 사용해야 하는지 모르겠다.
- 백엔드가 필요한지 모르겠다.
- 데이터를 어디에 저장해야 하는지 모르겠다.
- 프로젝트 구조를 어떻게 만들어야 하는지 모르겠다.

실제 코딩과 프로젝트 생성은 Codex에게 맡길 예정이다.

다음 방식으로 나와 함께 프로젝트를 구체화해줘.

1. 내가 만들려는 서비스를 한 문단으로 명확하게 정의해줘.

2. 현재 적은 기능을 기준으로
   첫 버전에서 반드시 필요한 기능과
   나중에 추가해도 되는 기능을 구분해줘.

3. 개발을 시작하기 전에
   내가 반드시 결정해야 하는 사항을 우선순위대로 질문해줘.

4. 질문은 한꺼번에 너무 많이 하지 말고,
   프로젝트의 방향을 크게 바꾸는 중요한 질문부터 진행해줘.

5. 기술적인 선택지가 나오면
   전문 용어만 설명하지 말고
   각 선택을 했을 때 실제 앱이 어떻게 달라지는지 중심으로 설명해줘.

6. 지금 규모에서는 필요하지 않은
   과도하게 복잡한 기술이나 구조는 추천하지 마.

7. 내가 잘 모르는 부분은 임의로 결론 내리지 말고,
   판단에 필요한 내용을 쉽게 설명한 뒤 내가 선택할 수 있게 해줘.

8. 충분한 결정이 끝나면
   지금까지 합의한 내용을 다음 항목으로 정리해줘.

   - 프로젝트 목적
   - 주요 사용자
   - 첫 버전의 핵심 기능
   - 화면과 주요 사용자 흐름
   - 사용할 기술 구성
   - 데이터 저장 방법
   - 필요한 외부 API 또는 서비스
   - 지금은 만들지 않을 기능
   - 개발 순서

9. 마지막에는 위 결정을 바탕으로
   Codex에게 새로운 프로젝트를 처음부터 생성하도록 요청할
   체계적인 개발 프롬프트를 만들어줘.

Codex용 프롬프트에는
무엇을 만들 것인지뿐 아니라
프로젝트 생성, 기본 구조, 중요한 제약사항,
검증 방법까지 포함해줘.</pre>

    <div class="prompt-purpose">
      프로젝트 파일이 하나도 없는 상태에서
      아이디어를 실제 개발 가능한 수준으로 구체화하는 첫 번째 상담 프롬프트입니다.
    </div>
  </div>

  <h3>5. ChatGPT가 질문하면 하나씩 결정합니다</h3>

  <div class="concept">
    <div class="concept-title">💬 모르는 선택지가 나오면 그 자리에서 배우면 됩니다.</div>

    <p>
      예를 들어 ChatGPT가 다음과 같은 질문을 할 수 있습니다.
    </p>

    <div class="concept-example">
      “이 앱을 본인만 사용할 예정인가요,
      아니면 여러 사용자가 각자의 계정으로 사용할 예정인가요?”
    </div>

    <p>
      이 질문에 따라 필요한 기술이 크게 달라질 수 있습니다.
    </p>

    <p>
      혼자 사용하는 작은 앱이라면
      백엔드 없이 브라우저 내부에 데이터를 저장하는 방법으로
      간단하게 시작할 수도 있습니다.
    </p>

    <p>
      반대로 여러 사람이 로그인하고
      여러 기기에서 같은 데이터를 사용해야 한다면
      백엔드와 데이터베이스가 필요할 가능성이 높습니다.
    </p>
  </div>

  <div class="key-point">
    <strong>중요한 것은 정답을 미리 아는 것이 아닙니다.</strong><br>
    질문을 받고 → 차이를 이해하고 → 현재 프로젝트에 맞는 것을 선택하면 됩니다.
  </div>

  <h3>6. 이해되지 않는 선택지가 나오면 더 자세히 물어봅니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">기술 선택을 이해한 뒤 결정하기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">방금 네가 다음 두 가지 방법 중 하나를 선택해야 한다고 설명했어.

[이해되지 않는 선택지 또는 설명을 붙여 넣기]

나는 개발 입문자라서
각 방법이 실제로 내 앱에 어떤 차이를 만드는지 아직 잘 모르겠어.

다음 기준으로 설명해줘.

1. 각각의 방법을 처음 개발하는 사람도 이해할 수 있게 설명해줘.
2. 기술 내부 구조보다 실제 사용 결과가 어떻게 달라지는지를 중심으로 설명해줘.
3. 구현 난이도와 관리해야 할 것이 얼마나 늘어나는지도 비교해줘.
4. 지금 만드는 작은 첫 버전에는 어느 방법이 더 단순한지 알려줘.
5. 나중에 사용자가 늘어났을 때 어떤 차이가 생기는지도 알려줘.
6. 지금 선택했다가 나중에 변경하기 어려운 결정인지 알려줘.
7. 내 상황에서 추천하는 방법이 있다면 이유와 단점도 같이 알려줘.

설명을 들은 뒤 내가 직접 결정할 수 있도록 도와줘.</pre>

    <div class="prompt-purpose">
      개발 용어를 외우기보다
      현재 프로젝트에서 실제로 어떤 차이가 생기는지를 이해하기 위한 프롬프트입니다.
    </div>
  </div>

  <h3>7. 첫 번째 개발 범위는 작게 잡습니다</h3>

  <div class="concept">
    <div class="concept-title">🌱 처음부터 완성된 서비스를 만들 필요는 없습니다.</div>

    <p>
      첫 번째 버전에서는
      가장 중요한 기능이 실제로 동작하도록 만드는 것이 우선입니다.
    </p>

    <div class="concept-example">
      일정 관리 앱의 첫 버전이라면:<br><br>

      ✅ 일정 추가<br>
      ✅ 일정 수정<br>
      ✅ 일정 삭제<br>
      ✅ 완료 처리<br>
      ✅ 데이터 저장<br><br>

      다음 기능은 나중으로 미룰 수 있습니다.<br><br>

      ⏳ 회원가입<br>
      ⏳ 여러 기기 동기화<br>
      ⏳ 친구와 공유<br>
      ⏳ AI 일정 추천<br>
      ⏳ 알림 기능
    </div>
  </div>

  <div class="tip">
    <span class="box-title">💡 작은 첫 버전이 중요한 이유</span>
    기능이 적으면 문제가 발생했을 때 원인을 찾기 쉽고,
    실제 결과를 확인하면서 다음 기능을 하나씩 추가하기도 쉽습니다.
  </div>

  <h3>8. 상담이 끝났다면 개발 명세를 한 번 정리합니다</h3>

  <p>
    충분히 대화해서 중요한 결정을 마쳤다면
    ChatGPT에게 지금까지 정한 내용을 한 번 정리하도록 요청할 수 있습니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">결정된 내용을 개발 명세로 정리하기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">지금까지 우리가 결정한 내용을 기준으로
첫 번째 버전 개발 명세를 정리해줘.

다음 항목으로 구분해줘.

1. 프로젝트 목적
2. 주요 사용자
3. 핵심 사용자 흐름
4. 첫 버전에서 구현할 기능
5. 이번 버전에서는 구현하지 않을 기능
6. 사용할 frontend 기술
7. backend 필요 여부
8. 데이터 저장 방식
9. 사용할 외부 API 또는 서비스
10. UI에서 지켜야 할 기본 방향
11. 개발 순서
12. 테스트해야 할 주요 사용자 동작

이미 결정하지 않은 내용을
마치 결정된 것처럼 임의로 추가하지 마.

아직 중요한 결정이 남아 있다면
개발 명세를 확정하기 전에 먼저 알려줘.

정리가 끝나면
이 명세를 Codex에게 전달해서
완전히 새로운 프로젝트를 생성할 수 있는
구조적인 작업 프롬프트도 함께 만들어줘.</pre>

    <div class="prompt-purpose">
      여러 번의 상담에서 결정된 내용을
      Codex에게 넘기기 전에 하나의 명확한 개발 명세로 정리합니다.
    </div>
  </div>

  <div class="summary">
    <div class="summary-title">프로젝트 파일을 만들기 전에 여기까지 결정합니다</div>

    <p>
      첫 개발에서는 모든 기술을 이해할 필요가 없습니다.
    </p>

    <p>
      다만 최소한
      <strong>무엇을 만들지, 누가 사용할지, 첫 기능은 무엇인지,
      데이터를 어떻게 유지할지</strong> 정도는 결정하고 시작하는 것이 좋습니다.
    </p>

    <p>
      그 과정에서 모르는 것이 나오면
      ChatGPT에게 계속 질문하면서 필요한 만큼만 배우면 됩니다.
    </p>

    <p>
      다음 단계에서는
      <strong>지금까지 결정한 내용을 실제 Codex에게 전달해서
      아무것도 없는 상태에서 프로젝트를 생성</strong>합니다.
    </p>
  </div>

<section class="chapter">
  <div class="chapter-number">Chapter 04</div>
  <h2>이제 Codex에게 처음부터 프로젝트를 만들어 달라고 합니다</h2>

  <p>
    ChatGPT와 상담해서 프로젝트의 목적, 핵심 기능, 기술 구성, 데이터 저장 방식까지 정했다면
    이제 그 결정을 실제 Codex에게 전달할 차례입니다.
  </p>

  <p>
    여기서 중요한 것은
    <strong>“앱 하나 만들어줘”라고 끝내는 것이 아니라,

개인이 자신의 일정과 할 일을 관리할 수 있는 웹 애플리케이션을 만들고 싶다.

[첫 번째 버전의 핵심 기능]
- 일정을 추가할 수 있다.
- 일정을 수정할 수 있다.
- 일정을 삭제할 수 있다.
- 할 일을 완료 처리할 수 있다.
- 오늘 해야 할 일만 따로 볼 수 있다.
- 새로고침해도 데이터가 유지되어야 한다.

[기술 구성]
- Frontend: React
- Language: TypeScript
- Build Tool: Vite
- Backend: 첫 번째 버전에서는 사용하지 않는다.

[개발 방향]

- 아직 필요하지 않은 backend, authentication, database는 추가하지 않는다.
- 새로운 state management library는 추가하지 않는다.
- React의 기본 기능으로 충분하다면 외부 library를 추가하지 않는다.
- 기능별 책임은 적절히 나누되 처음부터 과도하게 복잡한 architecture를 만들지 않는다.

[UI 방향]
- 깔끔하고 단순한 일정 관리 화면으로 만든다.
- desktop과 mobile에서 모두 사용할 수 있게 한다.
- 처음부터 지나치게 화려한 animation이나 디자인 framework는 사용하지 않는다.
- 일정 추가, 목록 확인, 완료 처리가 쉽게 보이도록 한다.

[작업 순서]
1. 새로운 React + TypeScript + Vite 프로젝트를 생성해줘.
2. 기본 프로젝트가 정상적으로 실행 가능한지 확인해줘.
3. 첫 번째 버전에 필요한 최소한의 폴더와 파일 구조를 만들어줘.
4. 일정 관리의 기본 데이터 구조를 정의해줘.
5. 일정 추가, 수정, 삭제, 완료 기능을 구현해줘.
6. localStorage에 데이터를 저장하고 다시 불러오는 기능을 구현해줘.
7. 오늘 해야 할 일만 볼 수 있는 기능을 추가해줘.
8. 기본적인 responsive UI를 적용해줘.
9. 현재 프로젝트에 적절한 수준의 테스트를 구성하고 핵심 기능을 검증해줘.

[중요]
- 구현 과정에서 기술적으로 중요한 선택이 새롭게 필요하다면,
  불필요하게 복잡한 방법을 자동으로 선택하지 말고 현재 규모에 맞는 가장 단순한 방법을 우선해줘.
- 기존에 결정하지 않은 큰 기술 선택이 필요하면 먼저 알려줘.
- 불필요한 dependency를 추가하지 마.
- 임시방편이나 TODO로 핵심 기능 구현을 대신하지 마.

[완료 후]
다음 내용을 간단하게 알려줘.

- 생성한 프로젝트 구조
- 구현한 기능
- 사용한 주요 기술과 library
- 실행한 테스트와 결과
- 내가 직접 브라우저에서 확인해야 할 주요 동작
- 다음 기능을 개발하기 전에 결정해야 할 사항</pre>

    <div class="prompt-purpose">
      ChatGPT와 상담해서 결정한 프로젝트 명세를
      실제 Codex에게 전달해서 첫 번째 프로젝트를 만드는 기본 프롬프트입니다.

  <h3>9. `AGENTS.md`에는 어떤 내용이 들어가면 좋을까요?</h3>

  <div class="concept">
    <div class="concept-title">📌 AGENTS.md는 프로젝트의 모든 설명서가 아닙니다.</div>

## Before making changes

- Read the relevant documentation under `docs/`.

## Development

  <h2>첫 번째 버전이 만들어졌다면 기능을 하나씩 확장합니다</h2>

  <p>
    이제 프로젝트가 존재하고,
    기본 기능도 실제로 동작하는 상태입니다.
  </p>

  <p>
    이 시점부터는 처음부터 프로젝트 전체를 다시 만드는 것이 아니라,
    <strong>현재 프로젝트의 구조와 기능을 유지하면서 필요한 기능을 하나씩 추가</strong>하면 됩니다.
  </p>

  <div class="key-point">
    <strong>새 기능을 추가할 때의 기본 원칙:</strong><br>
    기존 프로젝트를 먼저 확인하고,
    현재 구조를 최대한 활용하면서
    필요한 부분만 점진적으로 수정합니다.
  </div>

  <h3>1. 먼저 “무엇을 추가할지” 정합니다</h3>

  <div class="concept">
    <div class="concept-title">➕ 새로운 기능도 바로 코딩부터 시작할 필요는 없습니다.</div>

    <p>
      기능이 단순하고 명확하다면 바로 Codex에게 요청해도 됩니다.
      하지만 기능의 범위가 애매하거나 여러 방법이 있을 것 같다면
      먼저 ChatGPT와 상담해서 요구사항을 정리하는 것이 좋습니다.
    </p>

    <div class="concept-example">
      예를 들어 다음 기능을 추가하고 싶다고 생각해 봅시다.<br><br>

      “일정마다 중요도를 설정하고 싶다.”<br><br>

      여기서 바로 개발을 시작할 수도 있지만,
      조금만 생각하면 여러 선택지가 생깁니다.<br><br>

      • 중요도는 몇 단계로 할 것인가?<br>
      • 목록에서는 어떻게 표시할 것인가?<br>
      • 중요도 순으로 정렬할 것인가?<br>
      • 기존 일정에는 어떤 기본값을 사용할 것인가?<br>
      • 필터 기능도 함께 필요한가?
    </div>
  </div>

  <h3>2. 새로운 기능을 ChatGPT와 먼저 구체화하기</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">새 기능을 개발하기 전에 요구사항 정리하기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">현재 Codex와 함께 만든 일정 관리 웹앱이 있다.

현재 앱에는 다음 기능이 있다.

- 일정 추가
- 일정 수정
- 일정 삭제
- 완료 처리
- 오늘 일정 보기
- localStorage 저장

새롭게 다음 기능을 추가하고 싶다.

[추가하고 싶은 기능]
각 일정에 중요도를 설정하고 싶다.

나는 아직 이 기능을 구체적으로 어떻게 구성할지는 결정하지 않았다.

다음 방식으로 기능을 구체화해줘.

1. 이 기능을 사용자가 실제로 어떻게 사용하게 될지 사용자 흐름을 정리해줘.

2. 개발 전에 내가 결정해야 할 중요한 사항을 질문해줘.
   예:
   - 중요도 단계
   - 화면 표시 방식
   - 정렬 또는 필터 필요 여부
   - 기존 데이터 처리 방식

3. 기능을 지나치게 크게 확장하지 말고
   현재 일정 관리 앱 규모에 적절한 첫 번째 버전을 제안해줘.

4. 기존 기능이나 데이터 구조에 어떤 영향을 줄 수 있는지도 알려줘.

5. 기존 데이터를 안전하게 유지하기 위해 고려해야 할 사항이 있으면 설명해줘.

6. 내가 이해하기 어려운 기술적인 선택이 필요하면
   실제 앱에서 어떤 차이가 생기는지 중심으로 설명해줘.

7. 충분히 결정한 뒤에는
   현재 프로젝트에 기능을 추가하기 위한
   체계적인 Codex용 개발 프롬프트를 만들어줘.

Codex용 프롬프트에는
- 새 기능의 목표
- 사용자 동작
- 기존 프로젝트에서 유지해야 할 부분
- 데이터에 미치는 영향
- 테스트해야 할 동작
- 완료 기준

을 포함해줘.</pre>

    <div class="prompt-purpose">
      이미 동작하는 앱에 새로운 기능을 추가하기 전에
      기능의 범위와 사용자 경험을 먼저 결정하는 프롬프트입니다.
    </div>
  </div>

  <h3>3. 요구사항이 명확하다면 바로 Codex에게 맡길 수 있습니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">기존 프로젝트에 새 기능 추가하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트에 일정 중요도 기능을 추가해줘.

[새 기능의 목표]
사용자가 각 일정의 중요도를 설정하고
일정 목록에서도 쉽게 확인할 수 있게 하고 싶다.

[요구사항]
- 중요도는 `높음`, `보통`, `낮음` 세 단계로 한다.
- 새로운 일정을 만들 때 중요도를 선택할 수 있어야 한다.
- 기존 일정을 수정할 때도 중요도를 변경할 수 있어야 한다.
- 일정 목록에서도 현재 중요도를 확인할 수 있어야 한다.
- 기존 일정에는 기본값으로 `보통`을 사용한다.
- 현재는 중요도 정렬이나 필터 기능까지 추가하지 않는다.

[현재 프로젝트에서 유지할 것]
- 작업 전에 `AGENTS.md`와 관련 `docs/`를 확인해줘.
- 현재 React + TypeScript + Vite 구성을 유지해줘.
- 현재 localStorage 저장 방식을 유지해줘.
- 기존 일정 추가, 수정, 삭제, 완료 기능을 유지해줘.
- 현재 UI 스타일과 화면 구조를 불필요하게 다시 만들지 마.
- 새로운 주요 dependency는 필요하지 않다면 추가하지 마.

[데이터 관련]
- 기존에 저장된 일정 데이터가 깨지지 않아야 한다.
- 기존 데이터에 중요도 값이 없다면 안전하게 기본값을 적용해줘.
- 저장 데이터 형식의 변경이 필요하다면 기존 데이터와 호환되도록 처리해줘.

[작업 방식]
1. 현재 일정 데이터 구조와 관련 코드를 먼저 확인해줘.
2. 기존 구조를 최대한 활용해서 기능을 추가해줘.
3. 같은 데이터를 별도의 중복 구조로 관리하지 마.
4. 관련 없는 코드까지 대규모로 수정하지 마.
5. 중요한 architecture 변경이 필요하다면 임의로 진행하지 말고 알려줘.

[검증]
다음 동작을 확인해줘.

- 새 일정 생성 시 중요도 저장
- 기존 일정 수정 시 중요도 변경
- 일정 목록에서 중요도 표시
- 기존 일정 데이터 정상 로드
- 새로고침 후 중요도 유지
- 기존 추가/수정/삭제/완료 기능 정상 동작

현재 테스트 방식에 맞게 필요한 테스트를 추가하고
관련 기존 테스트도 실행해줘.

[완료 후]
- 구현한 내용
- 변경한 주요 영역
- 데이터 호환 처리 방법
- 테스트 결과
- 내가 브라우저에서 직접 확인할 부분

을 간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      이미 만들어진 프로젝트에
      기존 기능을 유지하면서 하나의 기능을 안전하게 추가하는 기본형 프롬프트입니다.
    </div>
  </div>

  <h3>4. 작은 기능은 이렇게 간단하게 요청해도 됩니다</h3>

  <p>
    모든 기능에 긴 프롬프트가 필요한 것은 아닙니다.
    영향 범위가 작고 원하는 결과가 명확하다면 훨씬 간단하게 요청할 수 있습니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">작은 기능 추가</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 일정 카드에
일정을 복사할 수 있는 기능을 하나 추가해줘.

요구사항은 다음과 같다.

- 기존 일정 카드에 `복사` 기능을 추가한다.
- 복사하면 같은 내용의 새로운 일정이 생성된다.
- 복사된 일정은 기존 일정과 별개의 데이터여야 한다.
- 기존 UI 스타일을 유지한다.
- 현재 저장 방식과 데이터 구조를 불필요하게 변경하지 않는다.
- 관련 테스트를 확인한다.

작업 전에 현재 일정 카드와 일정 생성 로직을 먼저 확인하고,
가능하면 기존 생성 로직을 재사용해줘.</pre>

    <div class="prompt-purpose">
      기능의 목표와 영향 범위가 명확한 경우에는
      핵심 요구사항만 구조적으로 전달해도 충분합니다.
    </div>
  </div>

  <h3>5. 화면만 조금 수정하고 싶다면 자연어로 설명합니다</h3>

  <div class="concept">
    <div class="concept-title">🎨 CSS나 화면 구조를 몰라도 수정할 수 있습니다.</div>

    <p>
      실제 앱을 사용하다 보면
      기능은 정상인데 화면이 마음에 들지 않는 경우가 많습니다.
    </p>

    <p>
      이때 “margin-left를 12px 줄여주세요”처럼
      CSS를 직접 지정할 필요는 없습니다.
    </p>

    <p>
      사용자의 눈에 어떻게 보이는지만 설명해도 됩니다.
    </p>
  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">UI 일부만 수정하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 화면의 전체 디자인과 기능은 유지하고 싶다.

다만 상단 탭이 지금보다 조금 왼쪽에 위치했으면 좋겠다.

다음 조건으로 수정해줘.

[원하는 변경]
- 현재 상단 탭 영역을 조금 왼쪽으로 이동한다.
- 탭 사이의 간격과 크기는 유지한다.
- 다른 화면 요소의 위치는 가능하면 변경하지 않는다.

[유지해야 할 것]
- 탭의 기능
- 현재 반응형 동작
- 현재 디자인 스타일
- 기존 UI framework와 styling 방식

관련 UI 코드를 확인하고
필요한 부분만 최소한으로 수정해줘.

수정 후
내가 브라우저에서 확인해야 할 화면 변화만 알려줘.</pre>

    <div class="prompt-purpose">
      화면에서 보이는 문제를 그대로 설명하고
      내부 구현 방법은 Codex가 판단하게 하는 프롬프트입니다.
    </div>
  </div>

  <h3>6. 디자인 방향이 애매하다면 ChatGPT와 먼저 상담합니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">막연한 디자인 요구를 구체화하기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">현재 일정 관리 앱의 기능은 마음에 들지만
디자인이 조금 답답하게 느껴진다.

정확히 어떤 CSS를 바꾸고 싶은지는 모르겠다.

현재 느끼는 문제는 다음과 같다.

- 한 화면에 보이는 일정 수가 적다.
- 카드가 조금 크게 느껴진다.
- 중요한 정보와 덜 중요한 정보의 차이가 잘 보이지 않는다.
- 그렇다고 복잡하거나 화려한 디자인은 원하지 않는다.

내가 원하는 사용자 경험을 먼저 정리해줘.

다음 기준으로 도와줘.

1. 현재 내가 느끼는 불편함을 UI 요구사항으로 바꿔줘.
2. 큰 redesign 없이 개선할 수 있는 방법을 몇 가지 제안해줘.
3. 각 방법이 화면에 어떤 변화를 만드는지 쉽게 설명해줘.
4. 내가 결정해야 할 디자인 선택이 있다면 질문해줘.
5. 결정이 끝나면
   현재 기능과 데이터 구조는 유지하고
   UI만 필요한 만큼 수정하도록 하는
   Codex용 프롬프트를 만들어줘.</pre>

    <div class="prompt-purpose">
      “조금 답답하다”, “좀 더 깔끔했으면 좋겠다” 같은
      애매한 느낌을 실제 UI 작업 요청으로 바꾸는 데 사용합니다.
    </div>
  </div>

  <h3>7. 기능을 추가할수록 기존 기능을 지키는 것이 중요해집니다</h3>

  <div class="concept">
    <div class="concept-title">🛡 새로운 기능 하나가 기존 기능을 망가뜨릴 수도 있습니다.</div>

    <p>
      첫 번째 기능만 있을 때는 확인해야 할 것이 적습니다.
      하지만 기능이 늘어날수록 서로 영향을 주기 시작합니다.
    </p>

    <div class="concept-example">
      중요도 기능을 추가했는데 일정 수정이 안 된다.<br><br>

      필터 기능을 추가했는데 일정 삭제가 안 된다.<br><br>

      새로운 데이터 필드를 추가했는데 예전에 저장한 일정이 사라진다.
    </div>

    <p>
      이런 문제를 <strong>regression</strong>이라고 부를 수 있습니다.
    </p>
  </div>

  <div class="key-point">
    <strong>새 기능이 동작하는지만 확인하지 않습니다.</strong><br>
    이전에 잘 되던 기능이 계속 잘 되는지도 함께 확인합니다.
  </div>

  <h3>8. 기능 추가 후 기존 기능까지 검증시키기</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">기능 추가 후 regression 확인</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">이번 기능 구현이 완료되었다면
새로운 기능뿐 아니라 기존 주요 기능도 함께 검증해줘.

[새롭게 추가한 기능]
일정 중요도 기능

[반드시 계속 동작해야 하는 기존 기능]
- 일정 추가
- 일정 수정
- 일정 삭제
- 완료 처리
- 오늘 일정 보기
- localStorage 저장 및 로드

다음 방식으로 확인해줘.

1. 새 기능과 직접 관련된 테스트를 실행해줘.

2. 기존 핵심 기능의 regression 여부도 확인해줘.

3. 현재 자동 테스트에서 확인되지 않는 중요한 사용자 흐름이 있다면 알려줘.

4. 테스트가 부족하다면
   현재 프로젝트의 기존 테스트 방식에 맞춰 필요한 범위만 추가해줘.

5. 테스트를 통과시키기 위해
   기존 실패를 숨기거나 테스트를 약화시키지 마.

6. 문제가 발견되면 원인을 조사하고 수정한 뒤 다시 실행해줘.

완료 후에는
성공한 검사,
수정한 문제,
자동으로 확인하지 못한 부분만 간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      기능이 늘어난 프로젝트에서
      새 기능 때문에 이전 기능이 망가지지 않았는지 확인합니다.
    </div>
  </div>

  <h3>9. 새로운 개발 원칙이 생기면 문서에 반영합니다</h3>

  <p>

  <p>

  <div class="concept">

[결정]
- 모든 일정은 중요도 값을 가질 수 있다.
- 중요도 값이 없는 기존 일정은 `보통`으로 처리한다.
- 기존 localStorage 데이터와의 호환성을 유지한다.

이 내용이 앞으로 다른 기능을 개발할 때도 알아야 하는
장기적인 프로젝트 결정인지 확인해줘.

장기적인 결정에 해당한다면
현재 `AGENTS.md`와 `docs/` 구조를 먼저 확인하고
가장 적절한 문서에 반영해줘.

다음 원칙을 지켜줘.

- 같은 내용을 여러 문서에 반복하지 마.
- 구현 세부사항까지 과도하게 문서화하지 마.
- `AGENTS.md`는 계속 간결하게 유지해줘.
- 기존 문서와 충돌하는 내용이 있다면 임의로 덮어쓰지 말고 먼저 알려줘.

문서 변경 때문에 애플리케이션 코드나 UI를 추가로 변경하지 마.</pre>

    <div class="prompt-purpose">

  <h3>10. 큰 기능은 한 번에 만들지 않고 단계로 나눕니다</h3>

  <div class="concept">
    <div class="concept-title">🧱 기능이 복잡할수록 작은 단계로 나누는 것이 안전합니다.</div>

    <p>
      예를 들어 앞으로 사용자가 로그인해서
      여러 기기에서 일정을 공유하도록 만들고 싶다고 생각해 봅시다.
    </p>

    <p>
      이것을 한 번에
      “로그인하고 클라우드 저장까지 만들어줘”라고 요청할 수도 있지만,
      여러 중요한 변경이 동시에 발생합니다.
    </p>

    <div class="concept-example">
      인증 방식 결정<br>
      ↓<br>
      사용자 계정 생성<br>
      ↓<br>
      backend 구성<br>
      ↓<br>
      database 구성<br>
      ↓<br>
      기존 localStorage 데이터 처리<br>
      ↓<br>
      사용자별 데이터 저장<br>
      ↓<br>
      여러 기기 동기화<br>
      ↓<br>
      보안 및 권한 확인
    </div>
  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">큰 기능을 안전한 개발 단계로 나누기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">현재 일정 관리 앱은
React + TypeScript + Vite로 만들어져 있고,
데이터는 localStorage에 저장하고 있다.

이제 다음 기능을 추가하고 싶다.

[새로운 목표]
사용자가 회원가입하고 로그인해서
여러 기기에서 자신의 일정을 사용할 수 있게 하고 싶다.

이 기능은 기존 프로젝트 구조를 크게 바꿀 수 있을 것 같아서
한 번에 Codex에게 구현시키지 않고
검증 가능한 여러 단계로 나누어 진행하고 싶다.

다음 기준으로 개발 계획을 만들어줘.

1. 전체 작업을 안전한 작은 단계로 나눠줘.

2. 각 단계에서 무엇을 만들고
   어떤 상태가 되면 완료인지 알려줘.

3. 각 단계마다 내가 결정해야 할 중요한 기술 선택을 알려줘.

4. 기존 localStorage 데이터에 미칠 영향을 따로 설명해줘.

5. backend, database, authentication이 각각 왜 필요한지
   개발 입문자가 이해할 수 있게 설명해줘.

6. 보안이나 데이터 손실처럼
   특히 위험한 단계는 따로 표시해줘.

7. 현재 규모에서 불필요하게 복잡한 구조는 피하도록 해줘.

8. 이전 단계의 검증이 끝난 후
   다음 단계로 넘어갈 수 있는 순서로 구성해줘.

9. 각 단계가 확정되면
   Codex에게 전달할 작업 프롬프트를 만들 수 있도록
   필요한 요구사항을 정리해줘.

코드를 직접 작성하지 말고,
전체 기능을 어떻게 안전하게 나누어 개발할 것인지 중심으로 설명해줘.</pre>

    <div class="prompt-purpose">
      로그인, backend, database처럼
      여러 시스템에 영향을 주는 큰 기능을 단계적으로 개발할 때 사용합니다.
    </div>
  </div>

    <div class="summary-title">첫 버전 이후의 개발 흐름</div>

    <p>
      <strong>

      기능을 하나씩 쌓아가는 것이 기본입니다.
    </p>

  <h2>문제가 생기면 직접 코드를 찾기보다, AI에게 원인을 조사시킵니다</h2>

  <p>
    기능을 계속 추가하다 보면
    버튼이 갑자기 동작하지 않거나,
    이전에 잘 되던 기능이 깨지거나,

  <h3>1. “안 돼요. 고쳐주세요.”보다 좋은 요청</h3>

  <div class="compare-grid">

    <div class="compare-card good">
      <span class="compare-label">✅ 조사할 수 있는 요청</span>

      관련 코드를 먼저 조사해서 원인을 확인한 뒤

    </div>
  </div>

  <p>
    좋은 버그 수정 프롬프트에는

  <h3>2. 원인부터 조사하는 버그 수정 프롬프트</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">버그 원인 조사 후 수정하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트에서 다음 문제가 발생하고 있다.

[문제 상황]
새로운 일정을 추가한 뒤 저장 버튼을 눌러도
일정 목록에 새 일정이 나타나지 않는다.

[정상적으로 기대하는 동작]
- 제목과 날짜를 입력할 수 있다.
- 저장 버튼을 누르면 새로운 일정이 생성된다.
- 생성된 일정이 목록에 즉시 나타난다.
- 새로고침한 이후에도 저장된 일정이 유지된다.

[현재 확인한 내용]
- 입력창은 정상적으로 사용할 수 있다.
- 저장 버튼도 클릭할 수 있다.
- 오류 메시지는 화면에 표시되지 않는다.
- 하지만 저장 후 일정 목록에는 변화가 없다.

[최근 변경]
이 문제가 발생하기 전에
일정 중요도 기능을 추가했다.

다음 방식으로 진행해줘.

1. 작업 전에 `AGENTS.md`와 관련 프로젝트 문서를 확인해줘.

2. 추측해서 바로 수정하지 말고
   일정 입력 → 저장 이벤트 → 상태 변경 → localStorage 저장 → 화면 업데이트
   흐름을 따라가면서 관련 코드를 먼저 조사해줘.

3. 최근 중요도 기능 추가가
   이번 문제와 관련 있는지도 확인해줘.

4. 근본 원인을 확인한 뒤
   필요한 부분만 최소한으로 수정해줘.

5. 기존 일정 수정, 삭제, 완료 처리,
   localStorage 저장 기능은 유지해줘.

6. 문제를 숨기기 위해
   오류를 무시하거나,
   하드코딩하거나,
   테스트를 삭제하거나 약하게 만들지 마.

7. 가능하다면
   이번 문제가 다시 발생하는 것을 방지할 수 있는 테스트를 추가해줘.

8. 수정 후 관련 테스트와
   기존 핵심 기능의 regression 여부를 확인해줘.

[완료 후]
다음 내용만 간단하게 알려줘.

- 실제 원인
- 수정한 내용
- 실행한 테스트와 결과
- 내가 브라우저에서 직접 다시 확인해야 할 동작</pre>

      Codex가 데이터와 이벤트 흐름을 따라가며 원인을 조사하게 만드는 프롬프트입니다.
    </div>

  <h3>3. 최근 수정 이후 기존 기능이 망가졌다면 Regression을 의심합니다</h3>

  <div class="concept">
    <div class="concept-title">🔁 Regression은 새 변경 때문에 예전에 잘 되던 기능이 망가지는 현상입니다.</div>

    <div class="concept-example">
      완료 필터를 추가했더니 삭제가 안 된다.<br><br>

      중요도 기능을 넣었더니 예전에 저장한 일정이 열리지 않는다.<br><br>

      UI를 수정했더니 모바일에서 버튼이 화면 밖으로 나간다.
    </div>
  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">최근 변경으로 생긴 Regression 조사하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">최근 기능 추가 이후
기존 기능에 문제가 생겼다.

[최근 변경]
완료된 일정만 볼 수 있는 필터 기능을 추가했다.

[현재 정상인 부분]
- 일정 목록이 표시된다.
- 완료 필터는 정상적으로 동작한다.

[새롭게 발생한 문제]
기존에 정상적으로 동작하던 일정 삭제 기능이
이제 작동하지 않는다.

[원하는 최종 상태]
- 필터 기능은 그대로 유지한다.
- 일정 삭제 기능도 이전과 동일하게 정상적으로 동작해야 한다.
- 다른 일정 관리 기능에도 영향을 주면 안 된다.

다음 방식으로 진행해줘.

1. 최근 변경사항과 삭제 기능의 관련 코드를 먼저 조사해줘.
2. 이번 변경 때문에 regression이 발생했는지 확인해줘.
3. 필터 기능을 제거하는 방식으로 해결하지 마.
4. 기존 삭제 로직을 불필요하게 완전히 다시 작성하지 마.
5. 두 기능이 함께 정상적으로 동작하도록 근본 원인을 수정해줘.
6. 가능하면 이 조합을 검증하는 regression test를 추가해줘.
7. 관련 기존 테스트도 다시 실행해줘.

작업 후
문제 원인, 수정 내용, 테스트 결과만 간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      새 기능은 정상인데 기존 기능이 깨졌을 때
      최근 변경과의 관계를 중심으로 조사하게 합니다.
    </div>
  </div>

  <h3>4. Codex가 이상한 방식으로 해결한 것 같다면 다시 검토시킵니다</h3>

  <p>
    AI가 만든 코드도 항상 좋은 방식으로 구현된다고 보장할 수는 없습니다.
  </p>

  <p>
    기능은 겉으로 정상처럼 보이는데
    지나치게 많은 코드를 바꾸었거나,
    임시방편으로 해결했거나,
    새로운 중복 로직을 만든 경우도 있을 수 있습니다.
  </p>

  <div class="concept">
    <div class="concept-title">🔍 이런 부분을 Codex에게 다시 확인시킬 수 있습니다.</div>

    <div class="concept-example">
      • 필요 이상으로 많은 파일을 수정하지 않았는가?<br>
      • 같은 기능을 하는 코드를 또 만들지 않았는가?<br>
      • 특정 값만 동작하도록 하드코딩하지 않았는가?<br>
      • 오류를 그냥 무시하고 있지는 않은가?<br>
      • 테스트를 통과시키기 위해 테스트 자체를 약화하지 않았는가?<br>
      • 기존 개발 원칙을 우회하지 않았는가?
    </div>
  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">방금 구현한 변경을 자체 검토시키기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">방금 네가 완료한 변경사항을
한 번 더 독립적으로 검토해줘.

기능이 동작하는지만 보지 말고
현재 diff와 관련 코드를 기준으로 다음 항목을 확인해줘.

1. 임시방편으로 증상만 막은 부분이 있는지
2. 불필요한 하드코딩이 들어갔는지
3. 기존에 재사용할 수 있는 로직을 두고
   비슷한 코드를 새로 만들었는지
4. 기능 하나를 위해 필요 이상으로 많은 영역을 수정했는지
5. 기존 `AGENTS.md` 또는 관련 docs의 개발 원칙을 위반했는지
6. 오류를 숨기거나 무시하는 처리가 추가되었는지
7. 테스트를 통과시키기 위해
   assertion을 약하게 만들거나 테스트를 삭제한 부분이 있는지
8. 이번 변경으로 발생할 수 있는 edge case가 남아 있는지

문제가 없다면 그대로 유지해줘.

문제가 발견된다면
현재 architecture를 불필요하게 변경하지 않는 범위에서 수정하고,
관련 테스트를 다시 실행해줘.

마지막에는 발견한 문제와 수정 여부만 짧게 정리해줘.</pre>

    <div class="prompt-purpose">
      구현 결과를 사람이 직접 코드 리뷰하지 않더라도
      Codex에게 한 번 더 품질 검토를 맡길 수 있습니다.
    </div>
  </div>

  <h3>5. Codex가 하는 말을 이해하지 못하면 ChatGPT로 돌아옵니다</h3>

  <p>
    Codex가 다음과 같이 이야기할 수 있습니다.
  </p>

  <div class="concept">
    <div class="concept-title">💬 예시</div>

    <div class="concept-example">
      “현재 문제는 derived state와 persisted state가
      서로 다른 source of truth를 사용해서 발생했습니다.”<br><br>

      개발 경험이 없다면 이 문장이 무슨 뜻인지 몰라도 전혀 이상하지 않습니다.
    </div>
  </div>

  <p>
    이때 무작정 Codex의 추천을 승인하지 말고
    설명 전체를 ChatGPT에 가져와서 이해한 뒤 결정할 수 있습니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">Codex의 기술 설명을 이해하기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">나는 개발 입문자이고
현재 Codex와 함께 웹 애플리케이션을 만들고 있어.

Codex가 현재 문제에 대해 아래처럼 설명했다.

[Codex의 설명]
여기에 Codex가 보낸 내용을 그대로 붙여 넣기

이 내용을 내가 개발 방향을 판단할 수 있도록 설명해줘.

다음 기준으로 설명해줘.

1. 현재 실제로 어떤 문제가 발생한 것인지
   일상적인 표현으로 먼저 설명해줘.

2. Codex가 사용한 중요한 개발 용어가 있다면
   지금 문제를 이해하는 데 필요한 만큼만 설명해줘.

3. 문제가 발생하는 흐름을
   사용자 행동부터 내부 처리까지 순서대로 설명해줘.

4. Codex가 제안한 해결책이 있다면
   왜 그 방법으로 해결되는지 설명해줘.

5. 그 해결책이
   - 근본적인 해결인지
   - 임시방편인지
   - 프로젝트 구조를 크게 바꾸는 방법인지
   구분해서 알려줘.

6. 다른 현실적인 해결 방법이 있다면
   각각의 장단점을 비교해줘.

7. 지금 규모의 프로젝트에서
   가장 단순하고 유지하기 쉬운 방법이 무엇인지 알려줘.

8. 내가 Codex에게 추가로 확인해야 할 내용이 있다면 알려줘.

9. 충분히 판단할 수 있다면
   선택한 방향을 Codex에게 전달할
   명확한 다음 작업 프롬프트를 만들어줘.

코드 한 줄 한 줄을 해석하는 것보다
내가 개발 방향을 이해하고 결정할 수 있도록 설명해줘.</pre>

    <div class="prompt-purpose">
      어려운 기술 설명을 그대로 믿거나 거부하지 않고
      ChatGPT를 통해 이해한 뒤 다음 결정을 내리기 위한 프롬프트입니다.
    </div>
  </div>

  <h3>6. 중요한 구조 변경을 제안받으면 바로 승인하지 않아도 됩니다</h3>

  <div class="concept">
    <div class="concept-title">🏗 모든 해결책이 단순한 코드 수정으로 끝나는 것은 아닙니다.</div>

    <p>
      Codex가 문제를 해결하기 위해 다음과 같은 제안을 할 수도 있습니다.
    </p>

    <div class="concept-example">
      새로운 state management library를 추가하자.<br><br>

      localStorage 대신 database로 옮기자.<br><br>

      현재 데이터 구조 전체를 변경하자.<br><br>

      frontend 구조를 크게 다시 나누자.
    </div>

    <p>
      이런 변경은 여러 기능에 영향을 줄 수 있기 때문에
      바로 구현하지 않고 분석만 요청할 수 있습니다.
    </p>
  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">큰 변경은 아직 하지 말고 영향만 분석하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 문제를 해결하기 위해
프로젝트 구조에 영향을 줄 수 있는 변경을 제안한 것으로 이해했다.

아직 구현하지 마.

먼저 현재 프로젝트를 기준으로
이 변경이 실제로 필요한지 분석해줘.

다음 내용을 정리해줘.

1. 현재 구조에서 정확히 어떤 문제가 있는지
2. 작은 수정만으로 해결하기 어려운 이유가 있는지
3. 제안한 구조 변경이 해결하는 문제
4. 변경해야 할 주요 영역
5. 기존 기능과 데이터에 미치는 영향
6. 새로운 dependency가 필요한지
7. migration 또는 호환성 문제가 있는지
8. 구현 난이도와 이후 유지보수의 변화
9. 현재 규모에서 더 단순한 대안이 있는지
10. 지금 변경하지 않고 나중으로 미뤄도 되는지

여러 방법이 가능하면
각각의 장단점을 비교해줘.

내가 명시적으로 구현을 요청하기 전에는
소스코드, dependency, 데이터 구조, 프로젝트 설정을 변경하지 마.</pre>

    <div class="prompt-purpose">
      프로젝트 전체에 영향을 줄 수 있는 큰 선택은
      먼저 영향 범위를 확인하고 결정할 수 있게 합니다.
    </div>
  </div>

  <h3>7. 문제를 해결한 뒤에는 같은 문제가 다시 생기지 않게 합니다</h3>

  <p>
    중요한 버그를 한 번 고쳤다면
    다음 기능을 추가했을 때 같은 문제가 다시 생길 수 있습니다.
  </p>

  <p>
    그래서 가능한 경우
    <strong>버그를 재현하는 테스트를 남기는 것</strong>이 좋습니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">수정한 버그를 테스트로 남기기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">이번 버그 수정이 완료되었다면
같은 문제가 다시 발생하는 것을 방지할 수 있는 테스트가 필요한지 확인해줘.

[수정한 문제]
새 일정 저장 후 목록에 반영되지 않던 문제

다음 기준으로 판단해줘.

1. 현재 테스트 체계에서
   이 문제를 자동으로 재현하고 검증할 수 있는지 확인해줘.

2. 의미 있는 regression test를 만들 수 있다면 추가해줘.

3. 구현 내부 구조에 지나치게 의존하는 테스트보다
   실제로 보장해야 하는 동작을 검증하는 테스트를 우선해줘.

4. 테스트를 추가한 뒤
   관련 전체 테스트를 다시 실행해줘.

5. 이미 같은 상황을 충분히 검증하는 테스트가 있다면
   중복 테스트를 추가하지 마.

완료 후
어떤 동작을 테스트로 보호하게 되었는지만 간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      한 번 발견한 중요한 버그가
      이후 기능 추가 과정에서 다시 나타나는 것을 줄이는 방법입니다.
    </div>
  </div>

  <div class="summary">
    <div class="summary-title">문제가 생겼을 때의 기본 흐름</div>

    <p>
      <strong>
        증상 발견 →
        Codex에게 원인 조사 →
        필요한 부분 수정 →
        테스트 →
        결과가 이해되지 않으면 ChatGPT와 상담 →
        필요하면 다시 Codex에게 지시
      </strong>
    </p>

    <p>
      중요한 것은
      개발 입문자가 직접 문제 파일을 찾아내는 것이 아니라,
      <strong>현재 현상과 원하는 동작을 정확하게 설명하고
      AI에게 조사할 수 있는 정보를 주는 것</strong>입니다.
    </p>
  </div>

<section class="chapter">
  <div class="chapter-number">Chapter 07</div>
  <h2>테스트는 AI가 만든 기능을 믿을 수 있게 해주는 안전망입니다</h2>

  <p>
    Codex가 코드를 빠르게 만들어도,
    실제로 모든 기능이 정상적으로 동작한다는 뜻은 아닙니다.
  </p>

  <p>
    그래서 바이브 코딩에서는
    <strong>코드 작성뿐 아니라 테스트까지 Codex에게 함께 맡기는 습관</strong>이 중요합니다.
  </p>

  <div class="key-point">
    <strong>코드가 만들어졌다고 개발이 끝난 것은 아닙니다.</strong><br>
    가능한 범위에서
    <strong>구현 → 테스트 → 실패 원인 수정 → 다시 테스트</strong>
    까지를 하나의 작업으로 생각합니다.
  </div>

  <h3>1. 테스트 코드를 직접 이해하지 않아도 됩니다</h3>

  <div class="concept">
    <div class="concept-title">🧪 입문자에게 중요한 것은 “무엇을 검증해야 하는가”입니다.</div>

    <p>
      테스트 library의 문법이나
      테스트 코드 작성 방법을 처음부터 공부할 필요는 없습니다.
    </p>

    <p>
      Codex에게
      <strong>사용자가 어떤 행동을 했을 때 어떤 결과가 나와야 하는지</strong>
      알려주면 됩니다.
    </p>

    <div class="concept-example">
      일정 관리 앱이라면:<br><br>

      • 일정을 추가하면 목록에 나타나는가?<br>
      • 수정하면 변경된 내용이 저장되는가?<br>
      • 삭제하면 실제로 사라지는가?<br>
      • 완료 처리하면 상태가 바뀌는가?<br>
      • 새로고침 후에도 데이터가 유지되는가?<br>
      • 새로운 기능을 추가한 뒤 기존 기능도 계속 정상인가?
    </div>
  </div>

  <h3>2. 테스트에는 여러 단계가 있습니다</h3>

  <div class="table-wrap">
    <table>
      <thead>
        <tr>
          <th>테스트</th>
          <th>쉽게 설명하면</th>
          <th>일정 앱 예시</th>
        </tr>
      </thead>

      <tbody>
        <tr>
          <td><strong>Unit Test</strong></td>
          <td>
            작은 기능 하나를 따로 검사합니다.
          </td>
          <td>
            오늘 날짜인지 판단하는 함수가 정상적으로 동작하는지 확인
          </td>
        </tr>

        <tr>
          <td><strong>Integration Test</strong></td>
          <td>
            여러 기능이 연결되었을 때 정상적으로 동작하는지 검사합니다.
          </td>
          <td>
            일정 입력 → 저장 → 상태 변경 → 목록 표시까지 확인
          </td>
        </tr>

        <tr>
          <td><strong>E2E Test</strong></td>
          <td>
            실제 사용자가 앱을 사용하는 흐름과 비슷하게 검사합니다.
          </td>
          <td>
            페이지 접속 → 일정 추가 → 수정 → 새로고침 → 삭제
          </td>
        </tr>

        <tr>
          <td><strong>Regression Test</strong></td>
          <td>
            새로운 변경 때문에 예전에 잘 되던 기능이 망가지지 않았는지 검사합니다.
          </td>
          <td>
            중요도 기능을 추가한 뒤 기존 일정 삭제 기능도 정상인지 확인
          </td>
        </tr>
      </tbody>
    </table>
  </div>

  <div class="note">
    <span class="box-title">📌 모든 테스트를 처음부터 완벽하게 만들 필요는 없습니다</span>
    프로젝트가 작을 때는 중요한 기능부터 테스트하고,
    기능이 늘어날수록 필요한 테스트를 점진적으로 추가하면 됩니다.
  </div>

  <h3>3. Unit Test는 작은 로직을 빠르게 확인합니다</h3>

  <div class="concept">
    <div class="concept-title">🔬 작은 기능이 예상대로 동작하는지 확인합니다.</div>

    <p>
      예를 들어 일정의 날짜를 비교하거나,
      중요도 값을 변환하거나,
      완료된 일정만 골라내는 작은 로직은
      브라우저를 열지 않고도 빠르게 테스트할 수 있습니다.
    </p>

    <div class="concept-example">
      입력:<br>
      오늘 일정 3개 + 내일 일정 2개<br><br>

      기대 결과:<br>
      “오늘 일정 보기” 기능에서는 오늘 일정 3개만 반환되어야 함
    </div>
  </div>

  <h3>4. Integration Test는 여러 기능의 연결을 확인합니다</h3>

  <div class="concept">
    <div class="concept-title">🔗 실제 앱은 여러 기능이 연결되어 동작합니다.</div>

    <p>
      각각의 함수가 정상이어도
      서로 연결했을 때 문제가 생길 수 있습니다.
    </p>

    <div class="concept-example">
      일정 입력<br>
      ↓<br>
      저장 버튼 클릭<br>
      ↓<br>
      일정 데이터 생성<br>
      ↓<br>
      상태 업데이트<br>
      ↓<br>
      localStorage 저장<br>
      ↓<br>
      화면 목록 업데이트
    </div>

    <p>
      Integration Test는 이런 연결된 흐름이 정상인지 확인합니다.
    </p>
  </div>

  <h3>5. 실제 브라우저 없이도 많은 프론트엔드 테스트가 가능합니다</h3>

  <div class="concept">
    <div class="concept-title">🖥 화면 로직의 상당 부분은 테스트 환경에서 확인할 수 있습니다.</div>

    <p>
      React 프로젝트에서는 실제 Chrome 창을 직접 띄우지 않고도
      가상의 DOM 환경에서 컴포넌트를 렌더링하고
      클릭이나 입력을 흉내 내는 테스트를 만들 수 있습니다.
    </p>

    <div class="concept-example">
      테스트가 자동으로:<br><br>

      일정 제목 입력<br>
      ↓<br>
      저장 버튼 클릭<br>
      ↓<br>
      일정 목록에 제목이 나타나는지 확인<br>
      ↓<br>
      완료 버튼 클릭<br>
      ↓<br>
      완료 상태가 표시되는지 확인
    </div>
  </div>

  <div class="key-point">
    <strong>프론트엔드 테스트 = 반드시 사람이 브라우저를 직접 조작해야 하는 것은 아닙니다.</strong><br>
    화면의 많은 기능과 상태 변화는 자동 테스트 코드로 검증할 수 있습니다.
  </div>

  <h3>6. 그래도 실제 브라우저 테스트가 필요한 이유</h3>

  <div class="concept">
    <div class="concept-title">🌐 실제 브라우저에서만 확인하기 좋은 문제가 있습니다.</div>

    <p>
      화면 로직은 정상이어도
      실제 브라우저 환경에서 문제가 생길 수 있습니다.
    </p>

    <div class="concept-example">
      • 버튼이 실제로 클릭되지 않는다.<br>
      • 화면 이동이 예상과 다르다.<br>
      • 새로고침 후 상태가 다르다.<br>
      • 모바일 화면에서 레이아웃이 깨진다.<br>
      • 특정 브라우저 동작과 충돌한다.<br>
      • Canvas, drag &amp; drop, 실제 크기 계산처럼 브라우저 환경이 중요한 기능이 있다.
    </div>
  </div>

  <h3>7. E2E 테스트는 실제 사용자 행동을 자동으로 따라갑니다</h3>

  <div class="concept">
    <div class="concept-title">🤖 Playwright 같은 도구를 이용하면 실제 브라우저 엔진을 자동으로 조작할 수 있습니다.</div>

    <div class="concept-example">
      앱 실행<br>
      ↓<br>
      브라우저 페이지 열기<br>
      ↓<br>
      일정 추가 버튼 클릭<br>
      ↓<br>
      제목과 날짜 입력<br>
      ↓<br>
      저장 클릭<br>
      ↓<br>
      화면에 일정이 나타나는지 확인<br>
      ↓<br>
      페이지 새로고침<br>
      ↓<br>
      일정이 계속 남아 있는지 확인
    </div>
  </div>

  <p>
    브라우저 창을 화면에 직접 보여주지 않고
    백그라운드에서 실행하는 방식도 가능합니다.
  </p>

  <div class="note">
    <span class="box-title">📌 E2E 테스트도 Codex에게 맡길 수 있습니다</span>
    프로젝트에 적절한 테스트 환경이 있다면
    Codex가 테스트를 작성하고 실행한 뒤,
    실패하면 원인을 찾아 수정하는 작업까지 진행할 수 있습니다.
  </div>

  <h3>8. 테스트 환경이 없다면 바로 설치시키지 말고 먼저 확인할 수도 있습니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">현재 프로젝트의 테스트 상태 분석하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트의 테스트 환경을 분석해줘.

아직 새로운 테스트 library나 framework를 설치하지 마.

먼저 다음 내용을 확인해줘.

1. 현재 프로젝트에 어떤 테스트 도구가 이미 설치되어 있는지
2. unit test를 작성할 수 있는 환경이 있는지
3. frontend component 또는 integration test를 작성할 수 있는지
4. 실제 브라우저를 이용하는 E2E 테스트 환경이 있는지
5. 현재 어떤 테스트들이 이미 존재하는지
6. 지금 핵심 기능 중 자동 테스트로 보호되지 않는 중요한 부분이 무엇인지

그다음 현재 프로젝트 규모를 기준으로
추가하면 좋은 테스트 체계를 제안해줘.

새로운 도구가 필요하다면 각각에 대해
- 왜 필요한지
- 어떤 범위를 테스트할 수 있는지
- 새로운 dependency가 무엇인지
- 설정 복잡도가 어느 정도인지

를 설명해줘.

아직 실제 dependency 설치나 설정 변경은 하지 말고,
내가 어떤 테스트 환경을 도입할지 결정할 수 있도록 분석 결과만 알려줘.</pre>

    <div class="prompt-purpose">
      테스트 환경을 무조건 추가하기 전에
      현재 프로젝트에 이미 무엇이 있는지 확인하는 프롬프트입니다.
    </div>
  </div>

  <h3>9. 테스트 체계를 처음 구축할 때</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">프로젝트에 기본 테스트 안전망 만들기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트에 기본적인 자동 테스트 체계를 구축해줘.

[목표]
앞으로 Codex가 새로운 기능을 개발한 뒤
자동으로 주요 기능을 검증하고,
기존 기능의 regression을 확인할 수 있는 기본 안전망을 만들고 싶다.

[현재 프로젝트]
- React
- TypeScript
- Vite
- localStorage 기반 일정 관리 앱

먼저 현재 dependency와 프로젝트 구조를 다시 확인하고,
이미 사용할 수 있는 테스트 도구가 있다면 우선 활용해줘.

새로운 도구가 필요한 경우에는
현재 규모에 적절하고 널리 사용되는 최소한의 구성을 선택해줘.
불필요하게 여러 테스트 framework를 동시에 추가하지 마.

다음 범위를 우선적으로 보호해줘.

[Unit]
- 일정 필터링
- 날짜 판단
- 중요도 기본값 처리
- 데이터 변환처럼 중요한 순수 로직

[Integration]
- 일정 생성 후 화면 반영
- 일정 수정
- 일정 삭제
- 완료 상태 변경
- localStorage 저장 및 로드

[E2E]
가능하다면 실제 브라우저 환경에서 다음 주요 사용자 흐름을 검증해줘.

1. 앱 실행
2. 일정 생성
3. 생성된 일정 확인
4. 일정 수정
5. 완료 처리
6. 새로고침 후 데이터 유지 확인
7. 일정 삭제

[테스트 원칙]
- 구현 내부 세부사항보다 사용자가 기대하는 동작을 검증하는 테스트를 우선해줘.
- 테스트를 통과시키기 위해 기능을 하드코딩하지 마.
- 실패하는 테스트를 단순히 삭제하거나 비활성화하지 마.
- 의미 없는 assertion으로 테스트를 약하게 만들지 마.
- 지나치게 세부적인 테스트를 너무 많이 만들어 유지보수를 어렵게 하지 마.

[문서]
테스트 체계와 주요 명령어,
각 테스트 종류의 역할을
현재 `docs/` 구조에서 적절한 문서에 간단하게 기록해줘.

[완료 후]
- 추가하거나 사용한 테스트 도구
- 테스트한 주요 기능
- 실행 결과
- 자동 테스트로 확인하기 어려운 부분
- 내가 직접 확인해야 하는 부분

을 짧게 정리해줘.</pre>

    <div class="prompt-purpose">
      코드 리뷰보다 자동 테스트를 중심으로 프로젝트 품질을 관리하고 싶을 때
      처음 한 번 구축해두는 테스트 기반입니다.
    </div>
  </div>

  <h3>10. 새로운 기능을 만들 때 테스트까지 한 번에 요청합니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">구현과 검증을 하나의 작업으로 맡기기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트에 다음 기능을 추가해줘.

[기능]
완료된 일정만 따로 볼 수 있는 필터

[요구사항]
- 기본 상태에서는 모든 일정이 표시된다.
- `완료됨` 필터를 선택하면 완료된 일정만 표시된다.
- 필터를 해제하면 다시 전체 일정이 표시된다.
- 필터링은 원본 일정 데이터를 변경하지 않아야 한다.

작업 전에 관련 프로젝트 문서와 기존 일정 목록 구현을 확인해줘.

현재 architecture와 state 관리 방식을 유지하면서
필요한 부분만 수정해줘.

구현이 끝나면 작업을 종료하지 말고
다음 검증까지 진행해줘.

1. 새 필터 기능에 필요한 unit 또는 integration test
2. 필터 선택 및 해제 동작
3. 일정 추가 후 필터 동작
4. 완료 상태 변경 후 필터 결과
5. 기존 일정 수정 및 삭제 기능의 regression
6. 현재 E2E 환경이 있다면 주요 사용자 흐름 확인

실패가 발견되면
실제 원인을 조사하고 수정한 뒤 다시 테스트해줘.

모든 관련 검증이 끝난 뒤
구현 내용과 테스트 결과만 간단하게 보고해줘.</pre>

    <div class="prompt-purpose">
      기능 개발과 테스트를 분리하지 않고
      Codex에게 하나의 완료 조건으로 전달하는 방법입니다.
    </div>
  </div>

  <h3>11. 테스트가 통과했다고 무조건 모든 것이 완벽한 것은 아닙니다</h3>

  <div class="concept">
    <div class="concept-title">👀 자동 테스트와 사람의 확인은 역할이 다릅니다.</div>

    <p>
      자동 테스트는
      우리가 정의한 동작을 매우 빠르게 반복해서 확인하는 데 강합니다.
    </p>

    <p>
      하지만 사용자가 느끼는 디자인과 사용감까지
      완벽하게 판단해 주지는 못합니다.
    </p>

    <div class="concept-example">
      자동 테스트가 잘하는 것:<br><br>

      ✅ 버튼 클릭 후 데이터 저장<br>
      ✅ 목록 업데이트<br>
      ✅ 새로고침 후 데이터 유지<br>
      ✅ 특정 조건에서 오류가 발생하지 않는지 확인<br><br>

      사람이 직접 보기 좋은 것:<br><br>

      👀 화면이 답답하지 않은가?<br>
      👀 버튼 위치가 자연스러운가?<br>
      👀 모바일에서 실제로 사용하기 편한가?<br>
      👀 색상이나 강조가 내가 원한 느낌인가?
    </div>
  </div>

  <div class="key-point">
    <strong>좋은 역할 분담:</strong><br>
    Codex와 자동 테스트는 기능을 반복해서 검증하고,<br>
    사람은 마지막에 실제 제품을 사용해보고 원하는 경험인지 판단합니다.
  </div>

  <h3>12. 작업 완료 기준을 프로젝트 규칙으로 만들 수 있습니다</h3>

  <p>
    테스트 환경이 자리 잡았다면
    앞으로 매번 “테스트도 해주세요”라고 길게 설명하지 않아도 됩니다.
  </p>

  <p>
    프로젝트의 작업 완료 기준을
    <code>AGENTS.md</code> 또는 관련 테스트 문서에 기록할 수 있습니다.
  </p>

  <div class="file-tree">## Definition of Done

A meaningful feature change is complete only when:

- The requested behavior is implemented.
- Relevant existing tests pass.
- Important new behavior has appropriate tests.
- Existing core features are checked for regression.
- Type and lint checks pass when applicable.
- Failing tests are not hidden or disabled to complete the task.
- Important user-facing behavior that cannot be automated is reported for manual verification.</div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">테스트를 기본 작업 원칙으로 등록하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트의 테스트 환경이 구성되었다.

앞으로 의미 있는 기능 개발이나 버그 수정에서
테스트를 별도로 매번 요청하지 않아도
Codex가 기본적으로 필요한 검증을 수행하도록
프로젝트의 작업 완료 기준을 문서화해줘.

현재 `AGENTS.md`와 관련 `docs/`를 확인한 뒤
가장 적절한 위치에 Definition of Done을 추가해줘.

다음 원칙을 포함해줘.

- 요청한 기능 구현만으로 작업을 완료 처리하지 않는다.
- 관련 기존 테스트를 실행한다.
- 중요한 새로운 동작에는 적절한 테스트를 추가한다.
- 핵심 기존 기능의 regression을 확인한다.
- 프로젝트에서 사용하는 type check와 lint가 있다면 적절하게 실행한다.
- 테스트 실패를 삭제, 비활성화, 약화해서 숨기지 않는다.
- 자동으로 검증하기 어려운 사용자 동작은 최종 보고에서 알려준다.
- 실제 배포는 사용자의 명시적인 요청 없이는 진행하지 않는다.

문서는 간결하게 유지하고
같은 원칙을 여러 파일에 반복하지 마.

이번 작업에서는 애플리케이션 기능 자체는 변경하지 마.</pre>

    <div class="prompt-purpose">
      테스트를 일회성 요청이 아니라
      앞으로 Codex가 계속 따르는 프로젝트 기본 규칙으로 만드는 방법입니다.
    </div>
  </div>

  <div class="summary">
    <div class="summary-title">테스트에서 기억할 것</div>

    <p>
      코드를 직접 읽지 않더라도
      <strong>무엇이 정상적으로 동작해야 하는지</strong>를 명확하게 정의하면

    </p>

3. 필요 이상의 framework 또는 infrastructure는 추가하지 마.
4. frontend와 backend의 책임을 명확하게 분리해줘.
5. API 요청과 응답 형식을 단순하고 명확하게 유지해줘.

[검증]
- frontend에서 backend 요청
- backend의 외부 API 호출
- 정상 결과 반환
- 잘못된 요청 처리
- 외부 API 실패 처리

- 테스트 결과
- 사용자가 직접 설정해야 하는 값
- 내가 실제 브라우저에서 확인할 동작

을 간단하게 정리해줘.</pre>

    </div>

  <h3>10. API 오류도 정상적인 개발 상황입니다</h3>

  <div class="concept">
    <div class="concept-title">🚨 외부 서비스는 항상 성공한다고 가정하면 안 됩니다.</div>

    <div class="concept-example">
      • 인터넷 연결 실패<br>
      • API 사용량 제한 초과<br>
      • 잘못된 API Key<br>
      • 외부 서비스 장애<br>
      • 사용자가 너무 긴 내용을 입력함<br>
      • 외부 API 응답 형식이 예상과 다름
    </div>
  </div>

  <p>
    이런 상황에서 앱 전체가 멈추지 않고
    사용자에게 적절한 안내를 보여주는 것이 좋습니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">외부 API 실패 상황 보완하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 AI 추천 기능의 정상 요청은 동작한다.

이제 외부 API 실패 상황에서도
앱이 안정적으로 동작하도록 확인하고 싶다.

다음 상황을 점검해줘.

- backend에 필요한 환경 변수가 없는 경우
- 외부 API가 오류를 반환하는 경우
- 네트워크 요청이 실패하는 경우
- 응답 시간이 너무 오래 걸리는 경우
- 사용자의 입력값이 비어 있거나 허용 범위를 벗어나는 경우

다음 원칙을 지켜줘.

1. 오류를 단순히 무시하지 마.
2. 사용자가 이해할 수 있는 오류 상태를 frontend에 보여줘.
3. 내부의 민감한 오류 정보나 API Key가 사용자에게 노출되지 않도록 해줘.
4. AI 요청이 실패해도 기존 일정 관리 기능은 계속 사용할 수 있어야 한다.
5. 관련 테스트를 추가하고 실행해줘.
6. 기존 정상 흐름도 계속 동작하는지 확인해줘.

작업 후
어떤 실패 상황을 처리하게 되었는지와
내가 실제로 확인해야 할 부분만 정리해줘.</pre>

    <div class="prompt-purpose">
      외부 서비스가 실패해도
      앱 전체가 함께 망가지지 않도록 만드는 프롬프트입니다.
    </div>
  </div>

  <h3>11. 여러 사용자가 등장하면 Backend의 역할이 더 커집니다</h3>

  <div class="concept">
    <div class="concept-title">👥 개인용 앱과 여러 사람이 사용하는 서비스는 요구사항이 다릅니다.</div>

    <p>
      처음에는 localStorage에 저장해도 충분했던 일정 앱이
      여러 사람이 사용하는 서비스가 되면 새로운 문제가 생깁니다.
    </p>

    <div class="concept-example">
      누가 로그인했는가?<br>
      ↓<br>
      이 일정은 누구의 데이터인가?<br>
      ↓<br>
      다른 사용자가 볼 수 있어도 되는가?<br>
      ↓<br>
      여러 기기에서 어떻게 같은 데이터를 가져올 것인가?<br>
      ↓<br>
      데이터를 어디에 저장할 것인가?
    </div>
  </div>

  <div class="key-point">
    <strong>앱이 성장하면 필요한 기술도 달라질 수 있습니다.</strong><br>
    처음부터 모든 미래 기능을 대비하는 것이 아니라,
    실제로 필요한 순간에 구조를 확장하면 됩니다.
  </div>

  <h3>12. 큰 확장은 먼저 ChatGPT와 단계별 계획을 만듭니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">개인용 앱을 여러 사용자 서비스로 확장하기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">현재 내 일정 관리 앱은 다음 상태야.

[현재]
- React + TypeScript + Vite
- 일정 CRUD
- 완료 처리
- 중요도
- localStorage 저장
- 간단한 backend API를 통한 AI 추천 기능
- 아직 회원가입과 database는 없음

이제 앱을 여러 사용자가 사용할 수 있게 확장하고 싶어.

원하는 최종 상태는 다음과 같아.

- 회원가입
- 로그인
- 각 사용자는 자신의 일정만 확인
- 여러 기기에서 같은 일정 사용
- 로그아웃 후 다른 사용자로 로그인 가능

나는 개발 입문자이고
실제 구현은 Codex에게 맡길 예정이다.

한 번에 모든 기능을 구현하지 말고
안전한 단계로 개발 계획을 만들어줘.

다음 내용을 반드시 고려해줘.

1. authentication이 왜 필요한지
2. database가 왜 필요한지
3. 사용자와 일정 데이터를 어떻게 연결해야 하는지
4. 현재 localStorage 데이터는 어떻게 처리할 수 있는지
5. frontend와 backend 책임이 어떻게 달라지는지
6. 권한 확인이 왜 중요한지
7. 데이터 손실이나 보안 위험이 있는 단계
8. 각 단계별 테스트 방법
9. 각 단계에서 프로젝트 문서에 남겨야 할 중요한 결정

기술 선택지가 나오면
입문자가 실제 결과의 차이를 이해할 수 있게 설명해줘.

각 단계를 충분히 결정한 후에는
그 단계만 구현할 수 있도록
Codex용 작업 프롬프트를 만들어줘.</pre>

    <div class="prompt-purpose">
      앱의 규모가 커질 때
      바로 대규모 구조 변경을 시키지 않고 단계별로 확장하는 방법입니다.
    </div>
  </div>
