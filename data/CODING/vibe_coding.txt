    무엇을 만들고 싶은지 정리하고, 모르는 것은 ChatGPT와 상담하고,
    실제 프로젝트 작업은 Codex에게 맡기는 기본 개발 흐름을 익히는 것이 목표입니다.
  </p>

<section class="chapter">
  <div class="chapter-number">Chapter 01</div>
  <h2>먼저 알아야 할 최소한의 개발 개념</h2>

  <p>
    바이브 코딩을 시작하기 위해 개발자가 알고 있는 모든 내용을 배울 필요는 없습니다.
    다만 ChatGPT나 Codex가 사용하는 몇 가지 기본 용어를 알고 있으면
    AI와 훨씬 편하게 대화할 수 있습니다.
  </p>

  <div class="key-point">
    <strong>중요:</strong>
    아래 개념들을 완벽하게 외울 필요는 없습니다.
    “대충 무엇을 의미하는지”만 알고 있다가,
    실제 개발 중 이해되지 않는 내용이 나오면 ChatGPT에 다시 물어보면 됩니다.
  </div>

  <h3>1. 프로젝트 Project</h3>

  <div class="concept">
    <div class="concept-title">📁 프로젝트는 프로그램을 구성하는 전체 작업 공간입니다.</div>
    <div class="concept-subtitle">
      하나의 앱은 보통 하나의 파일이 아니라 여러 파일과 폴더로 이루어져 있습니다.
    </div>

    <p>
      예를 들어 일정 관리 앱을 만든다면 화면을 만드는 파일,
      데이터를 저장하는 파일, 여러 기능을 담당하는 파일,
      이미지와 설정 파일 등이 하나의 프로젝트 안에 들어갑니다.
    </p>

    <div class="concept-example">
      Codex에게 <strong>“현재 프로젝트를 먼저 확인해 주세요.”</strong>라고 하면
      Codex는 특정 코드 한 줄만 보는 것이 아니라 프로젝트 안의 파일들을 살펴보면서
      필요한 코드를 찾을 수 있습니다.
    </div>
  </div>

  <h3>2. Repository</h3>

  <div class="concept">
    <div class="concept-title">🗂 Repository는 프로젝트와 변경 기록을 관리하는 공간입니다.</div>

    <p>
      실습에서는 우선 <strong>“Codex가 작업할 프로젝트 폴더”</strong> 정도로 이해해도 충분합니다.
      Git을 사용하면 어떤 파일이 수정되었는지 확인하거나,
      이전 상태로 되돌리는 것도 가능해집니다.
    </p>

    <div class="concept-example">
      Codex가 “repository를 분석하겠습니다”라고 말한다면,
      어렵게 생각하지 않아도 됩니다.
      <strong>현재 프로젝트 전체를 먼저 살펴보겠다는 뜻</strong>입니다.
    </div>
  </div>

  <h3>3. Frontend</h3>

  <div class="concept">
    <div class="concept-title">🖥 Frontend는 사용자가 직접 보고 조작하는 부분입니다.</div>

    <p>
      버튼, 메뉴, 카드, 입력창, 화면 배치, 글자 크기처럼
      사용자의 화면에 나타나는 대부분의 요소가 프론트엔드에 해당합니다.
    </p>

    <div class="concept-example">
      예를 들어 이런 요청은 대부분 프론트엔드 작업입니다.<br><br>

      “상단 탭을 조금 왼쪽으로 이동시켜 주세요.”<br>
      “완료 버튼을 더 눈에 잘 띄게 해 주세요.”<br>
      “모바일에서는 카드가 한 줄에 하나씩 나오게 해 주세요.”
    </div>
  </div>

  <h3>4. Backend</h3>

  <div class="concept">
    <div class="concept-title">⚙️ Backend는 화면 뒤에서 필요한 일을 처리하는 부분입니다.</div>

    <p>
      사용자가 직접 보지는 않지만,
      로그인 확인, 데이터 저장, 여러 사용자 사이의 데이터 처리,
      권한 확인처럼 화면만으로 해결하기 어려운 일을 담당합니다.
    </p>

    <div class="concept-example">
      사용자가 로그인 버튼을 눌렀다고 생각해 봅시다.<br><br>

      프론트엔드는 이메일과 비밀번호를 입력받습니다.<br>
      백엔드는 실제로 그 사용자가 맞는지 확인합니다.<br>
      확인이 끝나면 결과를 다시 프론트엔드에 전달합니다.
    </div>
  </div>

  <h3>5. API</h3>

  <div class="concept">
    <div class="concept-title">🔌 API는 다른 기능을 가져오거나, 백엔드의 기능을 요청할 때 사용하는 연결 방법입니다.</div>

    <p>
      API를 처음 배울 때
      “프로그램끼리 데이터를 주고받는 통로”라고 설명하는 경우가 많지만,
      처음에는 그 말 자체가 어렵게 느껴질 수 있습니다.
    </p>

    <p>
      실제 개발에서는 다음처럼 생각하면 훨씬 쉽습니다.
    </p>

    <div class="concept-example">
      <strong>내 프론트엔드만으로 할 수 없는 일을 다른 곳에 부탁하는 방법</strong><br><br>

      • ChatGPT의 AI 기능을 내 앱에서 사용하고 싶다 → OpenAI API 사용<br>
      • 현재 날씨를 가져오고 싶다 → 날씨 서비스 API 사용<br>
      • 사용자의 로그인 정보를 확인하고 싶다 → 백엔드의 로그인 API 사용<br>
      • 서버에 저장된 일정을 가져오고 싶다 → 내가 만든 백엔드 API 사용
    </div>

    <p>
      즉 API에는 크게 두 가지 상황이 자주 등장합니다.
    </p>

    <ul>
      <li>
        <strong>외부 서비스의 기능을 가져오는 경우</strong><br>
        AI, 지도, 번역, 결제, 날씨 등 이미 다른 회사가 제공하는 기능을 사용합니다.
      </li>
      <li>
        <strong>내 백엔드에서 만든 기능을 프론트엔드가 사용하는 경우</strong><br>
        로그인, 데이터 저장, 사용자 정보 조회 같은 기능을 백엔드에 요청합니다.
      </li>
    </ul>
  </div>

  <div class="tip">
    <span class="box-title">💡 모르면 바로 ChatGPT에 물어보세요</span>
    Codex가 “이 기능을 구현하려면 API가 필요합니다”라고 이야기했는데
    API가 왜 필요한지 이해되지 않는다면 개발을 멈출 필요가 없습니다.
    그 내용을 그대로 ChatGPT에 붙여 넣고 설명을 요청하면 됩니다.
  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">개발 용어가 이해되지 않을 때</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">나는 바이브 코딩을 배우고 있는 개발 입문자야.

현재 Codex와 함께 웹 애플리케이션을 개발하고 있는데,
Codex가 아래와 같은 내용을 이야기했어.

[여기에 Codex의 설명을 붙여 넣기]

다음 기준으로 설명해줘.

1. 위 내용에서 내가 반드시 이해해야 하는 핵심 개념을 먼저 알려줘.
2. 어려운 개발 용어는 처음 개발하는 사람도 이해할 수 있게 설명해줘.
3. 각각의 개념이 지금 내가 만드는 기능에서 왜 필요한지도 설명해줘.
4. 여러 선택지가 있다면 각각의 장단점을 비교해줘.
5. 지금 당장 결정하지 않아도 되는 내용은 구분해줘.
6. 마지막에는 내가 Codex에게 어떤 결정을 전달하면 되는지 정리해줘.

코드 자체를 자세히 설명하기보다,
내가 개발 방향을 판단할 수 있도록 설명해줘.</pre>

    <div class="prompt-purpose">
      개발 용어를 전부 공부하려고 하지 않고,
      현재 작업에 필요한 만큼만 이해하기 위한 프롬프트입니다.
    </div>
  </div>

  <h3>6. Library / Dependency</h3>

  <div class="concept">
    <div class="concept-title">🧩 이미 다른 개발자가 만들어 놓은 기능을 가져다 사용할 수 있습니다.</div>

    <p>
      프로그램의 모든 기능을 처음부터 직접 만들 필요는 없습니다.
      이미 만들어진 기능을 프로젝트에 추가해서 사용할 수 있습니다.
    </p>

    <p>
      이런 외부 기능을 흔히 <strong>라이브러리</strong>라고 부르고,
      프로젝트가 그 라이브러리를 필요로 할 때
      <strong>dependency</strong>라고 표현하기도 합니다.
    </p>

    <div class="concept-example">
      달력 기능을 만들기 위해 날짜 계산을 전부 직접 구현하는 대신
      검증된 날짜 처리 라이브러리를 사용할 수 있습니다.<br><br>

      예쁜 아이콘 수백 개를 직접 그리는 대신
      아이콘 라이브러리를 설치할 수도 있습니다.
    </div>
  </div>

  <div class="warning">
    <span class="box-title">⚠️ 라이브러리를 무조건 추가하는 것은 좋은 개발이 아닙니다.</span>
    작은 기능 하나를 만들기 위해 큰 라이브러리를 계속 추가하면
    프로젝트가 복잡해질 수 있습니다.
    따라서 Codex가 새로운 핵심 라이브러리나 개발 방식을 도입하려 한다면
    이유를 확인한 뒤 결정하는 것이 좋습니다.
  </div>

  <h3>7. Framework</h3>

  <div class="concept">
    <div class="concept-title">🏗 Framework는 프로그램을 만드는 기본적인 틀입니다.</div>

    <p>
      웹앱을 만들 때 모든 것을 아무 규칙 없이 처음부터 작성하지 않고,
      일정한 구조와 개발 방법을 제공하는 도구를 사용하는 경우가 많습니다.
    </p>

    <p>
      예를 들어 React를 사용하는 프로젝트라면
      화면을 여러 개의 컴포넌트로 나누어 만드는 방식을 사용할 수 있습니다.
    </p>

    <div class="concept-example">
      중요한 것은 프레임워크 종류를 외우는 것이 아닙니다.<br><br>

      이미 React로 만들어진 프로젝트라면,
      특별한 이유 없이 Codex가 다른 프레임워크로 프로젝트 전체를 바꾸지 않도록
      기존 구조를 유지시키는 것이 더 중요합니다.
    </div>
  </div>

  <h3>8. 데이터 저장</h3>

  <div class="concept">
    <div class="concept-title">💾 앱에서 만든 정보를 어디에 보관할지 결정해야 합니다.</div>

    <p>
      일정 관리 앱에서 사용자가 일정을 만들었다면
      새로고침하거나 앱을 다시 실행해도 일정이 남아 있어야 할 수 있습니다.
    </p>

    <p>
      간단한 프로젝트에서는 브라우저 내부 저장소를 사용할 수도 있고,
      여러 기기와 사용자가 데이터를 공유해야 한다면
      서버와 데이터베이스가 필요할 수도 있습니다.
    </p>

    <div class="concept-example">
      <strong>작은 개인용 앱</strong><br>
      → 브라우저에 저장하는 방법으로 시작할 수도 있습니다.<br><br>

      <strong>로그인해서 여러 기기에서 사용하는 서비스</strong><br>
      → 서버와 데이터베이스가 필요한 경우가 많습니다.
    </div>
  </div>

  <h3>9. Test</h3>

  <div class="concept">
    <div class="concept-title">🧪 AI가 코드를 만들었다고 해서 개발이 끝난 것은 아닙니다.</div>

    <p>
      코드가 존재하는 것과 실제 기능이 정상적으로 동작하는 것은 다른 문제입니다.
      따라서 Codex에게 구현뿐 아니라 테스트까지 맡기는 습관이 중요합니다.
    </p>

    <p>
      입문 단계에서는 테스트의 세부 문법보다
      다음 차이만 이해하면 충분합니다.
    </p>

    <ul>
      <li>
        <strong>Unit Test</strong> —
        작은 기능 하나가 올바르게 동작하는지 확인합니다.
      </li>
      <li>
        <strong>Integration Test</strong> —
        여러 기능이 연결되었을 때 정상적으로 동작하는지 확인합니다.
      </li>
      <li>
        <strong>E2E Test</strong> —
        실제 사용자가 앱을 사용하는 것처럼 전체 흐름을 확인합니다.
      </li>
      <li>
        <strong>Regression Test</strong> —
        새로운 기능을 추가한 뒤 기존 기능이 망가지지 않았는지 확인합니다.
      </li>
    </ul>
  </div>

  <div class="key-point">
    <strong>바이브 코딩에서 중요한 습관:</strong>
    “코드 작성 완료”를 작업 완료라고 생각하지 말고,
    가능한 범위에서 <strong>구현 → 테스트 → 실패하면 수정 → 다시 테스트</strong>까지
    하나의 작업으로 생각합니다.
  </div>

  <h3>10. Build</h3>

  <div class="concept">
    <div class="concept-title">📦 Build는 작성한 프로젝트가 실제로 실행 가능한 상태인지 확인하고 준비하는 과정입니다.</div>

    <p>
      웹 프로젝트에서는 여러 소스 파일을 실제 서비스에서 사용할 수 있는 형태로
      정리하고 변환하는 과정이 필요할 수 있습니다.
    </p>

    <p>
      Build가 실패한다면 화면이 얼핏 정상처럼 보여도
      프로젝트 내부에 오류가 남아 있을 가능성이 있습니다.
    </p>

    <div class="concept-example">
      입문자가 build 명령어를 외울 필요는 없습니다.<br><br>

      Codex에게
      <strong>“필요한 검사와 테스트를 실행하고 문제가 있다면 알려주세요.”</strong>
      라고 요청하는 것부터 시작하면 됩니다.
    </div>
  </div>

  <h3>11. Git</h3>

  <div class="concept">
    <div class="concept-title">↩️ Git은 개발 과정의 변경 기록을 남기고 되돌릴 수 있게 해줍니다.</div>

    <p>
      AI가 한 번에 여러 파일을 수정할 수 있기 때문에
      바이브 코딩에서는 오히려 변경 기록을 관리하는 것이 중요해질 수 있습니다.
    </p>

    <p>
      첫 수업에서 Git 명령어를 모두 배울 필요는 없습니다.
      우선 <strong>“작업 전후의 상태를 기록해서 문제가 생기면 이전으로 돌아갈 수 있다”</strong>
      정도만 이해하면 충분합니다.
    </p>
  </div>

  <div class="summary">
    <div class="summary-title">이 장에서 기억할 것</div>
    <p>
      프로젝트, 프론트엔드, 백엔드, API, 라이브러리, 데이터 저장,
      테스트 같은 기본 용어를 모두 전문적으로 알 필요는 없습니다.
    </p>
    <p>
      중요한 것은 <strong>AI가 말하는 내용을 대략 이해하고,
      이해되지 않는 순간 ChatGPT에게 다시 질문할 수 있는 것</strong>입니다.
    </p>
  </div>

<section class="chapter">
  <div class="chapter-number">Chapter 02</div>
  <h2>ChatGPT와 Codex는 서로 다른 일을 맡깁니다</h2>

  <p>
    바이브 코딩에서 모든 일을 하나의 AI에게 맡길 필요는 없습니다.
    오히려 역할을 나누면 훨씬 편하게 개발할 수 있습니다.
  </p>

  <div class="role-grid">
    <div class="role-card">
      <h3>💬 ChatGPT Web</h3>
      <p>
        개발 과정에서 <strong>생각하고 이해하고 결정하는 일</strong>에 사용합니다.
      </p>
      <ul>
        <li>아이디어 정리</li>
        <li>필요한 기능 결정</li>
        <li>모르는 개발 개념 질문</li>
        <li>기술 선택지 비교</li>
        <li>프로젝트 진행 순서 상담</li>
        <li>Codex에게 전달할 프롬프트 작성</li>
      </ul>
    </div>

    <div class="role-card">
      <h3>🤖 Codex</h3>
      <p>
        결정된 내용을 바탕으로 <strong>실제 프로젝트에서 작업하는 일</strong>에 사용합니다.
      </p>
      <ul>
        <li>프로젝트 구조 조사</li>
        <li>관련 파일 찾기</li>
        <li>코드 작성 및 수정</li>
        <li>리팩터링</li>
        <li>테스트 작성 및 실행</li>
        <li>오류 조사 및 수정</li>
        <li>프로젝트 문서 갱신</li>
      </ul>
    </div>
  </div>

  <div class="key-point">
    <strong>가장 중요한 개발 습관:</strong><br>
    Codex에게 무엇을 시켜야 할지 모르겠다면
    억지로 개발 지식을 추측하지 말고 먼저 ChatGPT와 상담합니다.
  </div>

  <h3>ChatGPT → Codex 기본 흐름</h3>

  <ol class="flow">
    <li>
      <span class="flow-title">만들고 싶은 것을 설명합니다.</span>
      ChatGPT와 기능, 화면, 사용 방법을 정리합니다.
    </li>

    <li>
      <span class="flow-title">모르는 기술을 질문합니다.</span>
      여러 선택지가 있다면 장단점을 비교하고 필요한 결정을 내립니다.
    </li>

    <li>
      <span class="flow-title">Codex용 작업 프롬프트를 만듭니다.</span>
      결정된 요구사항을 실제 개발 에이전트가 이해하기 좋은 형태로 정리합니다.
    </li>

    <li>
      <span class="flow-title">Codex에게 실제 개발을 맡깁니다.</span>
      Codex가 프로젝트를 살펴보고 필요한 파일을 수정합니다.
    </li>

    <li>
      <span class="flow-title">결과를 확인하고 수정 요청을 합니다.</span>
      사용하면서 이상한 부분이나 원하는 변경사항을 자연어로 설명합니다.
    </li>

    <li>
      <span class="flow-title">테스트하고 중요한 결정은 프로젝트에 남깁니다.</span>
      다음 작업에서도 같은 원칙을 사용할 수 있도록 프로젝트 문서에 기록합니다.
    </li>
  </ol>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">처음 아이디어를 개발 계획으로 바꾸기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">나는 개발 입문자이고, AI와 함께 웹 애플리케이션을 만들려고 해.

[만들고 싶은 서비스]
나는 개인 일정과 할 일을 관리할 수 있는 애플리케이션을 만들고 싶어.

[현재 생각하고 있는 핵심 기능]
- 일정을 추가할 수 있다.
- 일정을 수정하고 삭제할 수 있다.
- 할 일을 완료 처리할 수 있다.
- 오늘 해야 할 일만 따로 볼 수 있다.
- 새로고침하거나 다시 접속해도 데이터가 유지되어야 한다.

[현재 상황]
- 아직 구체적인 기술 구조는 결정하지 않았다.
- 개발에 필요한 기술 용어는 잘 모를 수 있다.
- 실제 코딩은 Codex에게 맡길 예정이다.

다음 순서로 도와줘.

1. 내가 만들려는 서비스를 한 문단으로 명확하게 정의해줘.
2. 지금 적은 기능을 기준으로 최소 기능 제품(MVP)에 반드시 필요한 기능과 나중에 추가해도 되는 기능을 나눠줘.
3. 개발을 시작하기 전에 내가 결정해야 하는 사항을 질문 형태로 정리해줘.
4. 각 질문에서 기술적인 선택지가 있다면 입문자도 이해할 수 있도록 차이를 설명해줘.
5. 아직 결정할 필요가 없는 기술적인 세부사항은 제외해줘.
6. 기능을 어떤 순서로 구현하면 안전하고 이해하기 쉬운지 개발 순서를 제안해줘.
7. 마지막에는 지금까지 결정된 내용을 Codex에게 전달할 수 있는 개발 작업 명세의 초안을 만들어줘.

내가 코드를 직접 작성하는 방법보다,
무엇을 결정하고 어떤 순서로 Codex에게 일을 맡겨야 하는지를 중심으로 설명해줘.</pre>

    <div class="prompt-purpose">
      아이디어만 있는 상태에서 바로 코드를 만들기보다,
      먼저 무엇을 만들 것인지 정리하고 개발 순서를 잡는 데 사용합니다.
    </div>
  </div>

  <div class="summary">
    <div class="summary-title">핵심 개발 루프</div>
    <p>
      <strong>모름 → ChatGPT와 상담 → 결정 → Codex에게 실행 → 결과 확인 → 다시 상담</strong>
    </p>
    <p>
      이 흐름을 익히면 처음 보는 기술이나 기능이 등장해도
      모든 내용을 미리 공부한 뒤 개발을 시작할 필요가 없습니다.
    </p>

<section class="chapter">
  <div class="chapter-number">Chapter 03</div>
  <h2>`.md` 파일은 AI에게 프로젝트의 기억을 남기는 방법입니다</h2>

  <p>
    Codex는 현재 프로젝트의 소스코드를 직접 읽고 작업할 수 있습니다.
    하지만 <strong>코드만 보고는 알기 어려운 내용</strong>도 있습니다.
  </p>

  <p>
    예를 들어 아래와 같은 내용입니다.
  </p>

  <ul>
    <li>왜 이 기능을 이런 방식으로 만들었는가?</li>
    <li>앞으로 어떤 개발 방식을 계속 유지해야 하는가?</li>
    <li>어떤 라이브러리는 변경하면 안 되는가?</li>
    <li>어떤 화면이나 기능은 서로 어떤 관계를 가지고 있는가?</li>
    <li>현재 해결하지 않은 문제는 무엇인가?</li>
    <li>새로운 기능을 만들 때 반드시 확인해야 할 것은 무엇인가?</li>
  </ul>

  <p>
    이런 내용을 프로젝트 안의 문서로 남겨두면,
    다음 작업에서 Codex가 다시 읽고 참고할 수 있습니다.
  </p>

  <div class="key-point">
    <strong>쉽게 생각하면:</strong><br>
    채팅은 지금 하고 있는 대화이고,
    <code>.md</code> 파일은 프로젝트 안에 남겨두는
    <strong>장기적인 설명서와 개발 규칙</strong>입니다.
  </div>

  <h3>1. Markdown 파일이 무엇인가요?</h3>

  <div class="concept">
    <div class="concept-title">📝 `.md`는 글을 저장하는 간단한 문서 파일입니다.</div>

    <p>
      Markdown은 복잡한 문서 프로그램이 아니라,
      일반 텍스트에 제목, 목록, 코드 등의 간단한 형식을 추가할 수 있는 방식입니다.
    </p>

    <p>
      예를 들어 아래와 같이 작성할 수 있습니다.
    </p>

    <div class="file-tree"># 프로젝트 개요

## 주요 기능

- 일정 추가
- 일정 수정
- 일정 삭제
- 완료 처리

## 개발 원칙

- 기존 UI 스타일을 유지한다.
- 새로운 라이브러리는 필요한 경우에만 추가한다.
- 기능 수정 후 관련 테스트를 실행한다.</div>

    <p>
      입문자가 Markdown 문법을 모두 외울 필요는 없습니다.
      문서 내용이 필요하면 <strong>Codex에게 직접 작성하거나 수정해 달라고 요청</strong>하면 됩니다.
    </p>
  </div>

  <div class="tip">
    <span class="box-title">💡 직접 `.md`를 작성하지 않아도 됩니다</span>
    “지금까지 결정한 내용을 적절한 프로젝트 문서에 정리해 주세요.”
    라고 요청하면 Codex가 현재 프로젝트를 확인한 뒤 필요한 문서를 만들거나 수정할 수 있습니다.
  </div>

  <h3>2. 왜 채팅만 사용하면 안 될까요?</h3>

  <div class="concept">
    <div class="concept-title">💬 채팅은 개발 과정에 유용하지만 프로젝트의 기준 문서와는 역할이 다릅니다.</div>

    <p>
      ChatGPT와 긴 대화를 하면서 매우 좋은 개발 전략을 정했다고 생각해 봅시다.
    </p>

    <p>
      하지만 중요한 결정이 채팅 안에만 존재한다면
      며칠 뒤 다른 Codex 작업을 시작했을 때
      그 결정이 프로젝트 안에 명확하게 남아 있지 않을 수 있습니다.
    </p>

    <div class="concept-example">
      예를 들어 ChatGPT와 다음과 같이 결정했다고 가정해 봅시다.<br><br>

      “사용자의 일정은 당분간 서버가 아니라 브라우저에 저장한다.”<br>
      “새로운 상태 관리 라이브러리는 추가하지 않는다.”<br>
      “현재 디자인을 유지하고 기능만 확장한다.”<br><br>

      이런 내용이 중요한 결정이라면
      채팅에만 남겨두기보다 프로젝트 문서에도 기록해 두는 것이 좋습니다.
    </div>
  </div>

  <div class="key-point">
    <strong>좋은 흐름:</strong><br>
    ChatGPT와 상담 → 중요한 결정 → 프로젝트 문서에 기록 → Codex가 이후 작업에서 참고
  </div>

  <h3>3. `AGENTS.md`는 무엇인가요?</h3>

  <div class="concept">
    <div class="concept-title">🤖 `AGENTS.md`는 Codex가 프로젝트에서 일할 때 따라야 할 핵심 지침입니다.</div>

    <p>
      모든 세부 내용을 <code>AGENTS.md</code>에 길게 적을 필요는 없습니다.
      오히려 중요한 규칙과 관련 문서의 위치를 알려주는
      <strong>프로젝트 작업 가이드</strong>에 가깝게 사용하는 것이 좋습니다.
    </p>

    <div class="concept-example">
      예를 들어 다음과 같은 내용을 넣을 수 있습니다.<br><br>

      • 작업하기 전에 관련 <code>docs/</code> 문서를 확인한다.<br>
      • 기존 프레임워크와 핵심 라이브러리를 임의로 변경하지 않는다.<br>
      • 새로운 기능을 만들기 전에 기존 구현을 먼저 확인한다.<br>
      • 임시방편이나 불필요한 하드코딩으로 문제를 해결하지 않는다.<br>
      • 기능을 수정한 뒤 관련 테스트를 실행한다.<br>
      • 배포나 데이터 삭제는 명시적인 요청 없이 진행하지 않는다.
    </div>
  </div>

  <div class="warning">
    <span class="box-title">⚠️ `AGENTS.md`에 모든 것을 넣지는 않습니다</span>
    프로젝트가 커지면 기능 설명, 데이터 구조, 화면 설계, 테스트 정책까지
    한 파일에 모두 넣기 어려워집니다.
    따라서 <code>AGENTS.md</code>에는 핵심 규칙을 두고,
    자세한 내용은 <code>docs/</code>의 다른 문서로 나누는 것이 좋습니다.
  </div>

  <h3>4. `docs/` 폴더에는 무엇을 넣나요?</h3>

  <div class="concept">
    <div class="concept-title">📚 `docs/`는 프로젝트에 대한 자세한 설명을 나누어 저장하는 공간으로 사용할 수 있습니다.</div>

    <p>
      파일 이름은 프로젝트에 맞게 자유롭게 정할 수 있습니다.
      Codex가 이해하기 쉬운 이름을 사용하면 됩니다.
    </p>

    <div class="file-tree">AGENTS.md

    <code>project-overview.md</code> 정도만 있어도 시작할 수 있습니다.
    필요해질 때 Codex와 상담하면서 문서를 추가하면 됩니다.
  </div>

  <h3>5. 문서에는 무엇을 반드시 적어야 하나요?</h3>

  <p>
    프로젝트마다 필요한 문서는 다르지만,
    처음 시작할 때는 다음 네 가지가 있으면 충분합니다.
  </p>

  <div class="minimum-list">
    <div class="minimum-item">
      <strong>① 프로젝트 목적</strong>
      무엇을 만드는 앱인지, 사용자는 누구인지
    </div>

    <div class="minimum-item">
      <strong>② 핵심 기능</strong>
      반드시 제공해야 하는 기능과 주요 사용자 흐름
    </div>

    <div class="minimum-item">
      <strong>③ 개발 원칙</strong>
      기존 기술 유지, 불필요한 라이브러리 추가 금지, 안전한 수정 등
    </div>

    <div class="minimum-item">
      <strong>④ 완료 기준</strong>
      기능 구현뿐 아니라 테스트와 실제 동작 확인까지 포함할 것인지
    </div>
  </div>

  <h3>6. 기존 프로젝트라면 현재 상태와 앞으로의 원칙을 구분합니다</h3>

  <div class="concept">
    <div class="concept-title">🔍 현재 코드가 그렇다고 해서 반드시 좋은 원칙인 것은 아닙니다.</div>

    <p>
      특히 여러 번 AI에게 수정시키면서 만들어진 프로젝트라면
      서로 다른 개발 방식이 섞여 있을 수 있습니다.
    </p>

    <p>
      이때 현재 코드에 가장 많이 등장하는 방식을
      자동으로 “프로젝트 표준”이라고 판단하게 만들면 문제가 생길 수 있습니다.
    </p>

    <p>
      따라서 문서에서는 다음 세 가지를 구분하는 방법이 유용합니다.
    </p>

    <div class="concept-example">
      <strong>As-Is</strong><br>
      현재 프로젝트가 실제로 어떻게 동작하고 있는가?<br><br>

      <strong>Technical Debt</strong><br>
      현재 알고 있는 중복, 불일치, 임시 구현, 개선이 필요한 부분은 무엇인가?<br><br>

      <strong>To-Be</strong><br>
      앞으로 새로운 기능을 만들 때 어떤 방식을 기준으로 사용할 것인가?
    </div>
  </div>

  <div class="key-point">
    <strong>중요:</strong>
    중요한 구조 변경은 Codex가 혼자 결정하도록 두기보다
    선택지를 정리하게 한 뒤 ChatGPT와 상담하고 사용자가 결정하는 것이 좋습니다.
  </div>

  <h3>7. 처음 프로젝트 문서를 만들 때 사용하는 프롬프트</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">새 프로젝트의 기본 문서 구성 만들기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트를 먼저 확인한 뒤,
앞으로 AI 개발 에이전트가 일관된 방식으로 작업할 수 있도록
프로젝트 문서 구조를 만들어줘.

[목표]
프로젝트의 중요한 결정과 개발 원칙이 일회성 채팅에만 남지 않고,
앞으로 다른 Codex 작업에서도 참고할 수 있도록 문서화하고 싶다.

[작업 내용]

1. 현재 repository의 구조와 주요 기술 구성을 먼저 확인해줘.

2. 프로젝트 루트에 `AGENTS.md`가 없다면 생성하고,
   이미 존재한다면 현재 내용을 보존하면서 필요한 내용을 정리해줘.

3. `AGENTS.md`는 너무 길게 만들지 말고,
   앞으로 Codex가 작업할 때 반드시 따라야 할 핵심 규칙과
   관련 문서의 위치를 안내하는 역할을 하게 해줘.

4. 프로젝트의 자세한 내용은 `docs/` 아래의 Markdown 문서로 분리해줘.
   필요한 문서의 이름과 개수는 현재 프로젝트 규모에 맞게 판단해도 된다.

5. 문서에는 최소한 다음 내용을 다룰 수 있도록 해줘.
   - 프로젝트 목적
   - 주요 기능
   - 현재 기술 구조
   - 데이터 저장 방식
   - UI 또는 사용자 경험에서 유지해야 할 중요한 원칙
   - 테스트 및 작업 완료 기준
   - 알려진 기술 부채 또는 불일치

6. 현재 구현된 방식이 많다는 이유만으로
   자동으로 프로젝트의 공식 개발 원칙으로 만들지 마.
   기존 구현과 앞으로 권장할 방식을 구분해줘.

7. 중요한 구조적 선택이 필요한 경우에는
   임의로 하나를 선택해서 공식 규칙으로 확정하지 말고,
   선택지와 장단점을 정리해서 내가 결정할 수 있도록 알려줘.

[제약 사항]

- 기존 프레임워크나 핵심 라이브러리를 변경하지 마.
- 이 작업에서는 기능을 새로 만들거나 UI를 변경하지 마.
- 기존 코드의 동작을 변경하지 마.
- 문서를 만들기 위해 불필요한 리팩터링을 진행하지 마.

[완료 후 보고]

작업이 끝나면 다음 내용을 짧게 정리해줘.

- 새로 생성하거나 수정한 문서
- 각 문서의 역할
- 앞으로 내가 결정해야 할 중요한 사항
- 현재 프로젝트에서 발견한 주요 기술 부채</pre>

    <div class="prompt-purpose">
      기존 프로젝트를 처음 Codex에 맡길 때,
      바로 기능을 추가하기 전에 프로젝트의 기본 기억과 작업 규칙을 만드는 프롬프트입니다.
    </div>
  </div>

  <h3>8. 새로운 결정을 문서에 반영할 때</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">새로운 개발 결정을 프로젝트에 기록하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">이번 작업 과정에서 다음과 같은 결정을 내렸다.

[결정 내용]
- 새로 추가하는 데이터는 우선 브라우저 로컬 저장소에 저장한다.
- 현재 프로젝트의 상태 관리 방식은 유지한다.
- 새로운 상태 관리 라이브러리는 추가하지 않는다.
- 나중에 백엔드를 추가할 수 있도록 데이터 접근 로직은 UI와 지나치게 결합하지 않는다.

이 내용이 앞으로의 개발에서도 유지되어야 하는 중요한 결정인지 확인해줘.

중요한 프로젝트 원칙에 해당한다면
현재 `AGENTS.md`와 `docs/` 구조를 확인한 뒤
가장 적절한 문서에 반영해줘.

같은 내용을 여러 문서에 불필요하게 반복하지 말고,
`AGENTS.md`에는 꼭 필요한 상위 규칙이나 관련 문서 링크만 유지해줘.

기존 문서와 이번 결정이 충돌한다면
임의로 기존 내용을 덮어쓰지 말고 충돌 내용을 먼저 알려줘.</pre>

    <div class="prompt-purpose">
      ChatGPT와 상담해서 결정한 내용을
      이후 Codex 작업에서도 계속 사용할 수 있도록 프로젝트에 남기는 프롬프트입니다.
    </div>
  </div>

  <h3>9. 문서가 너무 복잡해졌을 때</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">프로젝트 문서 정리하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트의 `AGENTS.md`와 `docs/` 문서를 검토해줘.

목표는 문서의 양을 늘리는 것이 아니라,
앞으로 Codex가 중요한 정보를 빠르게 찾을 수 있도록 정리하는 것이다.

다음 기준으로 검토해줘.

1. 서로 중복된 설명이 있는지 확인해줘.
2. 이미 현재 코드와 맞지 않는 오래된 내용이 있는지 확인해줘.
3. 하나의 문서가 지나치게 많은 역할을 하고 있다면 적절히 분리해줘.
4. 반대로 내용이 지나치게 잘게 나뉘어 찾기 어려우면 통합해줘.
5. `AGENTS.md`는 프로젝트 전체의 핵심 규칙과 문서 안내 중심으로 간결하게 유지해줘.
6. 현재 동작과 앞으로의 권장 원칙을 혼동하지 않도록 정리해줘.
7. 확실하지 않은 내용은 임의로 삭제하거나 수정하지 말고 보고해줘.

문서 정리 과정에서 애플리케이션 소스코드의 동작은 변경하지 마.

완료 후 어떤 문서를 왜 수정했는지만 간단하게 설명해줘.</pre>

    <div class="prompt-purpose">

<section class="chapter">

  <h2>개발을 시작하기 전에 필요한 Minimum Requirement</h2>

  <p>
    프로젝트를 시작할 때부터 완벽한 기획서와 설계 문서를 만들 필요는 없습니다.
    하지만 아무것도 결정하지 않은 상태에서
    바로 “앱 만들어줘”라고 하면 AI도 많은 부분을 임의로 결정해야 합니다.
  </p>

  <p>
    따라서 최소한 아래 내용 정도는 먼저 정리하는 것이 좋습니다.
  </p>

  <div class="minimum-list">
    <div class="minimum-item">
      <strong>① 무엇을 만드는가?</strong>
      서비스의 목적을 한두 문장으로 설명할 수 있어야 합니다.
    </div>

    <div class="minimum-item">
      <strong>② 누가 사용하는가?</strong>
      나 혼자 사용하는지, 여러 사용자가 사용하는지 등을 정합니다.
    </div>

    <div class="minimum-item">
      <strong>③ 핵심 기능은 무엇인가?</strong>
      처음부터 반드시 동작해야 하는 기능을 정합니다.
    </div>

    <div class="minimum-item">
      <strong>④ 데이터가 필요한가?</strong>
      새로고침 후에도 정보를 남길지, 여러 기기에서 공유할지 등을 생각합니다.
    </div>

    <div class="minimum-item">
      <strong>⑤ 화면은 어떻게 사용할 것인가?</strong>
      사용자가 어떤 순서로 버튼을 누르고 기능을 사용하는지 생각합니다.
    </div>

    <div class="minimum-item">
      <strong>⑥ 무엇을 변경하면 안 되는가?</strong>
      기존 프로젝트라면 유지해야 할 디자인, 라이브러리, 데이터 형식 등을 알려줍니다.
    </div>

    <div class="minimum-item">
      <strong>⑦ 언제 완료라고 판단할 것인가?</strong>
      기능 구현, 테스트, 실제 사용 확인 등 완료 기준을 정합니다.
    </div>
  </div>

  <div class="key-point">
    이 내용을 처음부터 혼자 결정할 필요도 없습니다.
    <strong>아이디어만 가지고 ChatGPT에게 질문을 받아가며 하나씩 결정</strong>하면 됩니다.
  </div>

  <h3>프로젝트를 시작할 때 사용하는 기본 상담 프롬프트</h3>

  <div class="prompt-card">
    <div class="prompt-header">

      <span class="prompt-target">ChatGPT</span>

    <pre class="prompt-body">나는 개발 입문자이고,

현재 만들고 싶은 서비스는 다음과 같다.

[서비스 아이디어]
나는 A라는 애플리케이션을 만들고 싶다.

[현재 생각한 핵심 기능]
- B 기능
- C 기능
- D 기능

아직 개발 구조나 세부 기술은 결정하지 않았다.

내가 바로 구현 방법을 선택하도록 요구하지 말고,
먼저 이 서비스를 실제 개발 가능한 수준의 요구사항으로 정리할 수 있도록 도와줘.

다음 순서로 진행해줘.

1. 내가 만들려는 서비스의 목적과 핵심 사용 흐름을 정리해줘.

2. 현재 기능 중
   - 첫 버전에 반드시 필요한 기능
   - 나중에 추가해도 되는 기능
   을 구분해줘.

3. 개발을 시작하기 전에 내가 결정해야 할 사항을 질문해줘.
   질문은 한꺼번에 너무 많이 하지 말고,
   실제 개발 방향을 크게 바꾸는 중요한 결정부터 우선순위를 정해줘.

4. 기술적인 선택이 필요하다면
   각각의 방법을 비전공자도 이해할 수 있는 수준으로 설명해줘.
   단순히 전문 용어를 나열하지 말고
   실제로 내 앱에서 어떤 차이가 발생하는지를 중심으로 설명해줘.

5. 불필요하게 복잡한 기술이나
   지금 규모에서 필요하지 않은 구조는 추천하지 마.

6. 내가 답변한 내용을 바탕으로
   기능 요구사항과 개발 순서를 점점 구체화해줘.

7. 충분히 결정되었다고 판단되면
   마지막에 Codex에게 전달할 수 있는 작업 프롬프트를 만들어줘.

Codex용 최종 프롬프트에는 최소한 다음 내용을 포함해줘.

- 프로젝트 목표
- 구현할 기능
- 사용자가 경험해야 하는 동작
- 유지해야 할 기존 구조 또는 제약사항
- Codex가 먼저 확인해야 할 내용
- 테스트 및 검증 기준
- 작업 완료 후 보고해야 할 내용

내가 이해하지 못한 내용을 임의로 결정하도록 유도하지 말고,
중요한 선택은 내가 판단할 수 있도록 먼저 설명해줘.</pre>

    <div class="prompt-purpose">

  <h2>이제 Codex에게 실제 개발을 맡겨봅니다</h2>

  <p>
    ChatGPT와 상담해서 무엇을 만들지 결정했다면,

      기존 기술과 UI 구조는 가능한 한 유지하고,

[목표]
사용자가 자신의 일정을 추가하고 관리할 수 있는 기능을 만들고 싶다.

[필요한 기능]
- 새로운 일정을 추가할 수 있다.
- 기존 일정을 수정할 수 있다.
- 일정을 삭제할 수 있다.

1. 사용자가 일정 추가 버튼을 누른다.

3. 저장하면 일정 목록에 바로 나타난다.
4. 기존 일정을 선택하면 수정할 수 있다.
5. 삭제하면 목록에서 제거된다.
6. 페이지를 새로고침해도 저장한 일정이 남아 있어야 한다.

- 작업 전에 `AGENTS.md`와 관련 `docs/` 문서를 확인해줘.

- 새로운 핵심 라이브러리는 명확한 필요가 없다면 추가하지 마.
- 기존 데이터 구조와 UI를 불필요하게 변경하지 마.
- 이미 존재하는 공통 로직이 있다면 먼저 재사용할 수 있는지 확인해줘.
- 임시방편이나 하드코딩으로 기능을 구현하지 마.

[작업 방식]
- 먼저 관련 코드를 조사해줘.
- 현재 구조와 충돌하지 않는 범위에서 구현해줘.
- 필요한 부분만 수정하고 관련 없는 대규모 리팩터링은 하지 마.
- 구현 과정에서 중요한 구조적 결정이 필요하면 임의로 크게 변경하지 말고 알려줘.

[검증]
- 현재 프로젝트에 적절한 테스트 체계가 있다면 관련 테스트를 추가하거나 수정해줘.
- 기존 테스트도 확인해서 이번 변경으로 기존 기능이 깨지지 않았는지 검사해줘.
- TypeScript, lint, 기타 프로젝트의 기본 검사 수단이 있다면 적절하게 실행해줘.

[완료 후]
다음 내용을 간단하게 보고해줘.
- 구현한 기능
- 주요 변경 파일
- 테스트 및 검사 결과

  <h3>2. 프롬프트를 직접 만들기 어렵다면 ChatGPT에게 만들어 달라고 합니다</h3>

  <p>
    개발 입문자라면 기능은 생각났지만
    Codex에게 어떤 수준으로 설명해야 할지 모르는 경우가 많습니다.

    <strong>Codex가 작업하기 좋은 형태의 프롬프트로 변환</strong>해 달라고 요청할 수 있습니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">내 아이디어를 Codex용 개발 프롬프트로 바꾸기</span>
      <span class="prompt-target">ChatGPT</span>

    <pre class="prompt-body">나는 Codex를 이용해서 현재 프로젝트에 새로운 기능을 추가하려고 해.

내가 원하는 기능은 다음과 같아.

[원하는 기능]
사용자가 일정마다 중요도를 설정할 수 있었으면 좋겠어.

중요도는
- 높음
- 보통
- 낮음

세 단계면 충분해.

일정 목록에서도 중요도를 쉽게 확인할 수 있었으면 좋겠고,
기존 일정 수정 화면에서도 중요도를 변경할 수 있었으면 좋겠어.

나는 구체적으로 어떤 파일이나 코드를 수정해야 하는지는 모르고,
그 부분은 Codex가 현재 repository를 조사해서 판단하게 하고 싶어.

다음 조건을 반영해서 Codex용 프롬프트를 작성해줘.

1. 먼저 현재 프로젝트 구조와 기존 일정 기능을 조사하게 해줘.
2. 기존 프레임워크와 핵심 라이브러리를 불필요하게 변경하지 않게 해줘.
3. 현재 데이터 구조와 저장 방식에 미치는 영향을 먼저 확인하게 해줘.
4. 기존 UI 스타일을 최대한 유지하게 해줘.
5. 필요한 부분만 수정하도록 하고 대규모 리팩터링은 피하게 해줘.
6. 기존 일정 데이터가 깨지지 않도록 고려하게 해줘.
7. 구현 후 관련 테스트와 regression을 확인하게 해줘.
8. 중요한 구조 변경이 필요하면 임의로 진행하지 않고 먼저 알려주게 해줘.
9. 작업 완료 후 변경사항과 내가 직접 확인할 부분을 요약하게 해줘.

프롬프트는 단순한 한두 문장보다
실제 개발 에이전트에게 업무를 맡길 수 있을 정도로
구조적이고 명확하게 작성해줘.</pre>

    <div class="prompt-purpose">
      기술 구현 방법을 몰라도
      원하는 사용자 경험만 설명해서 전문적인 Codex 작업 지시를 만드는 방법입니다.
    </div>
  </div>

  <h3>3. 작은 UI 수정은 훨씬 간단하게 요청해도 됩니다</h3>

  <p>
    모든 작업에 긴 프롬프트가 필요한 것은 아닙니다.

  <div class="concept">
    <div class="concept-title">🎨 화면을 보고 느낀 문제를 그대로 설명할 수 있습니다.</div>

    <div class="concept-example">
      “상단 탭이 너무 오른쪽에 있어요.”<br>
      “카드 사이 간격을 조금 더 넓혀 주세요.”<br>
      “모바일에서 저장 버튼이 너무 크게 보여요.”<br>
      “전체 디자인은 그대로 두고 제목 크기만 조금 줄여 주세요.”

  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">현재 화면의 일부만 수정하기</span>
      <span class="prompt-target">Codex</span>

    <pre class="prompt-body">현재 화면의 전체 디자인은 마음에 들어서 그대로 유지하고 싶다.

다만 상단에 있는 탭 영역이 현재보다 조금 왼쪽에 위치했으면 좋겠다.

다음 조건으로 수정해줘.

- 전체 레이아웃 구조는 변경하지 마.
- 탭의 기능이나 텍스트는 변경하지 마.
- 다른 화면의 위치까지 함께 바뀌지 않도록 해줘.
- 새로운 UI 라이브러리를 추가하지 마.
- 현재 스타일링 방식을 그대로 사용해줘.
- 필요한 CSS 또는 관련 UI 코드만 최소한으로 수정해줘.

수정 후 어떤 부분을 변경했는지 간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      눈에 보이는 작은 UI 문제는
      내부 코드를 몰라도 원하는 결과와 변경 범위만 정확하게 말하면 됩니다.

[새 기능]
완료된 일정만 따로 확인할 수 있는 필터를 추가해줘.

[현재 동작]
현재 일정 목록에는 완료된 일정과 완료되지 않은 일정이 함께 표시된다.
기존의 일정 추가, 수정, 삭제, 완료 처리 기능은 현재 방식 그대로 유지하고 싶다.

[원하는 동작]
- 기본 상태에서는 기존과 동일하게 모든 일정이 보인다.
- 사용자가 "완료됨" 필터를 선택하면 완료된 일정만 보인다.
- 필터를 다시 해제하면 전체 일정으로 돌아온다.
- 필터링 때문에 원본 일정 데이터가 변경되면 안 된다.

[제약사항]
- 작업 전에 현재 일정 목록과 상태 관리 방식을 확인해줘.
- 기존 컴포넌트나 상태 관리 구조를 불필요하게 다시 작성하지 마.
- 같은 기능을 하는 별도의 데이터 구조를 중복해서 만들지 마.
- 기존 저장 데이터 형식을 변경하지 마.
- 기존 UI 스타일을 유지해줘.
- 필요한 부분만 점진적으로 수정해줘.

[검증]
- 전체 일정 보기
- 완료된 일정 필터링
- 필터 해제
- 일정 추가/삭제/완료 처리 후 필터가 정상적으로 동작하는지

위 흐름을 확인할 수 있는 적절한 테스트가 있다면 추가하거나 수정해줘.
기존 테스트도 실행해서 regression이 없는지 확인해줘.

작업 후에는
무엇을 변경했고 어떤 검증을 했는지 짧게 정리해줘.</pre>

    <div class="prompt-purpose">

  <h3>5. 기능을 여러 단계로 나누어 개발할 수도 있습니다</h3>

      1. 로그인 화면 만들기<br>
      2. 인증 방식 연결하기<br>
      3. 로그인 상태 유지하기<br>
      4. 로그아웃 만들기<br>

      6. 전체 흐름 테스트하기
    </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">큰 기능을 구현하기 전에 작업 단위로 나누기</span>

[기능]
사용자가 회원가입하고 로그인한 뒤,
자신의 데이터를 여러 기기에서 사용할 수 있게 하고 싶다.

나는 개발 입문자이고 실제 구현은 Codex에게 맡길 예정이다.

이 기능을 한 번에 Codex에게 전부 구현시키기보다
안전하게 여러 단계로 나누어 진행하고 싶다.

다음 기준으로 개발 계획을 만들어줘.

1. 기능을 서로 검증 가능한 작은 단계로 나눠줘.
2. 각 단계가 끝났을 때 무엇이 동작해야 하는지 알려줘.
3. 이전 단계가 정상적으로 완료되어야 다음 단계로 넘어갈 수 있게 순서를 정해줘.
4. 데이터 손실이나 보안 문제처럼 특히 조심해야 하는 부분을 표시해줘.
5. 각 단계에서 내가 결정해야 할 기술적인 선택이 있다면 먼저 알려줘.
6. 지금 단계에서 불필요하게 복잡한 기능은 나중 단계로 분리해줘.
7. 각 단계마다 Codex에게 전달할 수 있는 작업 요청의 핵심 내용을 정리해줘.

코드를 직접 작성하지 말고,
전체 기능을 어떻게 나누어 Codex에게 맡길지를 중심으로 설명해줘.</pre>

    <div class="prompt-purpose">
      복잡한 기능을 한 번의 거대한 AI 작업으로 만들지 않고,

[Codex의 설명]
여기에 Codex가 보낸 내용을 그대로 붙여 넣기

내가 이 선택을 이해하고 결정할 수 있도록 도와줘.

다음 순서로 설명해줘.

1. Codex가 지금 왜 이 선택을 요구하고 있는지 설명해줘.
2. 각각의 방법이 실제 내 앱에서 어떤 차이를 만드는지 설명해줘.
3. 구현 난이도, 유지보수, 확장성, 데이터 안정성 등 중요한 차이가 있다면 비교해줘.
4. 지금 규모의 프로젝트에서는 어떤 선택이 불필요하게 복잡할 수 있는지도 알려줘.
5. 나중에 다른 방법으로 변경하기 어려운 결정인지 알려줘.
6. 내가 선택하기 위해 추가로 알아야 할 정보가 있다면 질문해줘.
7. 충분한 정보가 있다면 추천안을 제시하되,

내가 선택한 이후에는
그 결정을 Codex에게 전달하기 위한 명확한 프롬프트도 만들어줘.</pre>

  <h2>한 번에 완벽하게 만들려고 하지 않습니다</h2>

  <p>
    AI가 코드를 빠르게 만들 수 있다고 해서
    첫 번째 요청에서 완벽한 결과가 나오는 것은 아닙니다.
  </p>

  <p>
    실제 바이브 코딩에서는
    <strong>만들기 → 확인하기 → 문제를 설명하기 → 다시 수정하기</strong>를
    반복하는 과정이 자연스럽습니다.
  </p>

  <div class="key-point">
    처음부터 완벽한 프롬프트를 만드는 것이 목표가 아닙니다.<br>
    <strong>현재 결과를 보고 다음 작업을 정확하게 전달하는 능력</strong>이 더 중요합니다.
  </div>

  <h3>1. 화면은 동작하지만 마음에 들지 않을 때</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">기존 기능은 유지하고 사용감만 개선하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 기능 자체는 정상적으로 동작하고 있으므로
기능 로직은 변경하지 않았으면 좋겠다.

다만 실제로 사용해보니 다음 부분이 마음에 들지 않는다.

[현재 불편한 점]
- 일정 카드의 높이가 너무 커서 한 화면에 보이는 정보가 적다.
- 완료 버튼이 다른 버튼과 비슷해서 빠르게 찾기 어렵다.
- 카드 사이의 간격이 약간 넓게 느껴진다.

[원하는 방향]
- 현재 디자인 스타일은 유지한다.
- 화면을 완전히 다시 디자인하지 않는다.
- 카드의 정보 구조는 그대로 유지한다.
- 조금 더 compact하게 보이도록 조정한다.
- 완료 기능은 현재보다 쉽게 찾을 수 있게 한다.

관련 UI 코드를 먼저 확인하고,
기존 동작에 영향을 주지 않는 범위에서 필요한 스타일과 레이아웃만 수정해줘.

새로운 UI framework나 디자인 라이브러리는 추가하지 마.

수정이 끝나면
내가 실제 화면에서 확인해야 할 부분을 간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      기능은 정상인데 디자인이나 사용감만 조금씩 바꾸고 싶을 때 사용합니다.
    </div>
  </div>

  <h3>2. 원하는 기능을 말로 정확하게 설명하기 어려울 때</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">막연한 요구사항을 개발 요구사항으로 정리하기</span>
      <span class="prompt-target">ChatGPT</span>
    </div>

    <pre class="prompt-body">내가 원하는 기능의 느낌은 알고 있지만
개발 요구사항으로 정확하게 설명하기 어렵다.

[내가 원하는 것]
일정이 많아졌을 때 중요한 일정이 눈에 잘 들어왔으면 좋겠어.
그렇다고 화면이 너무 화려하거나 복잡해지는 것은 싫어.

현재 앱은 전체적으로 단순한 디자인이고
그 느낌은 유지하고 싶어.

이 요구사항을 Codex에게 전달하기 전에 정리해줘.

1. 내가 실제로 원하는 사용자 경험이 무엇인지 구체적인 요구사항으로 바꿔줘.
2. 여러 구현 방법이 있다면 사용자 경험 기준으로 몇 가지 선택지를 제안해줘.
3. 불필요하게 기능을 추가하거나 디자인을 크게 변경하지 않는 방법을 우선해줘.
4. 내가 결정해야 할 부분이 있다면 질문해줘.
5. 충분히 결정된 후에는
   현재 프로젝트를 먼저 조사하고 기존 디자인을 유지하도록 하는
   Codex용 개발 프롬프트를 만들어줘.</pre>

    <div class="prompt-purpose">
      “뭔가 이런 느낌이었으면 좋겠다”처럼 애매한 생각을
      AI와 대화하면서 실제 요구사항으로 바꾸는 방법입니다.
    </div>
  </div>

  <h3>3. 작업 결과가 예상과 다르면 바로 다시 지시합니다</h3>

  <div class="concept">
    <div class="concept-title">🔁 수정 요청도 개발의 일부입니다.</div>

    <p>
      Codex가 처음 만든 결과가 마음에 들지 않는다고 해서
      프로젝트를 처음부터 다시 만들 필요는 없습니다.
    </p>

    <p>
      현재 결과에서 무엇이 마음에 들지 않는지,
      무엇은 그대로 유지하고 싶은지 알려주면 됩니다.
    </p>

    <div class="concept-example">
      “방금 만든 기능 자체는 괜찮은데 버튼 위치만 원래대로 돌려주세요.”<br><br>

      “데이터 저장 방식은 마음에 듭니다.
      다만 화면 구성을 변경한 것은 원하지 않았습니다.
      기존 화면 구조로 되돌리고 기능만 유지해주세요.”<br><br>

      “필터 기능은 정상입니다.
      하지만 완료된 일정의 원본 데이터를 수정하면 안 됩니다.
      현재 구현을 확인해서 필요한 경우 수정해주세요.”
    </div>
  </div>

  <div class="key-point">
    <strong>AI에게 무엇을 바꿀지만 말하지 말고,
    무엇을 유지해야 하는지도 함께 알려주면 훨씬 안전합니다.</strong>
  </div>

  <div class="summary">
    <div class="summary-title">한 번에 완성하려고 하지 않아도 됩니다</div>
    <p>
      AI 개발의 장점은 수정 비용이 매우 낮다는 것입니다.
    </p>
    <p>
      따라서 처음부터 완벽한 명세를 만들기보다
      <strong>큰 방향은 명확하게 정하고,
      실제 결과를 보면서 작은 수정들을 반복</strong>하는 방식으로 개발할 수 있습니다.
    </p>
  </div>

<section class="chapter">
  <div class="chapter-number">Chapter 07</div>
  <h2>코드를 만들었다면 반드시 검증합니다</h2>

  <p>
    바이브 코딩에서는 AI가 매우 빠르게 코드를 작성할 수 있습니다.
    하지만 빠르게 만들 수 있다는 것과
    <strong>정확하게 동작한다는 것은 다른 문제</strong>입니다.
  </p>

  <p>
    따라서 Codex에게 단순히 코드를 작성하게 하는 것에서 끝내지 않고,
    가능한 범위에서 테스트까지 하나의 작업으로 맡기는 것이 좋습니다.
  </p>

  <div class="key-point">
    <strong>작업 완료의 기준을 바꿔봅니다.</strong><br><br>

    코드가 만들어졌다 → 아직 완료 아님<br>
    기능이 동작한다 → 거의 완료<br>
    관련 테스트까지 통과한다 → 완료에 가까움<br>
    실제로 직접 사용해도 문제가 없다 → 최종 확인
  </div>

  <h3>1. 테스트를 직접 작성할 필요는 없습니다</h3>

  <div class="concept">
    <div class="concept-title">🧪 Codex에게 테스트 작성과 실행도 맡길 수 있습니다.</div>

    <p>
      개발 입문자가 테스트 코드를 직접 작성하거나
      테스트 라이브러리의 사용법을 모두 배울 필요는 없습니다.
    </p>

    <p>
      중요한 것은
      <strong>어떤 기능이 정상이어야 하는지 명확하게 전달하는 것</strong>입니다.
    </p>

    <div class="concept-example">
      예를 들어 일정 저장 기능이라면 다음 내용을 검증할 수 있습니다.<br><br>

      • 제목과 날짜를 입력하면 일정이 저장되는가?<br>
      • 저장된 일정이 목록에 표시되는가?<br>
      • 수정하면 변경된 내용이 반영되는가?<br>
      • 삭제하면 실제로 사라지는가?<br>
      • 새로고침해도 저장된 데이터가 유지되는가?<br>
      • 새로운 기능 때문에 기존 일정 기능이 망가지지 않았는가?
    </div>
  </div>

  <h3>2. 테스트에는 여러 단계가 있습니다</h3>

  <div class="table-wrap">
    <table>
      <thead>
        <tr>
          <th>종류</th>
          <th>쉽게 설명하면</th>
          <th>예시</th>
        </tr>
      </thead>
      <tbody>
        <tr>
          <td><strong>Unit Test</strong></td>
          <td>작은 기능 하나를 따로 검사합니다.</td>

        </tr>
        <tr>
          <td><strong>Integration Test</strong></td>
          <td>여러 부분을 연결했을 때 정상인지 검사합니다.</td>

        </tr>
        <tr>

          <td>실제 사용자가 앱을 사용하는 흐름처럼 검사합니다.</td>

          <td>필터 기능 추가 후 기존 일정 삭제 기능도 계속 정상인지 확인</td>
        </tr>
      </tbody>
    </table>

  <div class="note">

    작은 프로젝트라면 현재 프로젝트에 이미 있는 테스트 방식을 우선 사용하고,
    기능이 많아질수록 필요한 테스트를 점진적으로 추가하면 됩니다.

  <h3>3. 기능 구현 후 검증까지 맡기는 프롬프트</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">기능 구현 후 테스트와 regression 확인</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">방금 구현한 기능을 기준으로
현재 프로젝트에서 가능한 범위의 검증을 진행해줘.

[검증 목표]
새로운 기능이 요구사항대로 동작하고,
이번 변경 때문에 기존 기능이 깨지지 않았는지 확인하고 싶다.

다음 순서로 진행해줘.

1. 현재 프로젝트에서 사용 중인 테스트 도구와 검사 방법을 먼저 확인해줘.

2. 이번 기능과 직접 관련된 기존 테스트가 있다면 실행해줘.

3. 필요한 테스트가 부족하다면
   현재 프로젝트의 테스트 방식에 맞게 적절한 테스트를 추가해줘.

4. 가능한 경우 다음 범위를 확인해줘.
   - 핵심 로직에 대한 unit test
   - 서로 연결된 기능에 대한 integration test
   - 기존 기능의 regression 여부

5. TypeScript type check, lint 또는
   프로젝트에 이미 존재하는 정적 검사 방법이 있다면 적절하게 실행해줘.

6. 테스트를 통과시키기 위해
   테스트를 무의미하게 약하게 만들거나,
   정상적인 오류를 숨기거나,
   기능을 하드코딩하지 마.

7. 테스트가 실패하면
   단순히 실패한 테스트를 삭제하거나 비활성화하지 말고
   먼저 실제 원인을 조사해줘.

8. 문제가 구현에 있다면 수정하고 다시 테스트해줘.

9. 기존 프로젝트 자체에 이미 존재하던 실패가 있다면
   이번 작업으로 발생한 문제와 구분해서 알려줘.

[완료 후 보고]
- 실행한 테스트 및 검사
- 성공한 항목
- 실패하거나 실행하지 못한 항목
- 수정한 문제
- 내가 실제 화면에서 추가로 확인해야 하는 부분

을 짧게 정리해줘.</pre>

    <div class="prompt-purpose">
      AI가 코드를 작성한 뒤
      스스로 검증하고 실패한 부분을 다시 수정하는 작업까지 맡길 때 사용합니다.
    </div>

      버튼을 누르고, 입력하고, 화면이 바뀌는 과정까지 자동으로 검증할 수 있습니다.
    </p>

    <div class="concept-example">

이미 Playwright 또는 비슷한 브라우저 테스트 환경이 있다면

1. 현재 프로젝트에서 E2E 테스트가 필요한 정도인지
2. 어떤 도구를 사용할 수 있는지
3. 새로운 dependency가 필요한지
4. 설정 작업의 규모는 어느 정도인지
5. 현재 프로젝트에 도입했을 때 얻는 장점과 단점

내가 도입을 결정하기 전에는
새로운 주요 테스트 framework를 임의로 추가하지 마.</pre>

  <h2>문제가 생기면 직접 코드를 찾지 말고 원인부터 조사시킵니다</h2>

      관련 코드를 조사해서 원인을 먼저 확인한 뒤

  <h3>2. 버그를 조사하고 수정하는 기본 프롬프트</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">원인부터 조사하는 버그 수정</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 다음 문제가 발생하고 있다.

[문제 상황]
일정 추가 버튼을 눌러도 새로운 일정이 화면에 나타나지 않는다.

[정상적으로 기대하는 동작]
제목과 날짜를 입력하고 저장 버튼을 누르면
새로운 일정이 목록에 즉시 표시되어야 한다.

[확인한 내용]
- 화면 자체는 정상적으로 표시된다.
- 입력창에 내용을 입력할 수 있다.
- 저장 버튼도 클릭할 수 있다.
- 하지만 저장 후 일정 목록에는 변화가 없다.

[최근 변경 사항]
이 문제가 발생하기 전에 일정 필터 기능을 추가했다.

다음 방식으로 조사해줘.

1. 추측해서 바로 코드를 수정하지 말고
   먼저 관련 이벤트, 상태 관리, 저장 로직, 화면 반영 흐름을 확인해줘.

2. 최근 변경 사항이 이번 문제와 관련 있는지 확인해줘.

3. 근본 원인을 설명할 수 있을 정도로 확인한 뒤 수정해줘.

4. 기존 기능과 현재 architecture를 불필요하게 변경하지 마.

5. 오류를 숨기거나,
   try/catch로 단순히 무시하거나,
   하드코딩으로 정상처럼 보이게 만들지 마.

6. 필요한 부분만 최소한으로 수정해줘.

7. 가능하면 이 문제가 다시 발생하는 것을 막을 수 있는 테스트를 추가해줘.

8. 관련 테스트와 기존 regression 테스트를 실행해줘.

작업이 끝나면
- 문제의 원인
- 수정한 내용
- 테스트 결과
- 내가 직접 확인해야 할 동작

을 간단하게 정리해줘.</pre>

    <div class="prompt-purpose">

      문제의 위치를 직접 찾지 않고 Codex에게 조사부터 맡기는 기본 프롬프트입니다.

  <h3>3. Codex의 설명 자체가 이해되지 않으면 다시 ChatGPT에 가져옵니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">버그 원인 설명을 이해하기</span>
      <span class="prompt-target">ChatGPT</span>

    <pre class="prompt-body">Codex가 현재 발생한 버그의 원인을 아래처럼 설명했다.

[Codex 설명]
여기에 Codex의 설명을 그대로 붙여 넣기

나는 개발 입문자이므로
이 설명을 읽고도 문제가 정확히 무엇인지 잘 모르겠다.

다음 기준으로 설명해줘.

1. 실제로 어떤 일이 잘못된 것인지 쉬운 말로 설명해줘.
2. 사용자가 앱을 사용할 때 어떤 과정에서 문제가 발생하는지 설명해줘.

내가 직접 확인할 부분만 간단하게 알려줘.</pre>
  </div>

<section class="chapter">
  <div class="chapter-number">Chapter 07</div>
  <h2>코드를 만들었다면 반드시 검증합니다</h2>

  <p>
    바이브 코딩에서는 AI가 매우 빠르게 코드를 작성할 수 있습니다.
    하지만 빠르게 만들 수 있다는 것과
    <strong>정확하게 동작한다는 것은 다른 문제</strong>입니다.
  </p>

  <p>
    따라서 Codex에게 단순히 코드를 작성하게 하는 것에서 끝내지 않고,
    가능한 범위에서 테스트까지 하나의 작업으로 맡기는 것이 좋습니다.
  </p>

  <div class="key-point">
    <strong>작업 완료의 기준을 바꿔봅니다.</strong><br><br>

    코드가 만들어졌다 → 아직 완료 아님<br>
    기능이 동작한다 → 거의 완료<br>
    관련 테스트까지 통과한다 → 완료에 가까움<br>
    실제로 직접 사용해도 문제가 없다 → 최종 확인
  </div>

  <h3>1. 테스트를 직접 작성할 필요는 없습니다</h3>

  <div class="concept">
    <div class="concept-title">🧪 Codex에게 테스트 작성과 실행도 맡길 수 있습니다.</div>

    <p>
      개발 입문자가 테스트 코드를 직접 작성하거나
      테스트 라이브러리의 사용법을 모두 배울 필요는 없습니다.
    </p>

    <p>
      중요한 것은
      <strong>어떤 기능이 정상이어야 하는지 명확하게 전달하는 것</strong>입니다.
    </p>

    <div class="concept-example">
      예를 들어 일정 저장 기능이라면 다음 내용을 검증할 수 있습니다.<br><br>

      • 제목과 날짜를 입력하면 일정이 저장되는가?<br>
      • 저장된 일정이 목록에 표시되는가?<br>
      • 수정하면 변경된 내용이 반영되는가?<br>
      • 삭제하면 실제로 사라지는가?<br>
      • 새로고침해도 저장된 데이터가 유지되는가?<br>
      • 새로운 기능 때문에 기존 일정 기능이 망가지지 않았는가?
    </div>
  </div>

  <h3>2. 테스트에는 여러 단계가 있습니다</h3>

  <div class="table-wrap">
    <table>
      <thead>
        <tr>
          <th>종류</th>
          <th>쉽게 설명하면</th>
          <th>예시</th>
        </tr>
      </thead>
      <tbody>
        <tr>
          <td><strong>Unit Test</strong></td>
          <td>작은 기능 하나를 따로 검사합니다.</td>
          <td>날짜를 정렬하는 함수가 제대로 동작하는지 확인</td>
        </tr>
        <tr>
          <td><strong>Integration Test</strong></td>
          <td>여러 부분을 연결했을 때 정상인지 검사합니다.</td>
          <td>일정 입력 → 저장 → 화면 목록 반영까지 확인</td>
        </tr>
        <tr>
          <td><strong>E2E Test</strong></td>
          <td>실제 사용자가 앱을 사용하는 흐름처럼 검사합니다.</td>
          <td>페이지 접속 → 일정 추가 → 수정 → 새로고침 → 삭제</td>
        </tr>
        <tr>
          <td><strong>Regression Test</strong></td>
          <td>새로운 수정 때문에 기존 기능이 망가지지 않았는지 확인합니다.</td>
          <td>필터 기능 추가 후 기존 일정 삭제 기능도 계속 정상인지 확인</td>
        </tr>
      </tbody>
    </table>
  </div>

  <div class="note">
    <span class="box-title">📌 처음부터 모든 테스트를 완벽하게 만들 필요는 없습니다</span>
    작은 프로젝트라면 현재 프로젝트에 이미 있는 테스트 방식을 우선 사용하고,
    기능이 많아질수록 필요한 테스트를 점진적으로 추가하면 됩니다.
  </div>

  <h3>3. 기능 구현 후 검증까지 맡기는 프롬프트</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">기능 구현 후 테스트와 regression 확인</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">방금 구현한 기능을 기준으로
현재 프로젝트에서 가능한 범위의 검증을 진행해줘.

[검증 목표]
새로운 기능이 요구사항대로 동작하고,
이번 변경 때문에 기존 기능이 깨지지 않았는지 확인하고 싶다.

다음 순서로 진행해줘.

1. 현재 프로젝트에서 사용 중인 테스트 도구와 검사 방법을 먼저 확인해줘.

2. 이번 기능과 직접 관련된 기존 테스트가 있다면 실행해줘.

3. 필요한 테스트가 부족하다면
   현재 프로젝트의 테스트 방식에 맞게 적절한 테스트를 추가해줘.

4. 가능한 경우 다음 범위를 확인해줘.
   - 핵심 로직에 대한 unit test
   - 서로 연결된 기능에 대한 integration test
   - 기존 기능의 regression 여부

5. TypeScript type check, lint 또는
   프로젝트에 이미 존재하는 정적 검사 방법이 있다면 적절하게 실행해줘.

6. 테스트를 통과시키기 위해
   테스트를 무의미하게 약하게 만들거나,
   정상적인 오류를 숨기거나,
   기능을 하드코딩하지 마.

7. 테스트가 실패하면
   단순히 실패한 테스트를 삭제하거나 비활성화하지 말고
   먼저 실제 원인을 조사해줘.

8. 문제가 구현에 있다면 수정하고 다시 테스트해줘.

9. 기존 프로젝트 자체에 이미 존재하던 실패가 있다면
   이번 작업으로 발생한 문제와 구분해서 알려줘.

[완료 후 보고]
- 실행한 테스트 및 검사
- 성공한 항목
- 실패하거나 실행하지 못한 항목
- 수정한 문제
- 내가 실제 화면에서 추가로 확인해야 하는 부분

을 짧게 정리해줘.</pre>

    <div class="prompt-purpose">
      AI가 코드를 작성한 뒤
      스스로 검증하고 실패한 부분을 다시 수정하는 작업까지 맡길 때 사용합니다.
    </div>
  </div>

  <h3>4. 브라우저에서 실제 사용자처럼 테스트할 수도 있습니다</h3>

  <div class="concept">
    <div class="concept-title">🌐 E2E 테스트는 실제 사용 흐름에 더 가깝습니다.</div>

    <p>
      프로젝트에 Playwright와 같은 브라우저 자동화 도구가 구성되어 있다면
      실제 브라우저 엔진을 사용해서
      버튼을 누르고, 입력하고, 화면이 바뀌는 과정까지 자동으로 검증할 수 있습니다.
    </p>

    <div class="concept-example">
      예를 들어 자동 테스트가 다음과 같은 행동을 할 수 있습니다.<br><br>

      페이지 열기<br>
      ↓<br>
      “일정 추가” 버튼 클릭<br>
      ↓<br>
      제목과 날짜 입력<br>
      ↓<br>
      저장 버튼 클릭<br>
      ↓<br>
      일정이 화면에 나타나는지 확인<br>
      ↓<br>
      페이지 새로고침<br>
      ↓<br>
      일정이 그대로 남아 있는지 확인
    </div>
  </div>

  <div class="warning">
    <span class="box-title">⚠️ 자동 테스트가 모든 것을 판단해 주는 것은 아닙니다</span>
    버튼이 실제로 눌리는지는 자동으로 확인할 수 있어도,
    화면이 보기 좋은지, 사용하기 편한지,
    애니메이션이 자연스러운지 같은 부분은
    마지막에 사람이 직접 사용하는 것이 좋습니다.
  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">브라우저 자동 테스트가 가능한지 확인하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 프로젝트에서
실제 사용자 흐름을 자동으로 검증할 수 있는 E2E 테스트 환경이 있는지 확인해줘.

이미 Playwright 또는 비슷한 브라우저 테스트 환경이 있다면
현재 방식과 설정을 유지해서 이번 기능의 주요 사용자 흐름을 테스트해줘.

현재 E2E 테스트 환경이 없다면
바로 새로운 도구를 설치하지 말고 다음 내용을 먼저 알려줘.

1. 현재 프로젝트에서 E2E 테스트가 필요한 정도인지
2. 어떤 도구를 사용할 수 있는지
3. 새로운 dependency가 필요한지
4. 설정 작업의 규모는 어느 정도인지
5. 현재 프로젝트에 도입했을 때 얻는 장점과 단점

내가 도입을 결정하기 전에는
새로운 주요 테스트 framework를 임의로 추가하지 마.</pre>

    <div class="prompt-purpose">
      프로젝트에 없는 테스트 도구를 Codex가 마음대로 추가하지 않도록 하면서
      브라우저 테스트 도입 여부를 판단하는 프롬프트입니다.
    </div>
  </div>

  <h2>문제가 생기면 직접 코드를 찾지 말고 원인부터 조사시킵니다</h2>

  <p>
    개발 중에는 정상적으로 작동하던 기능이 갑자기 망가지거나,
    버튼을 눌러도 아무 반응이 없거나,
    예상하지 못한 오류가 발생할 수 있습니다.
  </p>

  <p>
    이때 개발 입문자가 직접 문제가 있는 파일을 찾아낼 필요는 없습니다.
  </p>

  <div class="key-point">
    <strong>증상을 정확하게 설명하고,
    Codex에게 관련 코드를 조사해서 원인을 찾도록 요청합니다.</strong>
  </div>

  <h3>1. “안 돼요. 고쳐주세요.”보다 좋은 요청</h3>

  <div class="compare-grid">
    <div class="compare-card bad">
      <span class="compare-label">❌ 정보가 부족한 요청</span>
      일정 기능 안 돼. 고쳐줘.
    </div>

    <div class="compare-card good">
      <span class="compare-label">✅ 조사할 수 있는 요청</span>
      일정 추가 버튼을 누르면 아무 반응이 없습니다.
      최근 필터 기능을 추가한 이후부터 발생했습니다.
      관련 코드를 조사해서 원인을 먼저 확인한 뒤
      필요한 부분만 수정해주세요.
    </div>
  </div>

  <h3>2. 버그를 조사하고 수정하는 기본 프롬프트</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">원인부터 조사하는 버그 수정</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 다음 문제가 발생하고 있다.

[문제 상황]
일정 추가 버튼을 눌러도 새로운 일정이 화면에 나타나지 않는다.

[정상적으로 기대하는 동작]
제목과 날짜를 입력하고 저장 버튼을 누르면
새로운 일정이 목록에 즉시 표시되어야 한다.

[확인한 내용]
- 화면 자체는 정상적으로 표시된다.
- 입력창에 내용을 입력할 수 있다.
- 저장 버튼도 클릭할 수 있다.
- 하지만 저장 후 일정 목록에는 변화가 없다.

[최근 변경 사항]
이 문제가 발생하기 전에 일정 필터 기능을 추가했다.

다음 방식으로 조사해줘.

1. 추측해서 바로 코드를 수정하지 말고
   먼저 관련 이벤트, 상태 관리, 저장 로직, 화면 반영 흐름을 확인해줘.

2. 최근 변경 사항이 이번 문제와 관련 있는지 확인해줘.

3. 근본 원인을 설명할 수 있을 정도로 확인한 뒤 수정해줘.

4. 기존 기능과 현재 architecture를 불필요하게 변경하지 마.

5. 오류를 숨기거나,
   try/catch로 단순히 무시하거나,
   하드코딩으로 정상처럼 보이게 만들지 마.

6. 필요한 부분만 최소한으로 수정해줘.

7. 가능하면 이 문제가 다시 발생하는 것을 막을 수 있는 테스트를 추가해줘.

8. 관련 테스트와 기존 regression 테스트를 실행해줘.

작업이 끝나면
- 문제의 원인
- 수정한 내용
- 테스트 결과
- 내가 직접 확인해야 할 동작

을 간단하게 정리해줘.</pre>

이 변경이 영향을 주는 영역을 조사하고,
가능한 방법과 각각의 장단점을 알려줘.

기존 데이터, 기존 기능, dependency,
보안 또는 migration에 영향을 줄 수 있다면 함께 설명해줘.

내가 결정해야 할 사항을 정리한 뒤 멈춰줘.</pre>
  </div>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">⑩ 작업을 끝낼 때</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">이번 작업을 마무리하기 전에 최종 검토해줘.

- 요구사항이 모두 구현되었는지
- 관련 테스트가 통과하는지
- 기존 기능에 regression이 없는지
- 임시방편이나 하드코딩이 남아 있지 않은지
- 불필요한 dependency가 추가되지 않았는지
- 장기적으로 남겨야 할 중요한 결정이 있는지

확인해줘.

필요한 프로젝트 문서가 있다면 갱신하고,
완료된 내용, 테스트 결과,
내가 직접 확인할 부분만 간단하게 알려줘.</pre>
  </div>
</section>
