<section class="chapter">
  <div class="chapter-number">Chapter 01</div>

  <h2>가장 먼저 프로젝트의 기본 틀을 만듭니다</h2>

  <p>
    아직 소스코드가 하나도 없는 상태라고 생각해봅시다.
  </p>

  <p>
    개발 경험이 없다면
    React를 써야 하는지, 어떤 라이브러리가 필요한지,
    프로젝트 구조를 어떻게 만들어야 하는지 알기 어렵습니다.
  </p>

  <p>
    하지만 그 기술을 먼저 공부할 필요는 없습니다.
  </p>

  <div class="key-point">
    <strong>기술을 모르겠다면 Codex에게 기술을 물어보게 하지 않습니다.</strong><br><br>

    대신 이렇게 말합니다.<br><br>

    “나는 기술을 모르니까 구현 방법은 네가 판단해.
    대신 네가 판단하기 위해 내가 알려줘야 할 내용을 질문해줘.”
  </div>


  <h3>1. 먼저 Codex에게 필요한 정보가 무엇인지 물어봅니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">프로젝트를 시작하기 위해 필요한 정보 물어보기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">나는 웹 기반의 실시간 협업 아이디어 보드를 만들고 싶어.

나는 개발 입문자라서
framework, library, state management,
database 같은 기술적인 내용은 잘 모른다.

따라서 기술 선택을 나에게 질문하지 말고,
현재 규모에 적절하고 유지보수하기 쉬운 방법은 네가 판단해줘.

아직 프로젝트를 만들지는 마.

프로젝트의 기본 기술 구성과 구조를 결정하기 위해
내가 사용자 또는 서비스 기획자의 입장에서
알려줘야 하는 정보가 무엇인지 질문해줘.

한 번에 질문 하나씩 해줘.</pre>

    <div class="prompt-purpose">
      기술을 직접 선택하는 대신,
      Codex가 기술 판단에 필요한 제품 정보를 사용자에게 역으로 질문하게 합니다.
    </div>
  </div>


  <h3>2. Codex는 어떤 것을 물어볼 수 있을까요?</h3>

  <p>
    실제 질문은 상황에 따라 달라질 수 있습니다.
    중요한 것은 <strong>정확히 똑같은 질문이 나오는 것이 아니라,
    내가 답할 수 있는 제품 관점의 질문에 답하는 것</strong>입니다.
  </p>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 01 — 누가 사용하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      이 서비스는 개인이 혼자 사용하는 도구인가요,
      아니면 여러 사람이 같은 보드에 동시에 접속해서 사용하는 서비스인가요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      여러 사람이 같이 사용할 거야.
      한 방에 5~10명 정도가 동시에 접속해서
      같은 보드를 보면서 아이디어를 작성할 수 있으면 좋겠어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 02 — 어떤 기기에서 사용하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      주로 PC에서 사용하는 서비스인가요?
      스마트폰이나 태블릿에서도 사용할 필요가 있나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      노트북이 기본이지만
      아이패드나 갤럭시탭에서도 사용할 수 있었으면 좋겠어.
      태블릿에서는 펜이나 손가락으로 그림을 그릴 수 있으면 좋겠어.
      스마트폰에서는 최소한 보드를 보고 간단하게 조작할 수 있으면 좋겠어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 03 — 무엇을 가장 중요하게 사용하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      이 서비스에서 가장 중요한 사용자 행동은 무엇인가요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      회의할 때 아이디어를 빠르게 공유하는 게 가장 중요해.
      누군가는 그림을 그리고,
      누군가는 텍스트나 포스트잇을 추가하고,
      다른 사람이 그것을 이동하거나 색을 바꿀 수 있었으면 좋겠어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 04 — 데이터는 얼마나 유지되어야 하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      작성한 보드는 브라우저를 닫거나
      다시 접속한 뒤에도 남아 있어야 하나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      응.
      회의가 끝난 다음에도 다시 들어와서
      이전에 작성한 내용을 볼 수 있어야 해.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 05 — 로그인은 필요한가요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      처음 버전부터 회원가입과 로그인이 필요한가요?
      아니면 링크를 받은 사람이 바로 보드에 들어오는 방식이면 되나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      처음 버전에서는 로그인까지는 필요 없어.
      링크를 공유하면 다른 사람이 바로 들어올 수 있으면 좋겠어.
      로그인은 나중에 필요하면 추가하자.
    </div>
  </div>


  <div class="note">
    <span class="box-title">📌 답을 전문적으로 할 필요는 없습니다</span>

    “WebSocket을 사용하고 싶습니다.”
    “NoSQL Database를 사용하겠습니다.”
    같은 기술적인 답을 할 필요가 없습니다.<br><br>

    <strong>
      “여러 사람이 동시에 써야 해.”<br>
      “태블릿에서도 펜으로 그리고 싶어.”<br>
      “로그인은 아직 필요 없어.”
    </strong><br><br>

    이런 식으로 실제 사용 경험만 설명하면 됩니다.
  </div>


  <h3>3. 질문이 끝났다면 프로젝트 기본 틀만 생성합니다</h3>

  <p>
    Codex와 대화해서 필요한 정보가 충분히 모였다면
    이제 별도의 명령으로 프로젝트를 생성합니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">프로젝트 기본 틀 생성하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">좋아.

지금까지 내가 답한 내용을 기준으로
현재 VS Code 디렉터리에
웹 애플리케이션 프로젝트의 기본 틀을 만들어줘.

구체적인 기술 스택은
현재 요구사항과 프로젝트 규모에 맞게 네가 판단해줘.

다음 원칙만 지켜줘.

- 유지보수하기 쉬운 일반적인 기술을 우선한다.
- 현재 규모에 비해 지나치게 복잡한 architecture는 사용하지 않는다.
- 불필요한 dependency는 추가하지 않는다.
- 아직 필요하지 않은 기능을 미리 구현하지 않는다.

이번 작업에서는
프로젝트 기본 틀만 만들어줘.

아직 실제 아이디어 보드 기능은 구현하지 마.
`AGENTS.md`와 `docs/*.md`도 아직 만들지 마.
배포도 하지 마.</pre>

    <div class="prompt-purpose">
      앞에서 수집한 요구사항을 바탕으로
      실제 개발을 시작할 수 있는 프로젝트 골격만 생성합니다.
    </div>
  </div>


  <h3>4. 여기서 무엇을 배운 것일까요?</h3>

  <div class="concept">
    <div class="concept-title">
      🧠 기술을 몰라도 개발을 시작할 수 있는 이유
    </div>

    <p>
      사용자는 기술을 선택하지 않았습니다.
    </p>

    <p>
      대신 어떤 서비스를 만들고 싶은지,
      누가 어떻게 사용할지를 설명했습니다.
    </p>

    <p>
      Codex는 그 정보를 바탕으로
      실제 구현에 필요한 기술을 판단합니다.
    </p>
  </div>


  <div class="key-point">
    <strong>
      내가 어떤 Context를 전달해야 하는지 모르겠다?
    </strong><br><br>

    그러면 억지로 프롬프트를 길게 만들지 말고
    <strong>AI에게 필요한 정보를 질문하게 하면 됩니다.</strong>
  </div>


  <div class="practice">
    <div class="practice-title">🚀 실습</div>

    <div class="practice-goal">
      실제 Codex에서 프로젝트 생성 대화를 진행합니다.
    </div>

    <ol>
      <li>첫 번째 프롬프트를 Codex에게 전달합니다.</li>
      <li>Codex가 하는 질문에 자연어로 답합니다.</li>
      <li>모르는 기술적인 질문이 나오면 “기술은 네가 판단해”라고 다시 알려줍니다.</li>
      <li>필요한 정보가 모이면 프로젝트 기본 틀 생성 명령을 전달합니다.</li>
      <li>프로젝트가 정상적으로 생성되었는지만 확인합니다.</li>
    </ol>
  </div>


  <div class="summary">
    <div class="summary-title">Chapter 01의 핵심</div>

    <p>
      <strong>
        기술을 직접 선택하는 것이 아니라,
        Codex가 판단하기 위해 필요한 사용자 정보를 질문하게 합니다.
      </strong>
    </p>

    <p>
      그리고 충분한 정보가 모이면
      프로젝트의 기본 틀만 생성합니다.
    </p>

    <p>
      다음 Chapter에서는
      같은 방법으로
      <strong>AGENTS.md와 docs/*.md에 무엇을 기록해야 하는지 Codex에게 질문</strong>합니다.
    </p>
  </div>
</section>

<section class="chapter">
  <div class="chapter-number">Chapter 02</div>

  <h2>Codex가 앞으로 참고할 프로젝트 문서를 만듭니다</h2>

  <p>
    프로젝트의 기본 틀이 만들어졌다면
    바로 기능 개발을 시작하기 전에
    <strong>Codex가 앞으로 계속 참고할 프로젝트 정보</strong>를 남겨둡니다.
  </p>

  <p>
    이때 사용할 수 있는 것이
    <code>AGENTS.md</code>와 <code>docs/*.md</code>입니다.
  </p>

  <div class="concept">
    <div class="concept-title">
      🤖 AGENTS.md
    </div>

    <div class="concept-subtitle">
      Codex가 이 프로젝트에서 작업할 때 지켜야 하는 기본적인 작업 원칙
    </div>

    <div class="concept-example">
      예를 들어:<br><br>

      • 기존 기능을 함부로 깨뜨리지 않는다.<br>
      • 현재 사용 중인 주요 기술을 특별한 이유 없이 바꾸지 않는다.<br>
      • 작업 전에 관련 코드를 먼저 확인한다.<br>
      • 불필요한 라이브러리를 추가하지 않는다.<br>
      • 배포는 사용자가 요청했을 때만 진행한다.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      📚 docs/*.md
    </div>

    <div class="concept-subtitle">
      우리가 어떤 프로그램을 만들고 있는지 설명하는 프로젝트 문서
    </div>

    <div class="concept-example">
      예를 들어:<br><br>

      • 이 서비스의 목적은 무엇인가?<br>
      • 누가 사용하는가?<br>
      • 어떤 기능이 필요한가?<br>
      • 어떤 기기에서 사용해야 하는가?<br>
      • 데이터는 어떻게 유지되어야 하는가?<br>
      • 현재 만들지 않을 기능은 무엇인가?
    </div>
  </div>


  <div class="key-point">
    <strong>
      AGENTS.md = Codex가 어떻게 작업해야 하는가
    </strong>
    <br><br>
    <strong>
      docs/*.md = 우리가 무엇을 만들고 있는가
    </strong>
  </div>


  <h3>1. 문서에 무엇을 써야 할지 직접 고민하지 않습니다</h3>

  <p>
    개발 입문자가 처음부터
    어떤 프로젝트 문서가 필요한지 판단하기는 어렵습니다.
  </p>

  <p>
    그래서 이번에도 먼저 Codex에게 질문합니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">프로젝트 문서 작성을 위해 필요한 정보 물어보기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">이제 이 프로젝트에
`AGENTS.md`와 필요한 `docs/*.md` 문서를 만들고 싶어.

나는 개발 입문자라서
어떤 내용을 문서에 기록해야 하는지 잘 모른다.

현재 프로젝트 구조와
지금까지 우리가 나눈 요구사항을 먼저 확인해줘.

그리고 이 프로젝트의 문서를 만들기 위해
내가 사용자 또는 서비스 기획자의 입장에서
추가로 알려줘야 하는 정보가 있다면 질문해줘.

기술적인 구현 방법은 나에게 질문하지 말고
현재 프로젝트에 적절한 방법을 네가 판단해줘.

한 번에 질문 하나씩 해줘.

아직 문서는 만들지 마.</pre>

    <div class="prompt-purpose">
      필요한 프로젝트 정보를 Codex가 먼저 찾아보고,
      부족한 제품 정보만 사용자에게 질문하게 합니다.
    </div>
  </div>


  <div class="note">
    <span class="box-title">📌 이미 말한 내용을 다시 입력할 필요는 없습니다</span>

    앞 Chapter에서
    사용자 수, 지원 기기, 데이터 유지 여부 같은 내용을 이미 설명했다면
    Codex가 현재 대화를 참고할 수 있습니다.
    <br><br>

    이번에는 <strong>문서를 만들기 위해 아직 부족한 정보만</strong>
    추가로 질문하도록 합니다.
  </div>


  <h3>2. Codex는 어떤 질문을 할 수 있을까요?</h3>

  <p>
    실제 질문의 순서와 내용은 프로젝트 상태에 따라 달라질 수 있습니다.
  </p>

  <p>
    아래 내용은
    <strong>실시간 협업 아이디어 보드 프로젝트에서 나올 수 있는 질문과 답변의 예시</strong>입니다.
  </p>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 01 — 이 서비스가 가장 중요하게 해결해야 하는 문제는 무엇인가요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      이 서비스의 핵심 목적을 프로젝트 문서에 기록하려고 합니다.
      사용자가 이 서비스를 사용하는 가장 중요한 이유는 무엇인가요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      회의나 스터디를 할 때
      여러 사람이 말로만 아이디어를 이야기하지 않고
      같은 화면에 직접 적고 그리면서 생각을 공유하는 게 목적이야.
      <br><br>

      전문적인 디자인 작업보다는
      빠르게 아이디어를 공유하고 정리하는 데 초점을 맞추고 싶어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 02 — 처음 버전에서 반드시 필요한 기능은 무엇인가요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      첫 번째 사용할 수 있는 버전에
      반드시 포함되어야 하는 기능을 알려주세요.
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      처음에는 아래 기능 정도가 꼭 있으면 좋겠어.
      <br><br>

      • 펜으로 자유롭게 그리기<br>
      • 텍스트 추가하기<br>
      • 텍스트를 선택해서 이동하기<br>
      • 텍스트와 펜의 색 바꾸기<br>
      • 만든 요소 삭제하기<br>
      • 보드 내용을 저장하기
      <br><br>

      실시간 협업은 그 다음 단계에서 추가해도 괜찮아.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 03 — 어떤 사용 경험을 유지해야 하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      앞으로 기능을 추가하더라도
      계속 유지되어야 하는 중요한 사용 경험이나 원칙이 있나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      처음 사용하는 사람도 설명서를 보지 않고
      바로 펜이나 텍스트 도구를 사용할 수 있었으면 좋겠어.
      <br><br>

      기능이 많아지더라도
      복잡한 전문 디자인 프로그램처럼 보이지 않았으면 좋겠어.
      아이디어를 빨리 적고 움직이는 게 중요해.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 04 — 화면은 어떤 느낌이면 좋을까요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      프로젝트의 기본 UI 방향을 기록하려고 합니다.
      원하는 화면의 분위기나 사용 방식이 있나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      화면 중앙에는 넓은 작업 공간이 있었으면 좋겠어.
      <br><br>

      펜, 텍스트, 도형 같은 도구는
      화면 한쪽에 간단하게 모여 있으면 좋겠고,
      전체적으로 깔끔한 업무 도구처럼 보였으면 좋겠어.
      <br><br>

      Figma처럼 화면 위의 객체를 직접 선택하고 움직이는 느낌은 좋지만
      기능 자체는 훨씬 단순했으면 좋겠어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 05 — 처음에는 만들지 않을 기능이 있나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      프로젝트 범위가 불필요하게 커지지 않도록
      현재 버전에서 제외할 기능이 있다면 알려주세요.
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      처음에는 이런 건 필요 없어.
      <br><br>

      • 회원가입과 로그인<br>
      • 결제<br>
      • 관리자 페이지<br>
      • 복잡한 권한 관리<br>
      • Figma 같은 전문적인 벡터 편집 기능<br>
      • 플러그인 시스템<br>
      • 여러 개의 프로젝트를 관리하는 대시보드
      <br><br>

      우선 한 개의 보드가 제대로 동작하는 것부터 만들고 싶어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 06 — 기존 기능을 변경할 때 중요한 조건이 있나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      앞으로 기능을 수정하거나 추가할 때
      반드시 지켜야 하는 작업 원칙이 있나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      새로운 기능을 만들다가
      이미 잘 되던 기능이 갑자기 안 되는 건 피하고 싶어.
      <br><br>

      그리고 임시방편으로 화면만 되는 것처럼 만들지 말고

  <h3>2. Codex는 어떤 것을 물어볼 수 있을까요?</h3>

  <p>
    실제 질문은 현재 프로젝트와
    앞에서 이미 답한 내용에 따라 달라질 수 있습니다.
  </p>

  <p>
    이미 결정된 내용은 다시 묻지 않을 수도 있습니다.
  </p>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 01 — 처음 화면에 무엇이 보여야 하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      사용자가 처음 보드에 들어왔을 때
      어떤 화면이 보이면 좋을까요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      화면 대부분은 아이디어를 작성할 수 있는
      넓은 빈 작업 공간이면 좋겠어.
      <br><br>

      그리고 한쪽에는
      펜, 텍스트, 포스트잇, 선택 같은
      자주 사용하는 도구들이 보이면 좋겠어.
      <br><br>

      처음 봐도 어디에 아이디어를 작성해야 하는지
      바로 알 수 있었으면 좋겠어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 02 — 펜은 어떻게 사용하면 좋을까요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      자유롭게 그림을 그리는 기능에서
      사용자에게 필요한 기본 동작을 알려주세요.
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      펜 도구를 선택하고
      작업 공간을 누른 상태로 움직이면
      그대로 선이 그려졌으면 좋겠어.
      <br><br>

      노트북에서는 마우스로 사용할 수 있고,
      태블릿에서는 펜이나 손가락으로도
      자연스럽게 그릴 수 있었으면 좋겠어.
      <br><br>

      처음에는 복잡한 브러시 기능까지는 필요 없어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 03 — 텍스트는 어떻게 추가하고 수정하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      텍스트를 추가한 뒤
      사용자가 어떤 작업을 할 수 있어야 하나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      텍스트 도구를 선택하고
      원하는 위치를 누르면 글을 입력할 수 있었으면 좋겠어.
      <br><br>

      입력한 다음에도
      그 텍스트가 그림에 완전히 합쳐지는 게 아니라
      하나의 객체처럼 남아 있었으면 좋겠어.
      <br><br>

      나중에 다시 선택해서
      위치를 옮기거나 내용을 수정할 수 있어야 해.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 04 — 포스트잇은 어떤 역할인가요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      일반 텍스트와 포스트잇은
      어떻게 다르게 사용하면 좋을까요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      일반 텍스트는 화면에 바로 글자를 적는 용도고,
      포스트잇은 아이디어 하나를 카드처럼 적는 용도로 사용하고 싶어.
      <br><br>

      포스트잇 안에 글을 입력할 수 있고
      포스트잇 전체를 자유롭게 이동할 수 있었으면 좋겠어.
      <br><br>

      회의할 때 여러 아이디어를
      포스트잇으로 빠르게 만들어서 배치하는 느낌이면 좋겠어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 05 — 객체를 선택하면 무엇을 할 수 있어야 하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      텍스트나 포스트잇 같은 객체를 선택했을 때
      어떤 편집 기능이 필요한가요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      일단 선택한 객체를 이동할 수 있어야 해.
      <br><br>

      그리고 색상을 변경하거나
      필요 없으면 삭제할 수 있었으면 좋겠어.
      <br><br>

      너무 많은 편집 기능은 아직 필요 없어.
      크기 조절이나 회전 같은 기능은 나중에 추가해도 돼.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 06 — 색상은 어느 정도 선택할 수 있어야 하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      펜이나 객체의 색상은
      사용자가 어떤 방식으로 변경하면 좋을까요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      처음부터 전문 그래픽 프로그램처럼
      복잡한 색상 기능은 필요 없어.
      <br><br>

      자주 사용하는 기본 색상을 몇 개 보여주고
      사용자가 선택할 수 있으면 충분해.
      <br><br>

      선택한 펜이나 객체에
      현재 고른 색상이 적용되면 좋겠어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 07 — 잘못 작업했을 때 어떻게 되돌리나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      사용자가 실수했을 때
      이전 작업을 되돌리는 기능이 필요한가요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      응.
      바로 전에 한 작업 정도는
      되돌릴 수 있었으면 좋겠어.
      <br><br>

      가능하다면 여러 번 Undo와 Redo를 할 수 있으면 좋지만,
      구현이 지나치게 복잡해진다면
      현재 프로젝트에 적절한 수준으로 만들어줘.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 08 — 보드 내용은 언제 저장되어야 하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      작성한 보드는 사용자가 직접 저장 버튼을 눌러야 하나요,
      아니면 자동으로 저장되면 좋을까요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      가능하면 자동으로 저장됐으면 좋겠어.
      <br><br>

      사용자가 브라우저를 새로고침하거나
      잠깐 나갔다가 다시 들어와도
      이전에 작성한 내용이 그대로 보였으면 좋겠어.
      <br><br>

      아직 여러 사용자와 공유할 필요는 없으니까
      이번 버전에 적절한 간단한 저장 방식이면 돼.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 09 — 태블릿과 모바일에서는 무엇이 중요할까요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      PC 이외의 기기에서
      반드시 유지되어야 하는 사용 경험이 있나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      태블릿에서는 그림을 그리는 기능이 중요해.
      펜이나 손가락으로 자연스럽게 그릴 수 있었으면 좋겠어.
      <br><br>

      도구 버튼도 손가락으로 누르기 너무 작지 않았으면 좋겠어.
      <br><br>

      스마트폰은 작업하기에는 화면이 작으니까
      완벽하게 PC와 똑같을 필요는 없지만
      화면이 깨지지는 않았으면 좋겠어.
    </div>
  </div>


  <div class="note">
    <span class="box-title">📌 구현 방법이 아니라 사용 방법을 설명합니다</span>

    “Canvas API를 사용하세요.”<br>
    “Pointer Event를 등록하세요.”<br>
    “Zustand Store를 만드세요.”
    <br><br>

    같은 내용을 사용자가 결정할 필요는 없습니다.
    <br><br>

    대신
    <strong>
      “태블릿에서도 펜으로 그려야 해.”<br>
      “텍스트를 나중에 다시 이동할 수 있어야 해.”<br>
      “새로고침해도 작성한 내용이 남아 있어야 해.”
    </strong>
    <br><br>

    처럼 최종적으로 원하는 동작을 설명합니다.
  </div>


  <h3>3. 충분히 결정했다면 첫 번째 버전을 구현합니다</h3>

  <p>
    Codex의 질문에 답하면서
    필요한 내용이 충분히 정리되었다면
    이제 별도의 명령으로 구현을 시작합니다.
  </p>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">첫 번째 동작 가능한 버전 구현하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">좋아.

지금까지 내가 답한 내용과
`AGENTS.md`, 관련 `docs/`를 기준으로
아이디어 보드의 첫 번째 동작 가능한 버전을 구현해줘.

이번 버전의 목적은
한 명의 사용자가 실제로 아이디어 보드를 사용할 수 있게 만드는 것이다.

지금까지 정한 요구사항을 구현하되
구체적인 component 구조,
state 관리,
입력 처리,
데이터 저장 방식,
파일 구성은
현재 프로젝트에 맞게 네가 판단해줘.

다음 원칙을 지켜줘.

- 현재 프로젝트의 주요 기술 구성을 유지한다.
- 기존에 만들어진 구조를 먼저 확인한다.
- 불필요한 dependency는 추가하지 않는다.
- 핵심 기능을 임시 코드나 TODO로 대신하지 않는다.
- 현재 요구사항에 없는 기능을 미리 추가하지 않는다.
- 현재 규모에 비해 지나치게 복잡한 구조를 만들지 않는다.
- PC와 태블릿에서 사용할 수 있는 입력 방식을 고려한다.

아직 실시간 다중 사용자 협업은 구현하지 마.
회원가입과 로그인도 만들지 마.
배포도 하지 마.

이번 작업에서는
첫 번째 버전의 기능 구현까지만 진행해줘.

완료되면
내가 실제 화면에서 확인해야 할 주요 동작만
간단하게 알려줘.</pre>

    <div class="prompt-purpose">
      앞에서 결정한 사용자 요구사항을 기준으로
      실제로 사용할 수 있는 첫 번째 아이디어 보드를 구현합니다.
    </div>
  </div>


  <h3>4. Codex가 어떤 파일을 수정하는지 직접 지정하지 않습니다</h3>

  <p>
    기능을 구현하면서 Codex는
    여러 파일을 만들거나 수정할 수 있습니다.
  </p>

  <div class="concept">
    <div class="concept-title">
      예를 들어 내부적으로는
    </div>

    <div class="concept-example">
      화면을 구성하는 코드<br>
      ↓<br><br>

      그림을 처리하는 코드<br>
      ↓<br><br>

      객체의 상태를 관리하는 코드<br>
      ↓<br><br>

      저장을 처리하는 코드<br>
      ↓<br><br>

      스타일을 담당하는 코드
    </div>
  </div>

  <p>
    하지만 개발 입문자가
    어떤 파일을 만들어야 하는지 먼저 결정할 필요는 없습니다.
  </p>

  <div class="key-point">
    <strong>
      사용자는 결과를 결정하고,
      Codex는 구현 방법을 결정합니다.
    </strong>
  </div>


  <h3>5. 구현이 끝나면 소스코드보다 실제 동작을 확인합니다</h3>

  <p>
    Codex가 “완료했습니다.”라고 말해도
    사용자가 원하는 프로그램이 실제로 만들어졌다는 뜻은 아닙니다.
  </p>

  <p>
    이제 프로그램을 직접 사용해봅니다.
  </p>


  <div class="practice">
    <div class="practice-title">✅ 첫 번째 버전 직접 확인하기</div>

    <div class="practice-goal">
      소스코드를 읽는 것이 아니라
      실제 사용자의 행동을 하나씩 실행해봅니다.
    </div>

    <ol>
      <li>
        펜 도구를 선택하고 실제로 선을 그려봅니다.
      </li>

      <li>
        텍스트를 추가하고 원하는 위치에 나타나는지 확인합니다.
      </li>

      <li>
        포스트잇을 만들고 내용을 입력합니다.
      </li>

      <li>
        텍스트나 포스트잇을 선택해서 다른 위치로 이동합니다.
      </li>

      <li>
        색상을 변경해봅니다.
      </li>

      <li>
        필요 없는 객체를 삭제합니다.
      </li>

      <li>
        Undo와 Redo가 있다면 실제로 사용합니다.
      </li>

      <li>
        새로고침한 뒤 작성한 내용이 유지되는지 확인합니다.
      </li>

      <li>
        가능하다면 태블릿에서도 직접 접속해서
        펜 또는 손가락 입력을 확인합니다.
      </li>
    </ol>
  </div>


  <div class="warning">
    <span class="box-title">⚠️ “완료”라는 답변보다 실제 화면을 믿습니다</span>

    AI가 구현을 완료했다고 말했더라도
    실제로 사용했을 때 원하는 방식으로 동작하지 않을 수 있습니다.
    <br><br>

    따라서 기능 구현 뒤에는
    <strong>사람이 실제 사용자 입장에서 결과를 확인하는 과정</strong>이 필요합니다.
  </div>


  <h3>6. 원하는 모습과 다르면 그대로 말합니다</h3>

  <p>
    첫 번째 결과가 마음에 들지 않는 것은 자연스럽습니다.
  </p>

  <p>
    이때 프로젝트 전체를 다시 설명할 필요는 없습니다.
  </p>

  <p>
    현재 화면에서 마음에 들지 않는 부분만
    그대로 Codex에게 이야기하면 됩니다.
  </p>


  <div class="compare-grid">
    <div class="compare-card bad">
      <span class="compare-label">❌ 필요 이상으로 기술적으로 설명</span>

      Canvas 객체 선택 로직을 수정하고
      drag event architecture를 변경해서
      object position state를 업데이트해줘.
    </div>

    <div class="compare-card good">
      <span class="compare-label">✅ 보이는 문제를 그대로 설명</span>

      텍스트를 선택해서 움직여봤는데
      손가락을 놓았을 때 원래 위치로 돌아가.
      이동한 위치에 그대로 남아 있었으면 좋겠어.
    </div>
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">사용하면서 발견한 문제 전달하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 앱을 직접 사용해봤어.

텍스트를 선택해서 이동하면
움직이는 동안에는 위치가 바뀌는데
손을 놓으면 원래 위치로 돌아가.

내가 원하는 동작은
텍스트를 옮긴 위치에 그대로 남아 있는 거야.

아직 코드는 수정하지 마.

`AGENTS.md`, 관련 `docs/`,
그리고 현재 구현을 확인해서
왜 이런 문제가 발생하는지 원인부터 찾아줘.</pre>

    <div class="prompt-purpose">
      구현 결과에서 문제가 발견되면
      기술적인 원인을 사용자가 추측하지 않고
      실제로 관찰한 현상을 전달합니다.
    </div>
  </div>


  <div class="note">
    <span class="box-title">📌 오류를 발견했다고 바로 전체를 다시 만들지 않습니다</span>

    이미 정상적으로 동작하는 부분은 그대로 두고
    문제가 있는 부분을 하나씩 확인합니다.
    <br><br>

    버그를 조사하고 수정하는 자세한 과정은
    뒤의 Chapter에서 다시 다룹니다.
  </div>


  <h3>7. 첫 번째 버전이 완성되면 무엇이 달라졌을까요?</h3>

  <p>
    처음에는 아무 기능도 없는 프로젝트였습니다.
  </p>

  <p>
    이제는 실제 사용자가
    아이디어를 화면에 표현하고 다시 편집할 수 있는
    하나의 웹 애플리케이션이 되었습니다.
  </p>


  <div class="flow">
    <li>
      <span class="flow-title">프로젝트 기본 틀</span>
      프로그램을 개발할 수 있는 환경만 있었습니다.
    </li>

    <li>
      <span class="flow-title">프로젝트 문서</span>
      무엇을 만들고 어떤 원칙을 유지할지 기록했습니다.
    </li>

    <li>
      <span class="flow-title">사용자 요구사항 확인</span>
      첫 번째 버전에 필요한 사용 경험을 Codex와 대화하며 결정했습니다.
    </li>

    <li>
      <span class="flow-title">MVP 구현</span>
      실제로 그림을 그리고 아이디어를 작성할 수 있는 첫 번째 버전을 만들었습니다.
    </li>

    <li>
      <span class="flow-title">직접 사용</span>
      소스코드가 아니라 실제 사용자 행동을 통해 결과를 확인했습니다.
    </li>
  </div>


  <div class="key-point">
    여기서부터 개발 방식이 달라집니다.
    <br><br>

    더 이상 앱 전체를 처음부터 만들 필요가 없습니다.
    <br><br>

    <strong>
      이미 만들어진 프로그램에
      필요한 기능을 하나씩 추가하고,
      마음에 들지 않는 기능을 수정하고,
      필요 없는 기능을 삭제하면서 발전시키면 됩니다.
    </strong>
  </div>

      실제로 한 사람이 사용할 수 있는

    </div>

    <ol>
      <li>

  <h2>기능을 하나씩 추가하고 수정하면서 앱을 발전시킵니다</h2>

  <p>
    첫 번째 동작 가능한 아이디어 보드가 만들어졌습니다.
  </p>

  <p>
    이제부터는 앱 전체를 처음부터 다시 만들 필요가 없습니다.
  </p>

  <p>
    실제 서비스를 개발할 때처럼
    필요한 기능을 하나씩 추가하고,
    마음에 들지 않는 동작을 수정하고,
    필요 없는 기능은 삭제하면서 발전시킵니다.
  </p>

  <div class="key-point">
    <strong>
      개발은 한 번에 완성하는 작업이 아니라,
      작은 변경을 반복하는 과정입니다.
    </strong>
  </div>


  <h3>1. 새로운 기능을 추가할 때도 먼저 필요한 정보를 질문하게 합니다</h3>

  <p>
    예를 들어 이제
    <strong>사각형 도형 기능</strong>을 추가한다고 생각해봅시다.
  </p>

  <p>
    그냥 “사각형 추가해줘.”라고 요청할 수도 있지만,
    어떤 방식으로 사용하고 싶은지에 따라 구현이 달라질 수 있습니다.
  </p>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">새로운 기능에 필요한 정보 물어보기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 아이디어 보드에
사각형 도형 기능을 추가하고 싶어.

작업 전에
`AGENTS.md`, 관련 `docs/`,
그리고 현재 구현된 도구와 객체 처리 방식을 먼저 확인해줘.

아직 코드는 수정하지 마.

이 기능을 만들기 위해
내가 사용자 또는 서비스 기획자의 입장에서
추가로 결정해야 할 내용이 있다면 질문해줘.

기술적인 구현 방법은 네가 판단하고
한 번에 질문 하나씩 해줘.</pre>

    <div class="prompt-purpose">
      새로운 기능을 바로 구현하기 전에
      기존 프로젝트와 연결해서 부족한 사용자 요구사항만 확인합니다.
    </div>
  </div>


  <h3>2. Codex는 어떤 질문을 할 수 있을까요?</h3>

  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 01 — 사각형은 어떻게 만들어야 하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      사각형 도구를 선택한 뒤
      사용자가 어떤 방식으로 사각형을 만들면 좋을까요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      사각형 도구를 선택한 다음
      작업 공간을 드래그하면
      드래그한 크기만큼 사각형이 만들어졌으면 좋겠어.
      <br><br>

      처음에는 정교한 도형 편집까지는 필요 없어.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 02 — 만든 뒤 무엇을 할 수 있어야 하나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      만들어진 사각형을 선택한 뒤
      어떤 편집 기능이 필요할까요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      다른 객체처럼 선택해서 이동할 수 있어야 하고
      색상도 바꿀 수 있었으면 좋겠어.
      <br><br>

      삭제도 가능해야 해.
      크기 조절은 나중에 추가해도 돼.
    </div>
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">새 기능 하나만 추가하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">좋아.

지금까지 내가 답한 내용을 기준으로
현재 아이디어 보드에
사각형 도형 기능 하나만 추가해줘.

작업 전에
`AGENTS.md`, 관련 `docs/`,
그리고 기존 객체 선택, 이동, 색상 변경, 삭제 기능을 먼저 확인해줘.

가능하다면 기존 객체 처리 방식을 재사용해줘.

이번 작업에서는
사각형 기능만 추가해줘.

다른 기능은 추가하지 말고
현재 정상적으로 동작하는 기존 기능은 유지해줘.

완료되면
내가 실제 화면에서 확인해야 할 동작만 알려줘.</pre>

    <div class="prompt-purpose">
      앱 전체를 다시 만들지 않고,
      현재 구조 안에 새로운 기능 하나만 추가합니다.
    </div>
  </div>


  <div class="key-point">
    <strong>
      새로운 기능 하나 = 하나의 작업
    </strong>
    <br><br>

    사각형, 화살표, 이미지 삽입, 확대/축소처럼
    기능이 여러 개라면 가능하면 하나씩 진행합니다.
  </div>


  <h3>3. 기존 기능이 마음에 들지 않으면 동작만 수정합니다</h3>

  <p>
    기능 자체는 있지만
    사용하면서 불편한 점이 발견될 수도 있습니다.
  </p>

  <p>
    예를 들어 포스트잇을 만들었는데
    현재는 항상 같은 크기로만 만들어진다고 생각해봅시다.
  </p>

  <div class="compare-grid">
    <div class="compare-card bad">
      <span class="compare-label">❌ 프로젝트 전체를 다시 요청</span>

      포스트잇 기능이 마음에 안 드니까
      아이디어 보드를 다시 만들어줘.
    </div>

    <div class="compare-card good">
      <span class="compare-label">✅ 바꾸고 싶은 동작만 설명</span>

      지금 포스트잇은 내용이 길어져도
      크기가 그대로야.
      <br><br>
      글이 많아지면 세로로 자연스럽게 늘어났으면 좋겠어.
    </div>
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">기존 기능 수정하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 포스트잇 기능의 동작을 수정하고 싶어.

지금은
내용이 길어져도 포스트잇 높이가 그대로 유지돼.

내가 원하는 동작은
글이 길어지면
내용이 보이도록 포스트잇 높이가 자연스럽게 늘어나는 거야.

작업 전에
관련 코드를 먼저 확인해줘.

기존 포스트잇의
생성, 이동, 색상 변경, 삭제 기능은 그대로 유지하고
이 동작만 수정해줘.

관련 없는 기능은 변경하지 마.</pre>

    <div class="prompt-purpose">
      현재 기능 전체를 없애지 않고
      원하는 사용자 경험만 부분적으로 수정합니다.
    </div>
  </div>


  <h3>4. UI도 보이는 문제를 그대로 설명하면 됩니다</h3>

  <p>
    디자인을 수정할 때도
    CSS나 화면 구조를 직접 설명할 필요는 없습니다.
  </p>

  <div class="concept">
    <div class="concept-title">
      🎨 예를 들어 도구 모음이 너무 복잡해 보인다면
    </div>

    <div class="concept-example">
      <strong>현재 모습</strong><br>
      도구 버튼마다 글자가 길게 표시되어 있어서
      작업 공간보다 메뉴가 너무 눈에 띈다.
      <br><br>

      <strong>원하는 모습</strong><br>
      자주 사용하는 도구는 아이콘 중심으로 단순하게 보이고
      어떤 도구인지 필요한 정도만 알 수 있었으면 좋겠다.
    </div>
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">UI 일부만 수정하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 아이디어 보드의
도구 모음 UI만 수정하고 싶어.

지금은 각 도구의 설명이 너무 크게 보여서
작업 공간보다 메뉴가 더 눈에 띄는 느낌이야.

도구 모음은 더 단순하고 작게 보이게 하고
작업 공간이 화면의 중심으로 느껴졌으면 좋겠어.

현재 기능은 모두 그대로 유지해줘.

기능 로직과 데이터 구조는 변경하지 말고
도구 모음 UI만 수정해줘.</pre>

    <div class="prompt-purpose">
      기능에 손대지 않고
      사용자가 실제로 보는 화면만 부분적으로 조정합니다.
    </div>
  </div>


  <h3>5. 필요 없는 기능은 실제로 제거합니다</h3>

  <p>
    개발 중에는
    처음에는 필요하다고 생각했던 기능이
    나중에는 오히려 불편하게 느껴질 수도 있습니다.
  </p>

  <p>
    예를 들어 테스트로 추가했던
    <strong>전체 보드 초기화 버튼</strong>을
    더 이상 사용하지 않기로 했다고 생각해봅시다.
  </p>

  <div class="warning">
    <span class="box-title">⚠️ 화면에서 버튼만 숨기는 것과 기능 삭제는 다릅니다</span>

    기능을 완전히 없애고 싶다면
    버튼뿐 아니라
    그 기능에서만 사용하던 코드도 남아 있는지 확인해야 합니다.
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">필요 없는 기능 삭제하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 아이디어 보드에서
전체 보드 초기화 기능을 더 이상 사용하지 않기로 했어.

작업 전에
이 기능과 연결된 코드를 먼저 확인해줘.

전체 초기화 기능과
이 기능에서만 사용하던 UI와 로직은 제거해줘.

하지만
개별 객체 삭제,
Undo / Redo,
자동 저장 같은 다른 기능은 유지해야 해.

공통으로 사용되는 코드는 삭제하지 말고
관련 없는 기능도 변경하지 마.

이번 작업에서는
전체 보드 초기화 기능 삭제만 진행해줘.</pre>

    <div class="prompt-purpose">
      필요 없어진 기능과
      그 기능에만 사용되던 코드를 안전하게 제거합니다.
    </div>
  </div>


  <h3>6. 이제 실시간 협업 기능을 추가합니다</h3>

  <p>
    지금까지는 한 사람이 사용하는 아이디어 보드였습니다.
  </p>

  <p>

      첫 번째 버전이 만들어진 뒤에는
      프로그램 전체를 반복해서 다시 만들지 않습니다.
    </p>

    <p>
      <strong>
        기능 하나 추가 → 직접 확인 → 필요한 부분 수정
      </strong>
      방식으로 프로젝트를 조금씩 발전시킵니다.
    </p>

    <p>
      새로운 기능이 복잡하다면
      바로 구현하지 않고
      Codex에게 먼저 필요한 사용자 정보를 질문하게 할 수 있습니다.
    </p>

    <p>
      실시간 협업처럼 기술적으로 복잡한 기능도
      사용자는 backend나 database 구조를 설계하는 대신
      <strong>여러 사용자가 실제로 무엇을 경험해야 하는지</strong>를 설명합니다.
    </p>

    <p>
      다음 Chapter에서는
      지금까지 만든 앱이 실제로 안정적으로 동작하는지
      <strong>
        테스트하고, 문제의 원인을 찾고,
        버그를 수정한 뒤 실제 서비스로 배포하는 과정
      </strong>
      을 진행합니다.
    </p>
  </div>

<section class="chapter">
  <div class="chapter-number">Chapter 05</div>

  <h2>테스트하고 문제를 해결한 뒤 실제 서비스로 배포합니다</h2>

  <p>
    아이디어 보드의 주요 기능과
    실시간 협업 기능까지 만들어졌습니다.
  </p>

  <p>
    하지만 기능이 만들어졌다고 해서
    바로 개발이 끝나는 것은 아닙니다.
  </p>

  <p>
    실제로 원하는 방식으로 동작하는지 확인하고,
    문제가 있다면 원인을 찾아 수정한 뒤
    안정적인 상태를 만들어야 합니다.
  </p>

  <div class="key-point">
    <strong>
      구현 완료 ≠ 검증 완료
    </strong>
    <br><br>

    AI가 코드를 만들었다면
    다음 단계는 실제로 그 결과가 맞는지 확인하는 것입니다.
  </div>


  <h3>1. 먼저 무엇이 정상 동작인지 정합니다</h3>

  <p>
    테스트를 하려면
    먼저 어떤 상태가 정상인지 알아야 합니다.
  </p>

  <p>
    개발 입문자가 어떤 테스트 코드를 작성해야 하는지
    직접 결정할 필요는 없습니다.
  </p>

  <p>
    대신
    <strong>사용자 입장에서 어떤 동작이 성공해야 하는지</strong>
    설명하면 됩니다.
  </p>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">테스트에 필요한 정보 물어보기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">이제 현재 아이디어 보드의
주요 기능을 테스트하고 싶어.

작업 전에
`AGENTS.md`, 관련 `docs/`,
현재 구현과 기존 테스트 환경을 먼저 확인해줘.

아직 테스트를 만들거나 실행하지 마.

현재 기능을 검증하기 위해
내가 사용자 또는 서비스 기획자의 입장에서
추가로 알려줘야 할 정상 동작이나 조건이 있다면 질문해줘.

Unit Test,
Integration Test,
E2E Test 같은 기술적인 테스트 방법은
현재 프로젝트에 맞게 네가 판단해줘.

한 번에 질문 하나씩 해줘.</pre>

    <div class="prompt-purpose">
      테스트 코드를 사용자가 설계하는 대신
      어떤 사용자 동작이 성공해야 하는지를 먼저 정합니다.
    </div>
  </div>


  <h3>2. Codex는 어떤 것을 물어볼 수 있을까요?</h3>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 01 — 그림 기능에서 반드시 정상이어야 하는 것은 무엇인가요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      펜 기능을 정상이라고 판단하기 위해
      어떤 사용자 동작이 반드시 성공해야 하나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      펜을 선택하고 작업 공간을 드래그하면
      내가 움직인 위치를 따라서 선이 그려져야 해.
      <br><br>

      그림을 그린 다음 다른 도구를 사용해도
      기존 선이 사라지면 안 돼.
      <br><br>

      태블릿에서도 펜이나 터치 입력으로
      그림을 그릴 수 있어야 해.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 02 — 객체 편집에서 중요한 동작은 무엇인가요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      텍스트나 포스트잇 같은 객체를 편집할 때
      반드시 유지되어야 하는 동작이 있나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      객체를 선택해서 이동하면
      이동한 위치에 그대로 남아 있어야 해.
      <br><br>

      색상을 바꾸면 선택한 객체만 바뀌어야 하고
      다른 객체까지 같이 바뀌면 안 돼.
      <br><br>

      객체 하나를 삭제해도
      다른 객체는 그대로 있어야 해.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 03 — 저장 기능은 어떻게 확인하면 되나요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      보드 저장 기능이 정상이라고 판단하려면
      어떤 상황에서도 데이터가 유지되어야 하나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      그림, 텍스트, 포스트잇 같은 내용을 만든 다음
      새로고침해도 그대로 남아 있어야 해.
      <br><br>

      다시 같은 보드에 들어와도
      마지막으로 작성했던 상태를 볼 수 있어야 해.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 04 — 실시간 협업에서 가장 중요한 검증은 무엇인가요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      여러 사용자 협업 기능에서
      어떤 동작이 반드시 정상적으로 공유되어야 하나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      한 사용자가 객체를 만들면
      같은 보드에 있는 다른 사람에게도 보여야 해.
      <br><br>

      이동, 수정, 삭제도 다른 화면에 반영되어야 하고
      다른 사용자가 새로고침해도 같은 상태를 봐야 해.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 예상 질문 05 — 기존 기능이 깨지지 않았는지도 확인할까요?
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      최근 추가한 실시간 협업 기능뿐 아니라
      기존 기능도 함께 검증할 필요가 있나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      응.
      <br><br>

      실시간 기능을 추가하기 전에 잘 되던
      펜, 텍스트, 포스트잇, 객체 이동, 삭제 같은 기능도
      그대로 정상인지 확인했으면 좋겠어.
    </div>
  </div>


  <div class="note">
    <span class="box-title">📌 테스트에서도 사용자는 결과를 설명합니다</span>

    사용자가
    테스트 프레임워크나 테스트 파일 구조를
    직접 결정할 필요는 없습니다.
    <br><br>

    <strong>
      “A를 하면 B가 되어야 한다.”
    </strong>
    <br><br>

    이 정상 동작을 명확하게 전달하는 것이 중요합니다.
  </div>


  <h3>3. 필요한 조건이 정리되면 자동 테스트를 실행합니다</h3>

  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">현재 기능 자동 테스트하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">좋아.

지금까지 확인한 정상 동작을 기준으로
현재 아이디어 보드를 테스트해줘.

작업 전에
현재 프로젝트의 테스트 환경과
기존 테스트가 있는지 먼저 확인해줘.

현재 프로젝트에서 사용할 수 있는 방법을 기준으로
필요한 테스트를 선택해줘.

필요한 테스트가 없다면
현재 프로젝트 구조에 맞게 추가해도 돼.

이번 작업의 목적은
현재 기능을 검증하는 것이다.

새로운 기능은 추가하지 마.
리팩터링도 하지 마.
테스트를 통과시키기 위해
기능 코드를 임의로 변경하지도 마.

테스트가 끝나면 아래만 알려줘.

- 정상적으로 확인된 기능
- 실패한 기능
- 자동으로 확인하기 어려워서 사람이 직접 확인해야 하는 부분</pre>

    <div class="prompt-purpose">
      현재 앱의 기능을 자동으로 검증하고,
      자동 테스트로 확인할 수 없는 부분도 구분합니다.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      🧪 테스트의 종류를 모두 외울 필요는 없습니다
    </div>

    <p>
      프로젝트에 따라 여러 종류의 테스트가 사용될 수 있습니다.
    </p>

    <div class="concept-example">
      <strong>Unit Test</strong><br>
      작은 로직 하나가 정상인지 확인
      <br><br>

      <strong>Integration Test</strong><br>
      여러 기능이나 구성 요소가 연결되었을 때 정상인지 확인
      <br><br>

      <strong>E2E Test</strong><br>
      실제 사용자가 프로그램을 사용하는 흐름을 기준으로 확인
    </div>

    <p>
      어떤 테스트를 어디에 사용할지는
      현재 프로젝트를 보고 Codex가 판단하게 할 수 있습니다.
    </p>
  </div>


  <h3>4. 자동 테스트와 사람이 직접 확인하는 것은 역할이 다릅니다</h3>

  <p>
    자동 테스트를 모두 통과했더라도
    화면이 실제로 사용하기 불편할 수 있습니다.
  </p>

  <p>
    반대로 사람이 몇 번 사용해봤다고 해서
    내부의 모든 경우가 정상이라는 것도 알 수 없습니다.
  </p>


  <div class="role-grid">
    <div class="role-card">
      <h3>🤖 자동 테스트</h3>

      <p>
        반복해서 확인해야 하는 기능을
        빠르고 일정하게 검사합니다.
      </p>

      <p>
        새로운 변경 때문에
        기존 기능이 깨졌는지 확인하는 데 도움이 됩니다.
      </p>
    </div>

    <div class="role-card">
      <h3>👤 직접 사용</h3>

      <p>
        화면이 실제로 편한지,
        펜의 느낌이 자연스러운지,
        협업하면서 불편한 점은 없는지 확인합니다.
      </p>

      <p>
        사용자의 실제 경험을 판단합니다.
      </p>
    </div>
  </div>


  <div class="key-point">
    <strong>
      자동 테스트 + 실제 사용 확인
    </strong>
    <br><br>

    두 가지를 함께 사용합니다.
  </div>


  <h3>5. 문제가 발견되면 바로 고치기 전에 원인을 찾습니다</h3>

  <p>
    테스트가 실패하거나
    직접 사용하면서 문제가 발견될 수 있습니다.
  </p>

  <p>
    이때 사용자가
    어느 파일의 어느 함수를 수정해야 하는지 알아낼 필요는 없습니다.
  </p>

  <p>
    실제로 발생하는 문제를 그대로 전달합니다.
  </p>


  <div class="concept">
    <div class="concept-title">
      🔍 예시 — 실시간 포스트잇 이동 문제
    </div>

    <div class="concept-example">
      노트북 A와 노트북 B가 같은 보드에 접속했습니다.
      <br><br>

      A에서 포스트잇을 이동하면
      B에서도 움직입니다.
      <br><br>

      하지만 B에서 페이지를 새로고침하면
      포스트잇이 이동하기 전 위치로 돌아갑니다.
    </div>
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">버그 원인만 조사하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 실시간 협업 기능에서 문제가 발생하고 있어.

같은 보드에 A와 B가 접속한 상태에서
A가 포스트잇을 이동하면
B 화면에도 새로운 위치가 바로 나타나.

그런데 B가 페이지를 새로고침하면
포스트잇이 이동하기 전 위치로 돌아가.

내가 원하는 동작은
이동한 최신 위치가 저장되고
새로고침한 뒤에도 그대로 보이는 거야.

아직 코드는 수정하지 마.

`AGENTS.md`, 관련 `docs/`,
그리고 현재 저장 및 실시간 동기화 코드를 확인해서
이 문제가 발생하는 실제 원인을 찾아줘.

추측만 하지 말고
현재 코드의 동작 흐름을 기준으로 조사해줘.

완료되면
개발 입문자도 이해할 수 있게
문제의 원인만 간단하게 설명해줘.</pre>

    <div class="prompt-purpose">
      문제를 바로 수정하지 않고
      현재 코드에서 실제 원인을 먼저 확인합니다.
    </div>
  </div>


  <div class="warning">
    <span class="box-title">⚠️ 원인 조사와 수정은 다른 작업입니다</span>

    문제를 조사하는 단계에서는
    코드를 변경하지 않습니다.
    <br><br>

    먼저 무엇이 문제인지 확인한 뒤
    다음 작업에서 그 문제만 수정합니다.
  </div>


  <h3>6. 원인을 확인했다면 그 문제만 수정합니다</h3>

  <p>
    Codex가 문제의 원인을 확인했다면
    이제 별도의 요청으로 수정합니다.
  </p>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">확인한 버그 수정하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">좋아.

방금 확인한
포스트잇 위치 저장 문제를 수정해줘.

목표는
한 사용자가 이동한 최신 포스트잇 위치가
다른 사용자에게 실시간으로 반영되고,
새로고침한 뒤에도 같은 위치가 유지되는 것이다.

현재 architecture와
기존 실시간 협업 기능은 유지해줘.

문제의 원인이 되는 부분만 수정하고
관련 없는 기능은 변경하지 마.

오류를 숨기거나
임시방편으로 정상처럼 보이게 만들지 마.

이번 작업에서는
이 버그 수정만 진행해줘.</pre>

    <div class="prompt-purpose">
      이미 확인한 원인에 해당하는 부분만 수정합니다.
    </div>
  </div>


  <h3>7. 수정이 끝났다면 다시 테스트합니다</h3>

  <p>
    버그가 수정되었다고 해서
    바로 다음 기능으로 넘어가지 않습니다.
  </p>

  <p>
    수정했던 문제와
    그 변경에 영향을 받을 가능성이 있는 기존 기능을 다시 확인합니다.
  </p>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">버그 수정 후 다시 검증하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">방금 수정한
포스트잇 위치 저장 문제를 다시 테스트해줘.

다음 동작이 정상인지 확인해줘.

- 한 사용자가 포스트잇을 이동한다.
- 다른 사용자 화면에도 새로운 위치가 반영된다.
- 두 사용자 모두 새로고침한다.
- 포스트잇이 최신 위치에 그대로 남아 있다.

그리고 이번 수정 때문에
기존 포스트잇 생성, 편집, 삭제,
실시간 동기화 기능이 깨지지 않았는지도
관련된 범위에서 확인해줘.

이번 작업에서는
테스트와 검증만 진행해줘.

추가 기능이나 리팩터링은 하지 마.</pre>

    <div class="prompt-purpose">
      문제 해결 여부와
      수정 때문에 기존 기능이 깨지지 않았는지를 다시 확인합니다.
    </div>
  </div>


  <div class="key-point">
    <strong>
      기능 개발 → 테스트 → 문제 발견 → 원인 조사 →
      수정 → 다시 테스트
    </strong>
    <br><br>

    실제 개발에서는 이 과정을 계속 반복합니다.
  </div>


  <h3>8. 실제 협업 환경도 직접 확인합니다</h3>

  <p>
    특히 실시간 협업처럼
    여러 사용자와 기기가 연결되는 기능은
    실제 사용 환경에서도 확인하는 것이 중요합니다.
  </p>


  <div class="practice">
    <div class="practice-title">👥 최종 협업 테스트</div>

    <div class="practice-goal">
      여러 기기에서 실제 회의를 한다고 생각하고 사용해봅니다.
    </div>

    <ol>
      <li>
        같은 보드를 노트북 두 대에서 엽니다.
      </li>

      <li>
        가능하다면 태블릿도 한 대 접속합니다.
      </li>

      <li>
        한 사용자는 펜으로 그림을 그립니다.
      </li>

      <li>
        다른 사용자는 포스트잇을 추가합니다.
      </li>

      <li>
        다른 사용자가 그 포스트잇을 이동합니다.
      </li>

      <li>
        텍스트와 도형도 추가하고 수정해봅니다.
      </li>

      <li>
        두 사용자가 번갈아 같은 보드를 편집합니다.
      </li>

      <li>
        한 사용자가 잠시 나갔다가 다시 접속합니다.
      </li>

      <li>
        모든 사용자가 같은 최신 상태를 보고 있는지 확인합니다.
      </li>
    </ol>
  </div>


  <div class="note">
    <span class="box-title">📌 실제 사용하면서 발견한 문제도 개발의 일부입니다</span>

    버튼이 너무 작다.<br>
    펜이 태블릿에서 불편하다.<br>
    포스트잇 이동이 너무 민감하다.<br>
    다른 사람 커서가 너무 눈에 띈다.
    <br><br>

    이런 문제는 테스트 실패가 아니더라도
    실제 제품을 개선할 수 있는 중요한 정보입니다.
  </div>


  <h3>9. 기능이 쌓여 코드가 복잡해졌다면 리팩터링할 수 있습니다</h3>

  <p>
    기능을 계속 추가하고 수정하다 보면
    코드에 중복이 생기거나
    처음보다 구조가 복잡해질 수 있습니다.
  </p>

  <p>
    기능은 그대로 유지하면서
    코드만 더 일관되고 관리하기 좋은 상태로 정리하는 것을
    <strong>Refactoring</strong>이라고 합니다.
  </p>


  <div class="warning">
    <span class="box-title">⚠️ 리팩터링은 새로운 기능 개발이 아닙니다</span>

    사용자가 할 수 있는 일이 달라지는 것이 아니라
    내부 구조를 정리하는 작업입니다.
    <br><br>

    따라서 리팩터링과
    새로운 기능 추가를 한 작업으로 섞지 않는 것이 좋습니다.
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">현재 프로젝트 리팩터링하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">현재 아이디어 보드의
코드 구조를 한 번 점검하고 리팩터링해줘.

작업 전에
`AGENTS.md`, 관련 `docs/`,
현재 전체 프로젝트 구조를 먼저 확인해줘.

이번 작업의 목적은
기능을 바꾸는 것이 아니라
현재 코드를 더 일관되고 유지보수하기 좋은 상태로 정리하는 것이다.

다음 원칙을 지켜줘.

- 현재 사용자 기능은 변경하지 않는다.
- 현재 framework와 주요 기술 구성은 유지한다.
- 기존 데이터 형식과 주요 API 동작은 유지한다.
- 전체 프로젝트를 새로운 architecture로 다시 만들지 않는다.
- 명확한 중복 코드는 정리한다.
- 사용하지 않는 코드가 확실하다면 제거한다.
- 지나치게 복잡해진 부분은 안전한 범위에서 단순화한다.
- 관련 없는 대규모 변경은 하지 않는다.

작업 후
기존 테스트를 실행해서
현재 기능이 유지되는지도 확인해줘.

이번 작업에서는
새로운 기능은 추가하지 마.</pre>

    <div class="prompt-purpose">
      현재 기능을 보존하면서
      누적된 코드 구조를 정리합니다.
    </div>
  </div>


  <h3>10. 리팩터링 후에도 다시 실제 기능을 확인합니다</h3>

  <p>
    리팩터링은 화면 기능을 바꾸는 작업이 아니지만
    내부 코드가 많이 변경될 수 있습니다.
  </p>

  <p>
    따라서 리팩터링 후에는
    자동 테스트와 핵심 사용자 흐름을 다시 확인합니다.
  </p>

  <div class="key-point">
    <strong>
      코드가 깔끔해졌다는 것보다
      기존 기능이 그대로 유지되는 것이 먼저입니다.
    </strong>
  </div>


  <h3>11. 이제 실제 서비스 환경으로 배포합니다</h3>

  <p>
    로컬 컴퓨터에서만 실행되는 프로그램은
    다른 사람이 주소를 입력해서 사용할 수 없습니다.
  </p>

  <p>
    실제 인터넷에서 사용할 수 있도록
    서비스 환경에 올리는 과정을
    <strong>배포</strong>라고 합니다.
  </p>


  <div class="concept">
    <div class="concept-title">
      🚀 배포가 끝나면
    </div>

    <div class="concept-example">
      내 컴퓨터에서만 실행<br>
      ↓<br><br>

      실제 인터넷 주소 생성<br>
      ↓<br><br>

      다른 사람이 URL 접속<br>
      ↓<br><br>

      여러 사용자가 같은 아이디어 보드 이용
    </div>
  </div>


  <div class="warning">
    <span class="box-title">⚠️ 배포도 별도의 작업으로 진행합니다</span>

    기능을 만들면서
    동시에 실제 서비스까지 배포하게 하지 않습니다.
    <br><br>

    기능과 테스트가 끝난 뒤
    현재 정상적인 버전을 별도로 배포합니다.
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">배포 전에 필요한 정보 확인하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">이제 현재 프로젝트를
실제로 다른 사람이 접속할 수 있게 배포하고 싶어.

아직 배포하지 마.

현재 프로젝트 구조와
기존 배포 관련 설정이 있는지 먼저 확인해줘.

배포를 진행하기 위해
내가 직접 결정하거나 제공해야 하는 정보가 있다면 알려줘.

기술적인 배포 방법은
현재 프로젝트에 적절한 방식을 네가 판단해줘.

계정이나 외부 서비스 설정처럼
내가 직접 해야 하는 일이 있다면
그 부분만 쉽게 알려줘.</pre>

    <div class="prompt-purpose">
      배포 전에 프로젝트 상태를 확인하고
      사용자가 직접 해야 하는 부분만 구분합니다.
    </div>
  </div>


  <div class="concept">
    <div class="concept-title">
      💬 배포 과정에서 이런 질문을 받을 수 있습니다
    </div>

    <div class="concept-example">
      <strong>Codex:</strong><br>
      이미 사용하고 있는 hosting 또는 backend 서비스가 있나요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      아직 아무것도 사용하고 있지 않아.
      이 프로젝트 규모에 적절하고
      입문자가 관리하기 쉬운 방식을 선택해줘.
      <br><br><br>

      <strong>Codex:</strong><br>
      공개된 인터넷 주소를 누구나 사용할 수 있게 할까요?
      <br><br>

      <strong>수강생 답변 예시:</strong><br>
      응.
      지금은 테스트와 수업용이니까
      링크를 받은 사람이 접속할 수 있으면 돼.
      결제나 회원가입은 아직 필요 없어.
    </div>
  </div>


  <div class="prompt-card">
    <div class="prompt-header">
      <span class="prompt-title">현재 버전 배포하기</span>
      <span class="prompt-target">Codex</span>
    </div>

    <pre class="prompt-body">좋아.

지금까지 확인한 내용을 기준으로
현재 아이디어 보드를 배포해줘.

배포 전에
현재 프로젝트의 빌드와 테스트가 정상인지 확인해줘.

현재 프로젝트에 이미 배포 설정이 있다면
그 설정을 우선해서 사용해줘.

새로운 배포 방식이 꼭 필요하다면
현재 프로젝트 규모에 적절하고
유지보수하기 쉬운 방법을 선택해줘.

이번 작업에서는
현재 정상적으로 완성된 버전을 배포하는 것만 진행해줘.

새로운 기능을 추가하거나
UI를 수정하거나
리팩터링하지 마.

배포가 완료되면
내가 실제로 접속해서 확인해야 할 내용만 알려줘.</pre>

    <div class="prompt-purpose">
      기능 개발과 분리해서
      검증이 끝난 현재 버전을 실제 서비스 환경에 올립니다.
    </div>
  </div>


  <h3>12. 배포가 끝났다고 개발이 끝난 것은 아닙니다</h3>

  <p>
    실제 서비스 환경에서는
    로컬에서는 발견하지 못했던 문제가 나타날 수도 있습니다.
  </p>

  <div class="practice">
    <div class="practice-title">🌐 배포 후 최종 확인</div>

    <div class="practice-goal">
      개발 환경이 아니라
      실제 사용자가 접속하는 환경에서 확인합니다.
    </div>

    <ol>
      <li>
        배포된 실제 URL에 접속합니다.
      </li>

      <li>
        새로운 보드를 열고 그림을 그려봅니다.
      </li>

      <li>
        텍스트와 포스트잇을 추가하고 이동합니다.
      </li>

      <li>
        새로고침 후 데이터가 유지되는지 확인합니다.
      </li>

      <li>
        다른 브라우저 또는 다른 기기에서 같은 보드에 접속합니다.
      </li>

      <li>
        실시간으로 변경사항이 공유되는지 확인합니다.
      </li>

      <li>
        태블릿이 있다면 펜 또는 터치 입력도 확인합니다.
      </li>

      <li>
        발견한 문제가 있다면 한 번에 하나씩 다시 Codex에게 전달합니다.
      </li>
    </ol>
  </div>


  <div class="key-point">
    배포 후 문제가 생겨도
    프로젝트를 처음부터 다시 만들지 않습니다.
    <br><br>

    <strong>
      문제 관찰 → 원인 조사 → 수정 → 테스트 → 다시 배포
    </strong>
    <br><br>

    같은 흐름으로 계속 개선합니다.
  </div>
</section>

  <h2>Codex와 개발하는 전체 흐름을 정리합니다</h2>

  <p>
    이번 수업에서는
    코딩 문법을 처음부터 모두 공부한 뒤
    프로그램을 만드는 방식으로 진행하지 않았습니다.
  </p>

  <p>
    대신 실제 서비스를 하나 만들면서
    필요한 일을 Codex에게 하나씩 맡겼습니다.
  </p>


  <ul class="flow">
    <li>
      <span class="flow-title">프로젝트 기본 틀 만들기</span>
      만들고 싶은 서비스를 설명하고,
      기술적인 선택은 Codex가 현재 규모에 맞게 판단하게 했습니다.
    </li>

    <li>
      <span class="flow-title">필요한 정보를 Codex에게 질문하게 하기</span>
      어떤 Context를 전달해야 하는지 모르겠다면
      사용자와 기획자의 입장에서 필요한 정보를 Codex가 질문하게 했습니다.
    </li>

    <li>
      <span class="flow-title">AGENTS.md와 docs/*.md 만들기</span>
      프로젝트의 작업 원칙과
      계속 참고해야 할 제품 정보를 문서로 남겼습니다.
    </li>

    <li>
      <span class="flow-title">첫 번째 동작 가능한 버전 만들기</span>
      처음부터 모든 기능을 만들지 않고
      한 명이 사용할 수 있는 기본 아이디어 보드를 먼저 완성했습니다.
    </li>

    <li>
      <span class="flow-title">기능 하나씩 추가하기</span>
      기존 프로그램을 유지하면서
      도형이나 실시간 협업 같은 새로운 기능을 하나씩 추가했습니다.
    </li>

    <li>
      <span class="flow-title">기존 기능 수정하기</span>
      마음에 들지 않는 동작은
      현재 모습과 원하는 모습을 설명해서 필요한 부분만 변경했습니다.
    </li>

    <li>
      <span class="flow-title">필요 없는 기능 삭제하기</span>
      화면만 숨기는 것이 아니라
      더 이상 필요 없는 기능과 전용 코드를 정리했습니다.
    </li>

    <li>
      <span class="flow-title">자동 테스트와 직접 확인</span>
      AI가 만들었다는 설명만 믿지 않고
      자동 테스트와 실제 사용자 행동으로 결과를 확인했습니다.
    </li>

    <li>
      <span class="flow-title">문제의 원인 조사하기</span>
      버그가 생기면 사용자가 코드를 추측하지 않고
      실제 현상을 전달해서 Codex가 원인을 조사하게 했습니다.
    </li>

    <li>
      <span class="flow-title">문제 하나만 수정하기</span>
      확인한 원인에 해당하는 부분만 수정하고
      기존 기능이 유지되는지 다시 테스트했습니다.

    <li>
      <span class="flow-title">필요할 때 리팩터링하기</span>
